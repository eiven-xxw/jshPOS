# T2-PAY-004 Provider 无关组合支付设计准入包

## 1. Owner 与模型

Payment Owner 独占 `TenderPlan`、`TenderAllocation`、份额状态和支付观察；Order/Shift Owner
独占部分现金事实和班次现金流水。Order 只在全部权威成功金额精确等于应收后完成。

一个订单最多一个活动计划、2—8 个份额、同一币种 CNY；现金最多一份且必须排在最后。
电子份额严格按 sequence 串行，不支持并发“抢付”。计划冻结后不能改金额或顺序。

## 2. 状态机

- Plan：`DRAFT → FROZEN → COLLECTING → PAID`；失败旁路为 `UNKNOWN`、`FAILED`、
  `CANCELLED`、`MANUAL_RECOVERY_REQUIRED`。
- Allocation：`PLANNED → PROCESSING → SUCCEEDED`，旁路为 `UNKNOWN`、`FAILED`、`CANCELLED`。
- `SUCCEEDED` 不可回退；`PROCESSING/UNKNOWN` 占额并阻断后续份额和替代命令。
- 取消只允许在没有成功/占额份额时执行。存在成功现金或电子份额时只能走原路退款编排。

## 3. 金额与资金不变量

1. `sum(allocation.amount_minor) = order.receivable_amount_minor`，币种完全一致。
2. `sum(SUCCEEDED) ≤ receivable`；只有相等且无 UNKNOWN/PROCESSING 才能完成订单。
3. 现金应用金额必须等于冻结份额；顾客实际交付现金可更大，找零等于交付额减应用额；
   现金事实、班次流水、审计和 Outbox 同一 Owner 事务。
4. 退款必须按原成功份额退回原介质；电子成功份额不得以现金退款替代。
5. 同幂等键异内容拒绝；UNKNOWN 只查询/回调/账单观察，禁止自动新建扣款。

## 4. 外部阻断边界

- 当前正式运行时只允许现金份额通过 Order/Shift Owner 落账；由于计划至少两份且现金
  至多一份，完整组合计划在电子轨解阻前不能形成可运行的全成功闭环。测试目录允许用
  合成电子成功状态验证后续现金、订单完成、退款原路分摊和恢复不变量，但该状态不得由
  正式装配生成，也不得作为 SANDBOX、真实资金或商业验收证据。
- `T2-PAY-002` 未解阻前，任何 ELECTRONIC collect 在生产代码必须返回
  `PAYMENT_EXTERNAL_BLOCKED`，不得引入 SDK、HTTP、回调端点、账单下载或凭据。
- Fake 仅限测试目录，不得通过依赖注入进入正式装配并返回成功。

## 5. 权限、审计与恢复

- `payment:tender:create/read/collect/cancel/recover` 分离；恢复需要受权和原因。
- 审计保存订单快照摘要、计划版本、每份金额/顺序、命令 ID、观察来源和关联 ID。
- ACK 丢失或重启后继续原 allocation command；部分成功后失败进入明确恢复工作台。
- 客户端提供的 tenant、门店、终端或“支付成功”不可作为可信资金事实。

## 6. 兼容与非目标

- 旧全现金路径继续使用 `ord_cash_payment`；新混合路径使用版本化 tender API。
- 旧单电子意图继续只读兼容；新路径通过前向迁移解除“一单一个 intent”结构限制，
  历史记录不改写。旧客户端遇到新计划必须失败关闭。
- 不包含储值、预付卡、找零跨介质、跨币种、并发电子份额、真实 Provider 或真实资金。
