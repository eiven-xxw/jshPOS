# T2-EXG-001 换货编排设计准入包

## 1. Owner 与事实

ReturnOrchestration Owner 独占换货 Saga、腿关联、检查点和审计事件；Return/Refund、
Promotion、Order、Payment、Inventory 各自仍独占原事实。交换关系不是资金或库存账本。

关键身份为 `exchange_id`、`command_id`、`payload_hash`、`original_return_command_id`、
`new_sale_command_id`、`tenant/store/terminal/operator/business_day` 与 `correlation_id`。
同幂等键异摘要必须拒绝。

## 2. 状态机与冻结点

`DRAFT → APPROVED → RETURN_PENDING → RETURN_COMPLETED → SALE_PENDING → COMPLETED`。

旁路状态：

- 原退货或退款不可知：`RETURN_UNKNOWN`，只能用原命令查询/观察；
- 新销售资金不可知：`SALE_UNKNOWN`，只能用原命令查询/观察；
- 不可逆事实前明确失败：`FAILED`；
- 部分 Owner 已成功而无法自动推进：`MANUAL_RECOVERY_REQUIRED`；
- 人工核对结束：追加 `CLOSED` 事件，不覆盖历史状态事实。

冻结点为 `APPROVED`：冻结原订单/行/促销快照身份、退货数量、预计退款、新销售购物篮、
报价 fingerprint、两条命令身份及摘要。过期报价只能重新预检形成新草稿，不能覆盖已批准换货。

## 3. 不变量

1. 退货累计数量和退款占额不超过原单上限；最后一次合法退款吸收舍入余数。
2. 新销售只能在原退货/退款权威完成后发起；任何 `UNKNOWN` 阻断推进。
3. 新销售应收沿用 `gross - discount + surcharge = receivable`，不由换货模块重算。
4. 展示差额只等于两条权威金额之差，不形成第三条资金事实。
5. 退款、现金、电子支付、库存、成本和促销事实成功后不可回退或覆盖。
6. 只允许同租户、同门店；客户端 tenant/store 不能成为授权依据。

## 4. 事务与恢复

- 创建换货、两条腿、首个事件、审计与 Outbox 在 Return Owner 同一 MySQL 事务。
- Owner 调用分别通过版本化应用端口与 Inbox/Outbox；不使用跨 Owner 数据库事务。
- POS 只保存本地恢复投影和原命令身份；V1 发起换货要求在线，断网时只允许查询本地已知状态，
  新建入口返回 `EXCHANGE_ONLINE_REQUIRED`，避免离线双退款。
- ACK 丢失、超时或进程重启必须重用原 ID 和摘要。人工恢复只能“观察/推进原命令”，
  不允许重新创建退款或销售。

## 5. 权限与审计

- `pos:exchange:preview/read/create`：门店数据范围；
- `pos:exchange:approve`：受权岗位和原因；
- `pos:exchange:recover`：主管/运维双重权限和强制原因；
- 审计记录前后状态、版本、原命令引用、操作者、设备、业务日、关联 ID 和脱敏错误。

## 6. 容量、兼容和非目标

- 单次最多 20 条退货行与 20 条新销售行；每个 exchange 恰有 RETURN/SALE 两条腿。
- 旧客户端不显示入口，旧退货和销售接口不变；Schema 只前进。
- 不包含跨店、无原单、跨币种、批次/序列号、配送、储值、优惠券或电子 Provider 对接。
