# 持久化、迁移、容量、兼容与回退设计

## 1. 迁移原则

- 本阶段不创建迁移文件；登记表只描述获批编码后的前向迁移计划。
- MySQL Flyway 与 SQLite 已发布迁移不可修改、重排或复用版本号。
- 所有正式表包含主键、`tenant_id VARCHAR(20)`、Owner、状态/版本、摘要、时间戳、
  可信范围索引和中文 COMMENT；离线实体使用 ULID。
- 数量使用 `DECIMAL(19,6)`，金额使用最小货币单位整数并保存币种，禁止浮点数。

## 2. 计划对象

完整清单见 `contracts/t2/gate7b-s20b/persistence-migration-register.csv`。核心为：

- EXG：MySQL `ret_exchange/ret_exchange_leg/ret_exchange_event`，SQLite
  `local_exchange_plan/local_exchange_leg`；
- PAY：MySQL `pay_tender_plan/pay_tender_allocation/pay_tender_history/ord_cash_tender`，
  SQLite `local_tender_plan/local_tender_allocation/local_tender_event/local_cash_tender`；
- 现有 `pay_payment_intent` 和 `shf_cash_ledger` 只允许兼容性前向扩展，不覆盖历史。

## 3. 约束与索引

- tenant + id、tenant + order + active-state、tenant + idempotency-key 唯一；摘要参与异内容拒绝。
- 份额 sequence 唯一、1—8；应用层与数据库双重校验总额、现金唯一/最后、状态版本。
- 事件/history 只追加；禁止 UPDATE/DELETE 的数据库保护必须纳入 MySQL 测试。
- 恢复扫描按 tenant/store/state/updated_at 索引，禁止无租户全表任务。

## 4. 容量和归档

- 每单最多 8 个份额；每个换货 2 条腿、每腿最多 20 行引用。
- 热路径不读取全量 history；查询使用快照 + 分页事件。百万合成事件必须验证索引计划。
- 审计/事件保留沿用商业 V1 统一政策；清理只允许归档只追加事实，不删除资金和订单依据。

## 5. 兼容、回退和前向修复

- 先部署兼容 Schema，再部署读写新版本，最后开放受权入口；旧客户端看不到新入口。
- 功能回退是关闭新建入口，既有 Saga/计划继续查询、观察和恢复，绝不回滚数据库版本。
- 迁移中断、半部署、旧/新客户端交叉和投影损坏必须失败关闭，并由新迁移/修复任务前向解决。
- 任何成功资金或库存事实不能因应用回退删除、覆盖或改写。
