## 2. T2-Prep GO 条件

以下全部满足才可建议进入正式编码：

- T2-Prep 文档、ADR、RTM、CI 和证据完整；
- 商业 V1 和便利店第一波次冻结；
- Gate 0 的 Requirement ID、Owner、验收、非目标和依赖明确；
- 详细设计 31—40 的 12 个决策项有截止门和责任人；
- T1 外部阻断、T2 映射阻断和证据等级没有被篡改；
- 生产业务目录相对 Week 4 基线变化为 0；
- 候选 tag 方案准备完成但未创建；
- 项目发起人明确授权哪一 Gate/需求可转 `READY`。

## 3. CONDITIONAL GO 条件

允许先启动 Gate 0/1 内部正式开发，同时满足：

- 硬件、支付、伙伴有可执行并行解阻计划；
- Gate 0/1 不依赖真实支付/实机即可独立验收；
- 支付、设备和试点相关需求保持 `BLOCKED`；
- 不对外宣称 Alpha、商用或硬件/支付支持完成。

当前推荐将在 T2-Prep CI 完成后评估，不能预先写成已批准。

## 4. NO-GO 自动触发

- 未经确认创建 tag 或开始业务编码；
- T1 `BLOCKED/DEFERRED` 被无证据解除；
- 正式 T2 需求在 Prep 中被标记实现/验收；
- 发现生产 Secret、真实支付、未脱敏商户数据；
- 模块数据主权冲突、资金/库存不变量存在多种解释而未决；
- CI 通过跳过测试、降低 HIGH/CRITICAL 阈值或删除失败用例获得；
- 候选基线不是 `962c4ed5…` 的后代；
- P0 风险无 Owner/回退或存在未修复 P0/P1 缺陷。

## 5. T2 Alpha 退出建议框架

| 建议 | 门槛 |
|---|---|
| `GO T3` | 现金+主支付、订单/退款、库存/成本、离线同步实验室闭环；P0/P1 清零；外部所需证据达级 |
| `CONDITIONAL GO T3-PREP` | 内部 Alpha 通过，少量外部项保持明确阻断且不影响加固准备 |
| `NO-GO` | 资金/库存/租户/离线不变量失败、不可恢复迁移、证据污染或关键外部路径不可执行 |

T2 Alpha 通过仍不等于商业 V1；商业结论必须经过 T3 加固、T4 真实门店和 T5 运营门禁。
