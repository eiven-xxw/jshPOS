# T2 核心 Alpha 项目章程

> 文档编号：JSH-POS-T2P-001  
> 版本：1.0  
> 基线：`962c4ed5e631bccd5c6fff737ed8e97fb665fd03`  
> 状态：启动评审候选

## 1. 项目使命

在不夸大 T1 `STATIC/FAKE` 结论的前提下，为“面向 1—30 家便利零售门店的稳定收银与轻连锁经营系统”建立可审计的 T2 核心 Alpha 开发边界、需求顺序和质量门禁。

T2 的目标不是堆页面，而是在实验室形成可恢复、可对账、可追溯的端到端核心闭环。商业收费仍需 T3 加固、T4 门店试点和 T5 商业验收。

## 2. T2-Prep 目标

1. 将商业 V1 高层能力拆成唯一 Requirement ID 和原子验收；
2. 便利店作为主样板，冻结零食折扣店和社区超市的行业模板边界；
3. 建立租户/门店、商品/价格、POS/订单、支付、库存、促销的逐模块准入；
4. 复核详细设计 31—40 的状态机、不变量、权限、审计、幂等、迁移和回退；
5. 给出 14 周 Alpha 迭代、团队 RACI、环境、测试、CI、灰度与回退计划；
6. 为硬件、支付、设计伙伴、鲸熵汇和许可证建立不污染内部研发结论的并行解阻轨道；
7. 形成可供项目发起人作 `GO/CONDITIONAL GO/NO-GO` 的启动评审包。

## 3. 非目标

- 不开发或修改正式租户、商品、价格、POS、订单、支付、退款、库存、促销等业务代码；
- 不创建正式 Flyway/SQLite 迁移、Controller、业务页面或 Provider；
- 不创建或推送任何 T2 tag；
- 不接入真实支付、硬件 SDK、生产网络或未脱敏商户数据；
- 不宣称 T1 已完成实机、沙箱、物理断电、试点或商业验收；
- 不把商业 V1 后置能力混入 Alpha。

## 8. 假设与约束

- `ASSUMPTION`：T2 正式团队可按 13—18 人研发质量配置；资源不足时必须缩范围；
- `ASSUMPTION`：T2 Alpha 日历窗口为 14 周，外部阻断可能延长支付/硬件关键路径；
- `BLOCKED`：主认证机、关键外设、支付沙箱和设计伙伴未落实；
- `DEFERRED`：鲸熵汇资料待收银主体完成后提供；许可证事项不阻断 Prep/内部编码，但阻断商业发布；
- GitHub 不升级套餐，继续使用仓库自有补偿控制。

## 9. T2-Prep 退出条件

只有同时满足以下条件，才可提交 T2 编码启动建议：

1. 本目录、ADR、RTM 和 CI 机器校验全部通过；
2. 所有正式业务需求仍处于非实现状态；
3. 第一开发波次范围、Owner、依赖、验收和回退明确；
4. 外部阻断保持真实状态并有截止点；
5. 候选 tag 名称、目标规则、注释内容和回退策略已准备但未创建；
6. 项目发起人明确确认启动评审报告。
