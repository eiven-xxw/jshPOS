# T2 范围、非目标与变更准入

## 1. T2 定位

T2 是 10—14 周的核心 Alpha 阶段。目标是在实验室环境形成便利店主样板的核心闭环，并为后续 T3 商用加固提供稳定领域基线。T2 不是商业发布，也不承诺真实门店、所有支付机构或全部硬件可用。

## 2. T2 Alpha 候选范围

| 域 | T2 Alpha 必须形成的内部闭环 | 外部依赖 |
|---|---|---|
| SaaS 基座 | 租户、组织、门店、员工权限、配置、审计、终端登记 | 实机激活验收仍 `BLOCKED` |
| 商品/价格 | SKU、条码、单位、导入、状态、基础价/门店价、发布数据包 | 可用合成商品；真实迁移样本另行授权 |
| POS/订单 | 开班、扫码购物篮、订单快照、现金、挂单、原单退货、交班、小票契约 | 打印实机 `BLOCKED` |
| 离线同步 | 正式 SQLite 设计、同事务 Outbox、Inbox 幂等、数据包原子切换 | 物理断电实机仍 `BLOCKED` |
| 支付/退款 | 主支付适配器边界、UNKNOWN、查询/回调、退款、对账 | 真实 Provider 只在沙箱解阻后准入 |
| 库存/采购/成本 | 不可变账本、销售出库、采购收货、盘点、移动加权平均 | 真实门店盘点/成本核对后置到试点 |
| 基础促销 | 手工改价、整单折扣、抹零、金额守恒和退款还原 | 不做复杂券、预算和组合营销 |
| 会员/报表 | 会员档案/识别、可选等级积分、销售/收银/库存/对账基础报表 | 真实个人信息禁止进入 Alpha |
| 质量运维 | 监控、审计、备份恢复、灰度、诊断、迁移和 Alpha 验收 | 等保测评与商业 SLA 后置 |

## 3. 商业 V1 范围但不必全部在 T2 达到商业级

以下能力属于商业 V1，T2 只建立其 Alpha 基础，商业等级分别在 T3—T5 完成：标准开户/套餐、门店克隆、厂商设备适配、标准实施工具、工单、鲸熵汇最小闭环、商业订阅、客户健康度和服务成本归集。

## 4. 明确不进入 T2 Alpha

- Windows 正式 POS、私有化交付和多套 POS 内核；
- 完整 WMS、生产加工、联营/代销、复杂业财一体；
- 储值、复杂优惠券、CDP、自动化营销和全域私域；
- 自助收银、AI 收银、智能补货、自然语言问数；
- 美团、抖音、京东、淘宝闪购等多渠道同时上线；
- 多支付机构动态路由、清分分账和真实资金生产交易；
- 未批准的定制字段、客户专用状态或核心特殊分支；
- 大型集团复杂组织、100 家以上规模承诺和全国服务网络。

## 5. T2-Prep 允许和禁止

### 允许

- 治理 Markdown/CSV/Schema、ADR、静态检查、CI 和合成验证计划；
- 为未来 Flyway、OpenAPI、事件和 SQLite 迁移定义命名、顺序与门禁；
- 为业务模块建立 `DRAFT` 需求、依赖和验收，不实现行为。

### 禁止

- 新增任何正式业务 Java/Dart/Kotlin/Vue 代码；
- 新增业务数据库迁移或真实业务表；
- 新增网络 SDK、支付凭据、设备证书和生产配置；
- 把 T1 PoC 代码移动到生产模块；
- 把 `DRAFT/BLOCKED/DEFERRED` 需求改成已实现状态。

## 6. 需求准入检查表

每个 T2 需求转为 `READY` 前必须满足：

1. 唯一 ID、业务价值、来源章节、Owner、优先级和非目标；
2. 可执行 Given/When/Then 或量化验收；
3. 数据主权、聚合边界和跨模块依赖；
4. 状态机、不变量、权限、审计、幂等和失败补偿；
5. API/事件/Schema 版本与兼容策略；
6. Flyway/SQLite 迁移、容量、灰度、回退或前向修复；
7. 成功、失败、越权、并发、重复、乱序、崩溃和恢复测试；
8. 监控、告警、Runbook、制品和 RTM 证据位置；
9. 外部证据等级与阻断是否匹配；
10. ARCH、PO、QA；涉及资金/库存/安全时增加独立领域负责人签署。

## 7. 范围变更规则

任何新增 V1 需求必须记录目标付费客户、合同价值、复用率、交付工时、质量风险和替代方案，并形成 CR。下列变更必须由项目发起人批准：

- 修改商业 V1 必选/后置清单；
- 改变订单、支付、库存或促销不变量；
- 增加新业态、新支付、新硬件主线或新客户端；
- 绕过真实沙箱/实机/试点证据；
- 延后 P0 安全、恢复、对账或迁移门禁。
