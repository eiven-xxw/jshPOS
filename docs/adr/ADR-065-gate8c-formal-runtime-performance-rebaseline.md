# ADR-065：Gate 8C 正式运行栈性能重基线与退化门禁

- 状态：Accepted
- 日期：2026-08-24
- 关联：T2-PERF-002、G8C-PERF-P1-001..002、CR-T2G8C-011

## 背景

Gate 6H 的七维性能证据早于 Gate 7 交易运营和 Gate 8 SaaS 运营能力；Gate 8B 的 55 次正式 HTTP 顺序观察只证明装配正确，不能证明当前代码面的并发、持续运行、尾延迟、资源上限、积压和退化行为。项目发起人已接受前置 T2-MTN-001，并授权仅关闭这两项性能证据 P1。

## 决策

1. 性能证据分为三个互补平面：正式 MySQL/Redis/JAR/HTTP 运行栈、Gate 7/8 Owner 容量与故障回归、Flutter POS 本地 SQLite 交易与同步。任何单一平面不得替代另外两个。
2. 每个工作负载在执行前冻结数据集、预热、并发、持续时间、采样、超时、错误率、背压和资源阈值；门禁同时校验业务正确性、金额数量守恒、租户隔离和性能，不允许以更快但错误的结果通过。
3. HTTP 负载记录 P50/P95/P99、吞吐和错误率；运行栈记录应用 CPU、RSS/堆、GC、MySQL/Redis 连接与内存、磁盘和积压。缺少原始样本或执行器指纹即为失败。
4. 冷启动、并发、持续运行、连接/队列压力和故障退化使用具名固定向量；过载必须有界拒绝或背压，恢复后必须收敛，不允许崩溃、静默丢失或资源无界增长。
5. GitHub `ubuntu-latest` 是正式可比较执行器类别；Windows 和本地执行器只验证脚本、契约与功能可重复性，不与 Ubuntu 墙钟值横向排名。每次证据保存实际 CPU、内存、磁盘、OS、JDK、MySQL、Redis 和 commit 指纹。
6. 阈值是内部回归护栏，不是生产 SLO/SLA。阈值只能经独立 CR、影响分析和完整重基线调整；失败后不得在同一变更中静默放宽或自动重跑。

## 不变量与非目标

- 不新增业务能力、依赖、表或迁移，不修改资金、库存、租户、订阅、订单或其他 Owner 事实。
- 不以直接数据库业务写入、测试后门或模拟成功绕过正式 API；基线数据只使用虚构租户、虚构终端和合成事实。
- 不进行 Provider 网络、真实资金、真实设备/外设、伙伴现场、完整 Alpha 或生产部署。
- 不把内部执行器结果外推为真实设备性能、生产容量、扩容模型、商业 SLA 或验收承诺。

## 失败处理与验证

性能失败必须保留原始样本、执行器指纹和固定 seed。只有稳定复现且属于现有已接受能力的 P0/P1 才允许最小运行时整改；整改必须先加回归并重新执行完整门禁。通过条件为两项既定 P1 关闭、固定阈值全部通过、开放性能 P0/P1 为零、全量 CI 全绿。证据上限为 `INTERNAL_FULL_STACK_PERFORMANCE_CANDIDATE`。
