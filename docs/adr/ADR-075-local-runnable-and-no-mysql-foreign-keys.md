# ADR-075：本地可运行基线与 MySQL 业务表无物理外键

- 状态：Accepted
- 日期：2026-09-05
- 需求：`T2-LOC-001`
- 变更：`CR-T2LOC-001`

## 背景

商业 V1 已具备内部合成业务闭环，但仓库缺少面向开发者的一键本地启动入口。与此同时，
V1—V89 历史迁移在 200 张业务表上累计形成 308 个现存 MySQL 外键。物理外键会增加大表
迁移、数据修复、按租户归档和 Owner 独立演进的耦合，并容易把跨 Owner 一致性错误隐藏成
数据库执行顺序问题。

历史 Flyway 迁移已经发布，禁止修改。POS SQLite 是单设备、单事务域的离线数据库，其本地
外键承担崩溃恢复与原子交易保护，和服务端 MySQL 的独立演进问题不同。

## 决策

1. 新增唯一前向迁移 `V202609050090__remove_business_foreign_keys.sql`，删除服务端 MySQL
   商业业务表的 308 个物理外键；V1—V89 不改写。
2. 保留全部主键、唯一约束、`CHECK`、`NOT NULL`、不可变触发器和既有索引；禁止使用
   `ON DELETE CASCADE` 或物理删除代替领域生命周期。
3. V90 之后的 MySQL 迁移禁止新增 `FOREIGN KEY`/`REFERENCES`。跨表引用必须在同一
   Owner 应用服务或具名 Owner 端口内，使用可信 `tenant_id`、状态、不变量和幂等规则校验。
4. 引用列必须具备与查询模式匹配的普通索引；跨 Owner 引用保存稳定事实 ID、版本/摘要或
   冻结快照，并由异常中心或一致性审计发现孤儿、摘要漂移和晚到事实。
5. 事实表继续只追加；父对象停用、注销或归档不得级联删除订单、支付、退款、库存、成本、
   审计等历史事实。
6. POS SQLite 现有领域内外键暂时保留；改变 SQLite 约束会影响本地事务和崩溃恢复语义，
   必须另行 CR，不得随本决策批量删除。
7. 本地环境使用 MySQL 8.4、Redis 7.4、`local` Spring profile 和仓库外生成的本机 Secret。
   初始化顺序固定为 RuoYi 基础表、Flyway V1—V90、最终外键数校验。

## 完整性责任替代

- 写入前：应用服务验证引用存在、同租户、状态可用和版本符合；客户端 `tenant_id` 不参与授权。
- 写入中：本 Owner 内使用事务、唯一键、条件更新、幂等结果与 Outbox 保持原子性。
- 写入后：周期性一致性审计只报告差异并创建受审计修复任务，不自动覆盖权威事实。
- 删除与更正：使用停用、状态迁移、冲正或新事实；禁止依赖数据库级联。
- 查询性能：每个引用查询都要有索引与 MySQL 执行计划证据，不能以取消外键为由取消索引。

## 验证

- 静态门禁精确核对 V1—V89 的 308 个现存外键均由 V90 删除；
- V90 以后任何新增 MySQL 外键语法使治理门禁失败；
- MySQL 8.4 空库迁移、V89 升级、重复执行和 Flyway validate 后，
  `information_schema.referential_constraints` 必须为 0；
- 本地启动后必须同时校验 Flyway 当前版本为 V90、外键为 0、服务端健康和 Web 可访问；
- 既有 Owner 单元测试、租户/权限、幂等、状态机、数据守恒和全量 CI 不得退化。

## 证据边界

本决策只建立本地开发运行和服务端 MySQL 约束策略，不改变资金、库存、同步或租户事实，
不解除支付、硬件、外设和伙伴阻断，也不形成 FULL_ALPHA、PRODUCTION、COMMERCIAL 或 SLA 证据。
