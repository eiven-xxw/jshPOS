# ADR-022：Gate 3A Provider 无关支付、退款与对账核心

状态：Accepted
日期：2026-08-16
需求：`T2-PAY-001`、`T2-PAY-003`、`T2-REF-001`、`T2-REC-001`

## 背景

S3 已建立正式 POS 同步，但电子支付沙箱仍未解阻。Gate 3A 需要先建立与渠道无关、可审计、可幂等验证的资金状态核心，同时确保 Fake 不被误认为外部渠道证据。

## 决策

1. 新建模块化单体边界 `jshpos-payment`，唯一拥有支付意图、支付尝试、Provider 观察、退款、退款占额、对账双源、差异案例、支付审计和支付 Outbox；不得把规则写入 Controller、RuoYi 系统模块或通用工具类。
2. 订单模块以只读 `PaymentOrderSnapshotPort` 暴露原订单、成交金额、币种、门店和行数量/成交金额快照；支付模块不得用 Mapper 跨模块更新订单表。
3. Provider 只以内部端口 `ProviderObservationPort` 和版本化 Schema 存在。Gate 3A 不提供网络适配器、SDK、回调 Controller、凭据、账单下载器或真实 Provider 实现。
4. 支付意图与 attempt 分离。`UNKNOWN` 阻止新 attempt；只能使用原 attempt 标识由可信 `QUERY/CALLBACK/STATEMENT` 观察收敛。已确认成功不得被失败或到达顺序回退；late success 可以从先前失败观察中恢复资金事实，但必须审计。
5. 观察值按稳定业务优先级而非到达顺序合并。观察 ID 相同且哈希不同为完整性冲突；金额、币种、商户/门店/终端或 Provider 引用冲突进入隔离，不改变资金状态。
6. 原单退款只允许对 `SUCCEEDED/PARTIALLY_REFUNDED` 电子支付创建。`PROCESSING/UNKNOWN/SUCCEEDED` 退款共同占用金额和行数量额度，支付聚合锁与数据库唯一/检查约束阻止并发超额。
7. 内部资金事实与 Provider 账单记录分别不可变；对账只生成差异案例，不自动改写支付或退款。差异关闭需要解决记录、审批人与审计证据。
8. 所有金额使用最小货币单位整数并保存币种；数量使用 `DECIMAL(19,6)`/`BigDecimal`，禁止浮点数。所有 ID、幂等键、状态历史和 Outbox 具备租户复合唯一约束。
9. MySQL 只追加 V9/V10，应用采用前向修复；回退到旧应用时新表保持未使用，禁止回滚删除资金事实。
10. Fake 只位于测试范围，通过固定向量调用内部端口；`T2-PAY-002` 保持 `BLOCKED`，外部证据始终为零。

## 事务边界

- 创建意图/attempt：校验原单快照、幂等记录、聚合/状态历史、审计和 Outbox 同一事务；不包含外部调用。
- 合并观察：先锁定支付聚合，幂等保存不可变观察，再按确定性规则迁移状态、写历史/审计/Outbox；冲突保存隔离证据但不改资金事实。
- 创建退款：锁定支付聚合，汇总所有占额退款，校验原单金额和行数量上限，再原子写退款/行/审计/Outbox。
- 对账：账单来源行先不可变入库；匹配在独立事务形成差异案例，不修改支付或退款事实。

## 后果与限制

- Gate 3A 可证明状态机、幂等、金额/数量上限、租户隔离和合成对账，但不能证明任何渠道可用性、签名兼容、回调公网或真实账单。
- 首家 Provider 必须在独立 Gate 3B 解阻后实现，并复用本 ADR 的端口和认证套件。
