# ADR-061：Gate 8B 正式运行时 API 汇总验收与平台职责分离

- 状态：Accepted
- 日期：2026-08-24
- 关联：T2-E2E-005、T2-SAA-001、T2-SUB-001、T2-SVC-001、CR-T2G8B-005、CR-T2G8B-006

## 背景

Gate 8B-Prep 已证明三个正式 Controller 的合成契约可以串联，但其应用服务为测试替身，不能证明正式 MySQL、Redis、认证会话、权限菜单和持久化装配。项目发起人授权 S25 仅修复正式 API 旅程暴露的 P0/P1 缺陷并形成内部候选证据。

正式装配审计发现：RuoYi 只允许 `user_id=1` 成为内置超级管理员，而 SaaS 开户与权益发布要求提交人与审批人分离。原实现把平台管理员等同内置超级管理员，导致无法通过正式 API 建立第二名合规审批人，属于 P0 授权死锁。

## 决策

1. `T2-E2E-005` 使用正式服务端、MySQL 8.4、Redis 7.4 和公开 HTTP API 串联 SAA→SUB→SVC；旅程脚本不连接数据库、Redis 或 Mapper，不调用测试后门。
2. 在默认平台租户 `000000` 中引入具名角色键 `platform_admin`，与内置超级管理员共同满足平台管理员身份。该角色只提供经菜单授权的操作，仍受 Controller 权限和应用层职责分离约束。
3. 非默认租户中的同名角色一律失败关闭；不能获得平台开户、跨租户生命周期或权益审批能力。
4. 只允许修复正式旅程发现的 P0/P1 装配、授权、幂等、历史保留和可观测性缺陷；不得新增业务 Owner、状态机或表。
5. 运行证据最高为 `INTERNAL_COMMERCIAL_OPERATIONS_CANDIDATE`，不得替代外部 P0、完整 Alpha、生产或商业验收。

## 后果与回退

- 平台可以通过正式 RuoYi 用户/角色 API 建立第二名独立审批人，不再复制超级管理员账号。
- 商户租户即使创建同名角色也不能提升为平台管理员。
- 若发现角色键冲突，回退方式是撤销该角色授权并恢复仅内置超管；不需要数据库迁移。业务历史、租户和订单等事实不受影响。
- 必须以单元测试、租户攻击测试和正式运行时 API 旅程共同证明边界。

## 运行时验证收口

正式旅程进一步确认：RuoYi 空环境必须同时装配基础与工作流 Schema；Owner 两段权限需要与框架三段权限共同纳入超管契约；审计序列化必须继承应用 Java Time 配置；自动配置清单中的模块入口必须使用 `@AutoConfiguration` 并显式扫描 Owner 组件。上述均属于本 ADR 允许的 P0/P1 装配与授权修复，没有新增业务状态机、表或外部能力。
