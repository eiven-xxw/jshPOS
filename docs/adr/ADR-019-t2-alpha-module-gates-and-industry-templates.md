# ADR-019：T2 Alpha 模块门禁与行业模板策略

- 状态：Proposed
- 日期：2026-08-16
- 决策人：待项目发起人确认 T2 正式开发启动
- 影响需求：`T2-*`

## 上下文

商业 V1 同时面向便利店、零食折扣店和社区超市，但三者共享商品、交易、资金和库存内核。一次铺开订单、支付、库存、促销会放大状态机、迁移和跨模块一致性风险；为每个业态复制代码又会形成不可维护的三套事实模型。

T1 只证明内部 `STATIC/FAKE` 风险模型可重复，真实硬件、支付沙箱和设计伙伴仍未解阻。因此 T2 必须把内部正式实现准入与外部实证准入分离。

## 建议决策

1. 商业 V1 使用一套模块化单体服务端、一套 Flutter Android POS 和一套核心领域模型；便利店为主样板。
2. 零食折扣店、社区超市差异通过版本化配置模板、能力开关、商品属性和已批准扩展点表达，禁止复制订单、支付、库存或促销状态机。
3. 正式编码按六道门分批准入：平台与安全基座；商品/条码/价格；POS/班次/订单/现金/离线；主支付/退款；库存/采购/成本；基础促销/会员/报表及 Alpha 集成。
4. 每道门必须独立满足 RTM、数据主权、状态机/不变量、权限审计、API/事件、Flyway、测试、可观测性和回退条件；下游不得绕过上游未决契约。
5. 支付和设备模块即使内部设计完成，也必须等待对应 `SANDBOX` 或 `REAL_DEVICE` 解阻才能进入外部集成与验收；现金路径不得被用来宣称电子支付完成。
6. T2-Prep 只产生准入候选，不自动把任何正式业务需求转为 `READY` 或启动编码。

## 后果

- 核心事实模型稳定，三类业态可以共享修复、测试和发布机制。
- 社区超市称重、短保/批次等能力可能因实机和范围门禁后置，不能拖慢便利店主闭环。
- 逐模块准入增加前置评审工作，但能把资金、库存和离线风险限制在可审查范围。

## 验证方式

- T2 RTM 中每个正式需求有唯一 ID、来源、验收、状态和依赖；
- 模块依赖图不存在订单/支付/库存/促销同时无门禁启动的路径；
- 三个行业模板不包含核心状态迁移分支或独立业务表；
- T2-Prep CI 阻断生产业务代码、迁移和外部网络凭据；
- 项目发起人确认 T2 启动评审后，本 ADR 才可改为 `Accepted`。
