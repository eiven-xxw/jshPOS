# ADR-042：Gate 7A 商业 V1 内部业务差距审计与串行准入

- 状态：Accepted
- 日期：2026-08-21
- 决策范围：T2 Gate 7A / Sprint S19
- 基线：`d66c252587561428def95058d67bc830e391a9ab`

## 背景

Gate 0—6H 已形成 64 项内部 `ACCEPTED` 能力和内部发布候选，但外部支付、硬件打印、伙伴与商业许可证仍未解阻。项目发起人决定先补齐商业 V1 内部业务功能，同时要求避免重复实现既有 Owner，并把外部对接继续后置。

现有全景规划包含商业 V1、后续版本和条件业态能力。若直接按功能名称编码，容易重建已有模块、把后续能力混入 V1，或用内部证据误解外部阻断。因此必须先做仓库事实审计和原子 RTM，再按依赖逐 Gate 准入。

## 决策

1. Gate 7A 只做静态治理、仓库证据审计、契约和验收准备，不新增正式业务运行时；
2. 64 项既有 ACCEPTED 能力按 Owner 复用，不为相同能力创建新模块、状态机、表或 Requirement；
3. 将确认差距拆为 18 个原子 Requirement，全部以 DRAFT 登记；
4. 后续严格按 Gate 7B POS 运营、Gate 7C 商品门店作业、Gate 7D 经营管理、Gate 7E 内部汇总候选串行推进；
5. `T2-EXG-001/MEM-003/SAA-001/SUB-001/SVC-001` 在与原范围冲突或扩张时必须先经独立 CR；
6. Gate 7B 第一批仅建议 `T2-POS-010 → T2-POS-011 → T2-ORD-004`，不能因 ADR Accepted 自动进入 READY；
7. 外部证据状态和零执行边界保持不变，内部候选的最高证据不能跨级。

## Owner 与复用边界

- Order/POS 继续拥有购物篮、订单、班次和本地交易事实；现金扩展进入既有只追加现金边界；
- Device 只拥有设备执行观察，不拥有订单、小票业务内容或授权；
- Return/Payment 继续拥有原单退货退款和资金状态，取消或换货不能复制状态机；
- Catalog/Pricing/Inventory/Procurement/Member/Reporting/Foundation 只在各自主权内扩展；
- 异常中心和日结只读或消费版本化权威事实，不得反向覆盖 Owner；
- 新的 SaaS/Subscription/Service Owner 是否建立，必须由 CR 决定，不能直接把商业规则写入 RuoYi 系统模块。

## 后果

正面后果：V1 剩余工作可逐项验收，减少平行模型和重复表，外部阻断不会拖住内部开发，也不会被内部证据错误解除。

成本与限制：需要维护原子 RTM、跨 Owner 契约与更多串行门禁；社区超市批次效期、换货、会员价和商业 SaaS 运营可能因 CR 结论被延后或移出 V1。

## 被拒绝方案

- 一次性实现 A—D 全部候选：无法证明准入顺序，也放大资金、库存和迁移风险；
- 把所有差距塞进既有 Requirement：会掩盖验收边界和重复实现；
- 把外部支付/设备 Fake 当成功：违反证据等级和失败关闭原则；
- 直接在前端或 RuoYi 系统模块补业务逻辑：破坏 Owner 主权与模块化单体边界。

## 验证

由 Gate 7A 专用检查器校验基线祖先、64 项 ACCEPTED、18 项 DRAFT、外部状态、零执行、允许变更路径和交付完整性；Ubuntu、Windows 与独立范围边界三类生产者通过后生成 SHA-256 证据索引。
