# ADR-017：T1 风险 PoC 范围与外部集成深度

- 状态：Accepted
- 日期：2026-08-16
- 决策人：项目发起人
- 影响需求：`T1-*`

## 上下文

T1 只有四周，目标是尽早证伪 Android 设备、支付不确定性、离线一致性、租户隔离和升级回滚等高风险技术假设，而不是提前实现商业业务。候选样板包含便利店、零食折扣店、社区超市；外部设备型号、支付沙箱、设计伙伴和鲸熵汇真实资料尚未齐备。

若同时对三种业态、多家硬件和十家支付候选做完整实接，范围必然失控；若全部使用 Fake，又不能证明实机和真实沙箱可用。因此必须分离“候选档案覆盖”“适配契约覆盖”“单一真实链路验证”和“商业认证”。

## 决策

1. 便利店作为首发主样板；零食折扣店、社区超市仅提供差异样本和边界用例，不在 T1 建立三套业务核心。
2. T1 划分七类 PoC：设备适配、支付不确定性、本地崩溃恢复、同步幂等与乱序、租户隔离、商品/价格数据包原子切换、应用与数据库升级回滚。
3. 设备采用 `pos_device_adapter` 稳定契约和 Kotlin 厂商插件。T1 只选择一台主认证 Android 机及规定外设做实机验证；其他主流品牌只建能力档案和扩展槽位，不声称兼容或认证。
4. 支付建立十家支付/聚合服务候选档案：易宝、汇付、拉卡拉、富友、收钱吧、银联商务、通联支付、嘉联支付、杉德支付、随行付；从中按资料、状态语义、沙箱和支持能力评选五家运行统一 Fake 契约。T1 只允许一家已授权沙箱完成真实端到端验证。真实资金、生产密钥和生产终端禁止进入 T1。
5. 首发能力必须覆盖微信支付、支付宝和银联/云闪付，但允许由选定的主/备聚合服务商提供，不要求商业 V1 同时维护三套直营通道。银行卡 ECR/支付终端、数字人民币和国际支付分别按真实门店与区域需求后续准入。
6. Fake 结果只证明内部契约与故障编排，不得作为实机、真实支付沙箱、第三方验收或商业可用证据。
7. 鲸熵汇连接器保持 `DEFERRED`，待收银系统主体完成后由项目发起人提供真实接口目录、鉴权、限流、沙箱、回调、验收标准和负责人。
8. Aviator、simple-http、MySQL Connector/J 的替换或法务处理不阻断 T1-Prep 和风险 PoC，但必须在商业发布前闭环。
9. GitHub 不升级套餐，沿用 ADR-016 的仓库自有依赖差异和供应链补偿门禁。

## 后果

- T1 可在四周内集中验证最危险的技术假设，同时保留多厂商扩展能力。
- 在真实主机、SDK 或支付沙箱缺失时，相应实证项为 `BLOCKED`；这不妨碍完成 Fake 方案，却会阻断对应 PoC 的最终 Go。
- “进入十家候选池”“五家 Fake 通过”“支持某支付机构/设备”是不同结论；只有相应真实接入与认证完成后才能对外宣称支持。
- 便利店之外的称重、散称、复杂促销、批次效期等业务不因对照样本而进入 T1 正式实现。

## 验证方式

- `docs/governance/rtm.csv` 中每项 T1 需求均有唯一 ID、状态、验收、负责人和证据位置。
- T1-Prep 评审核对七类 PoC、外部资料清单、量化测试矩阵、Go/No-Go 和回退方案。
- 实施时分别生成 `FAKE`、`SANDBOX`、`REAL_DEVICE` 证据，CI 禁止混用证据等级。
- 任何 PoC 编码必须在项目发起人确认启动后；需求须先通过准入，并在 RTM 中从 `READY` 合法转为 `IN_PROGRESS` 后方可执行。
