## 2. 已验证业务与架构行为

- Payment Owner 独占版本化 TenderPlan、2—8 个冻结份额、状态历史、审计和 Outbox；
  份额按序收取、同币种 CNY，金额逐分等于订单应收，现金最多一份且必须位于最后。
- 单现金交易继续走既有现金结算能力；本需求的 TenderPlan 不伪装成“多现金组合”。
  只要包含电子份额，正式运行时就因 `T2-PAY-002` 未解阻而失败关闭，不能形成完整
  组合支付成功。测试范围的合成电子成功观察仅验证状态机，不提升外部证据等级。
- 现金份额通过 `TenderCashCollectionPort` 进入 Order/Shift Owner；部分现金事实、班次
  现金流水、计划份额、审计和 Outbox 在同库 Spring 事务中原子提交。Payment Mapper
  不跨 Owner 写 `ord_*` 或 `shf_*`。
- `SUCCEEDED` 不回退；`PROCESSING/UNKNOWN` 占额并阻断后续份额、取消和替代命令。
  超时、ACK 丢失、进程重启或服务端结果未知只能复用原 plan/allocation/command 查询
  或观察，禁止重建扣款命令。
- 退款分配保持按原成功份额和原介质恢复的守恒规则；现金退现金，电子份额继续受
  外部阻断。本批未宣称电子组合退款已经完成网络闭环。
- MySQL V57/V58 和 SQLite V13 采用独立前向迁移，历史、观察、现金份额、审计和事件
  只追加；Flutter 页面只调用 Tender 应用服务，不直接访问 SQLite、MethodChannel、
  Mapper 或 Provider。
- 可信租户、门店、终端、员工、班次与业务日贯穿 API、Mapper、SQLite、事件和缓存/
  任务契约；同幂等键异内容、跨租户替换和内容摘要篡改均失败关闭。
- Java 与 Dart 共同读取 `tender-golden-vectors-v1.json`；14 个固定故障向量覆盖金额、
  顺序、电子阻断、找零、重复、UNKNOWN、崩溃回滚、ACK 丢失、跨租户和按原介质退款。
