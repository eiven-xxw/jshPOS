# SQL 查询计划、索引与 N+1 审计

## 当前事实

- 49 个正式 Owner Mapper XML、365 个 `<select>`；
- 27 个 Mapper XML 含 JOIN、GROUP BY 或子查询；生产 `SELECT *` 违规为 0；
- 当前不存在以 MySQL `EXPLAIN/EXPLAIN ANALYZE` 为断言的 Owner 回归文件；
- 因而不能仅凭 SQL 文本宣称索引、分页或 N+1 已得到生产形态验证。

首批 12 个风险查询已固化在 `sql-risk-candidates-v1.csv`，覆盖批次 FEFO、临期、促销规则、
销售/库存成本报表、支付对账、采购/调拨明细和积分批次。

## 拟议验证方法

1. 在 MySQL 8.4 使用固定 10k/100k/1m 合成基数与可信租户、门店参数；
2. 保存 SQL、绑定参数类型、表统计、索引清单和 `EXPLAIN ANALYZE` JSON；
3. 对事实表禁止未经批准的全表扫描，要求租户/门店/业务日首要范围可解释；
4. 列表页冻结稳定排序、页大小上限与 `count + page` 查询数预算；
5. 服务旅程记录 JDBC 查询数，发现 N+1 时先补失败回归再整改；
6. 若需要新索引或数据库对象，立即停止并提交独立 CR，只允许新的前向迁移；
7. 不以墙钟抖动单独判定 SQL 退化，不跨不同执行器比较绝对延迟。

准备阶段未执行 SQL 改写、索引创建或迁移。
