# 三业态跨 Owner 正式旅程冻结

## 统一拓扑

每条旅程必须同时使用正式 MySQL、Redis、商业 JAR、HTTP/OpenAPI、Vue dist、Flutter POS 与
文件 SQLite。Redis 只作为会话/缓存，不能成为业务唯一事实；业务初始化和执行只能通过正式 API、
应用端口、事件、Inbox/Outbox 或 POS Repository，禁止直接写业务表。

## 共同前置旅程

商户申请审批 → 套餐权益发布 → 技术租户开通 → 订阅激活 → 组织/门店/员工 → 实施检查 →
开业资料迁移 → 行业模板与开店检查 → 商品/价格/权益数据包 → 终端登记和可信员工登录。

## 共同业务旅程

开班 → 普通/秤码扫码 → 购物篮 → 促销/会员价/人工优惠 → 挂单取单 → 现金或部分现金成交 →
SQLite 原子事实与 Outbox → 正式 HTTP 同步 → 服务端订单 → 库存/成本/报表 → 部分/最终退货 →
换货 → 采购/盘点/调拨/补货 → 日结/异常处置 → 关班 → 合成备份恢复和升级前向修复 →
服务工单关闭 → 订阅受控降级/恢复。

## 业态差异

| Journey | 业态 | 必选差异 | 禁止的核心分叉 |
|---|---|---|---|
| R4-J01 | 便利店 | 普通条码、快速现金、会员默认关闭 | 不复制订单/促销/库存状态机 |
| R4-J02 | 零食折扣店 | 秤码/金额码、批量价促销参数 | 不建立专属计价算法 |
| R4-J03 | 社区超市 | 秤码、批次效期、FEFO、临期预警、可选会员 | 不引入批次成本或复杂 WMS |

业态差异只能来自版本化模板、规则和能力开关；核心资金、订单、库存、成本、同步状态机共用。

## 可信上下文与检查点

每一步必须保存并核对 tenant、组织/门店、终端、员工、班次、业务日、correlation ID、
idempotency key、source event ID、payload SHA-256 与各 Owner 检查点。客户端 tenant_id、金额、
数量、成本和状态不得成为服务端权威输入。
