# T2-CLS-001 设计准入与验收冻结

## 1. 准入结论

- Requirement：`T2-CLS-001`
- 当前状态：`IN_PROGRESS`
- Owner：`jshpos-operations`
- 证据边界：`INTERNAL_SOFTWARE_EXECUTION / SYNTHETIC_DATA`
- 前置：`T2-LOT-001 ACCEPTED`；`T2-EXC-001` 保持 `DRAFT`。

设计准入已冻结数据主权、状态机、冻结点、权限、审计、幂等、REST/事件、Flyway、
容量、兼容、重建、回退与验收向量。实现不得绕过本文进入跨 Owner SQL。

## 2. 数据主权与表策略

| 表 | 访问策略 | 说明 |
| --- | --- | --- |
| `ops_daily_close` | CONTROLLED_WRITE | 日结身份、当前编排状态和乐观锁；CLOSED 内容不可改 |
| `ops_daily_close_checkpoint` | APPEND_ONLY | Owner 来源版本、序号、状态和摘要 |
| `ops_daily_close_snapshot` | APPEND_ONLY | 逐币种冻结金额与统计快照 |
| `ops_daily_close_preflight` | APPEND_ONLY | 每轮预检项及阻断原因 |
| `ops_daily_close_difference` | APPEND_ONLY | 差异、晚到和更正关联；不得覆盖业务事实 |
| `ops_daily_close_approval` | APPEND_ONLY | 独立审批事实 |
| `ops_daily_close_signature` | APPEND_ONLY | 关闭签署与清单摘要 |
| `ops_daily_close_state_event` | APPEND_ONLY | 具名状态迁移历史 |
| `ops_daily_close_command_result` | APPEND_ONLY | 同租户/操作/幂等键的稳定结果 |
| `ops_daily_close_audit` | APPEND_ONLY | 允许、拒绝与恢复审计 |
| `ops_daily_close_outbox` | CONTROLLED_WRITE | 不可变载荷与受控投递状态 |

复杂汇总 SQL 必须置于各 Owner 的 XML Mapper，并显式绑定可信 tenant/store/date 或 UTC
时间窗。Operations 只调用窄端口；Controller 只处理协议、权限和 DTO。

## 3. 状态、冻结点与更正

状态覆盖 `DRAFT → PREFLIGHTING → READY/PREFLIGHT_FAILED → APPROVED → CLOSING → CLOSED`，
并显式支持 `FAILED/CORRECTION_REQUIRED/COMPENSATION_REQUIRED`。开始预检冻结来源检查点；
审批冻结审批人；签署前再次采集来源并比较摘要，任何变化均回到失败关闭路径。

`CLOSED` 快照、签名与状态事件只追加。晚到事实通过检测命令追加差异；更正创建新的
`close_version` 并引用原 `close_id`，旧签名不修改。创建人不得审批或签署；同键同内容
返回原结果，同键异内容返回 `OPS-IDEMPOTENCY-001`。

## 4. 业务不变量与预检

- `gross - discount + surcharge = receivable`，币种固定且所有金额为最小货币单位整数。
- 逐门店/业务日的订单、取消、退款、现金实收、现金退回和班次差异与 Owner 权威事实守恒。
- 所有必需班次已关闭；现金差异已确认；支付/退款 UNKNOWN 为零。
- Sync 待处理、重试、冲突和死信必须为零；Reporting SALES/INVENTORY_COST 投影检查点
  必须 CURRENT，未处理差异为零，并与权威订单金额逐字段一致。
- 权限、审计、Owner 版本、摘要或来源检查点缺失均阻断。
- 外部 Provider 对账始终显示 `BLOCKED/UNAVAILABLE`，不得记为通过；不存在电子资金事实时
  它作为外部证据提示而非内部现金日结的虚假绿色项。

## 5. API、权限与事件

API 不接收 tenant、金额、差异或目标状态。权限分为创建、预检、审批、签署、读取、
晚到检测与更正；门店数据范围强制检查。事件为：

- `operations.daily-close.preflighted.v1`
- `operations.daily-close.approved.v1`
- `operations.daily-close.closed.v1`
- `operations.daily-close.difference-detected.v1`
- `operations.daily-close.correction-required.v1`

事件包含 close ID、版本、门店、业务日、快照摘要、来源清单摘要、schemaVersion 和
correlationId，不含 PII、Secret 或客户端 tenant。

## 6. 容量、迁移、兼容与回退

- 单门店单业务日每轮最多 64 个检查点、128 个预检项和 256 个差异；单查询最多 100 条。
- 百万级合成事实仅验证线性汇总趋势，不形成生产 SLA。
- MySQL V71/V72 只前进；旧服务不识别 Operations 表但继续提供 Owner 事实，新服务在表或
  Owner 端口缺失时失败关闭。
- 投影可从权威事件重建；迁移失败使用新版本前向修复。已签署日结不可删除或回写。

## 7. 量化验收

固定故障向量不少于 40 个，覆盖正常关闭、未关班、现金差异、重复/异内容、并发审批、
跨夜/时区/夏令时、同步积压/死信、UNKNOWN、Owner 延迟、投影缺口、晚到、更正、重建、
跨租户/门店、摘要篡改、百万合成趋势和迁移前向修复。Server/Web/MySQL 与既有全量
CI 必须通过；不得降低测试、安全、覆盖率、SBOM、许可证或证据门禁。
