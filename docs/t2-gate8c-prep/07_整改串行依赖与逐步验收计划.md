# 整改串行依赖与逐步验收计划

## 串行顺序

`T2-SEC-002 → T2-MTN-001 → T2-PERF-002 → T2-RDY-001`

每一项均须独立完成：设计准入 → 回归先行 → 最小实现 → 本地验证 → 完整 CI → `VERIFIED` → 项目发起人确认。前项未被确认，后项保持 `DRAFT`。

## 第一批：T2-SEC-002

- 生产配置 Secret 化、可选集成默认关闭和启动失败关闭；
- Actuator 白名单与健康详情最小化；
- 附件大小前置校验、受限流式处理和并发资源测试；
- Secret、权限、租户、启动、资源耗尽和完整回归。

## 第二批：T2-MTN-001

- Service→SaaS 端口化；
- OpenAPI 唯一权威契约和历史草案标记；
- Flyway 回调审计器兼容但不放宽历史迁移保护；
- Foundation 锁定 SQL 迁入 XML；
- POS 超大文件按职责拆分且行为金标不变。

## 第三批：T2-PERF-002

在正式 MySQL/Redis/JAR/Web/Flutter/SQLite 栈上对最新已接受能力建立固定合成容量、并发、尾延迟、资源和退化阈值；失败不得靠自动重跑掩盖。

## 第四批：T2-RDY-001

收口内部许可证清单、自有包元数据、制品签名契约、部署配置、运维和 Go/No-Go；外部 P0、商业许可证、完整 Alpha 和生产发布仍独立等待授权。

任何新业务能力必须单独 CR 和 Requirement ID，不得混入四个质量需求。
