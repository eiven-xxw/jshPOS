# T1 范围、非目标与需求准入清单

> 文档编号：JSH-POS-T1P-002
> 版本：1.0
> 状态：启动评审候选
> 需求：`T1-SCP-001`

## 1. 范围控制原则

T1 只验证技术风险，不交付业务功能。每个进入编码的任务必须能回答：“该探针要证伪哪一个 T1 假设？失败后会影响哪个架构决策？”回答不清或只产生业务页面/CRUD 的任务不得准入。

## 2. 样板用例边界

| 样板 | T1 允许的合成数据/风险场景 | T1 不进入的业务 |
|---|---|---|
| 便利店（主） | 标准条码、普通/整箱单位、快速扫码、内置打印、现金抽屉、客显、弱网 | 正式销售/退货/交班、会员、优惠、支付入账 |
| 零食折扣店（对照） | 1万/10万 SKU 数据包、频繁价格版本、整箱/散件映射样本 | 复杂多级促销、加盟订货、供应商结算 |
| 社区超市（对照） | 称重读数、外置打印、多外设断连、多终端租户隔离 | 生鲜批次效期、计量合规结论、加工配方、库存业务 |

所有“销售、支付、退款”等词在 T1 探针中只代表合成状态或技术事件，不能复用为商业领域实现，也不能进入 T2 作为未经评审的正式代码。

## 3. 准入工作项

### 3.1 治理与契约

- T1 文档、RTM、ADR、风险台账、测试与证据模板；
- 设备能力契约、错误分类、超时和恢复语义；
- 支付命令/查询/回调的统一测试契约与 Provider Profile；
- 合成同步事件、Inbox/Outbox、数据包和升级兼容的最小协议；
- CI 门禁和测试夹具；
- Fake、Stub、故障代理、网络/进程/文件损坏注入工具。

### 3.2 最小技术探针

- 不含商业字段和正式业务规则的 SQLite 事务/恢复探针；
- 不含真实订单的合成事件幂等与乱序探针；
- 两个虚构租户的框架旁路隔离探针；
- 合成商品/价格数据包的签名、断点、损坏拒收和原子目录切换；
- 空壳 APK/插件与测试数据库的升级、迁移失败、回退兼容；
- 已授权设备和支付沙箱的最小端到端探针。

### 3.3 外部调查

- 主流 Android POS 厂商能力档案和一台主认证机选型；
- 至少两种打印、扫码、秤、钱箱、客显的接口/协议/许可/供货输入；
- 易宝、汇付、拉卡拉、富友、收钱吧五家候选支付档案；
- 一家真实沙箱的账号、终端、接口文档、回调白名单、联系人和验收规则；
- 5 家设计伙伴清单和至少 3 家后续试点意愿。

## 4. 非目标与禁止项

| 类别 | 非目标/禁止 | 处理方式 |
|---|---|---|
| 订单 | 正式下单、挂单、退货、交班、单据号规则 | 保留在 `V1-POS-001`，T2 再拆 |
| 支付 | 真实扣款、生产商户、清结算、正式渠道接入 | T1 只做 Fake 与一个测试沙箱 |
| 库存 | 库存余额、扣减、预占、盘点、成本核算 | 禁止进入 T1 |
| 促销 | 促销计算、优惠分摊、会员价、券 | 禁止进入 T1 |
| 会员 | 会员档案、积分、储值、营销 | 禁止进入 T1 |
| 连接器 | 鲸熵汇、美团、抖音等正式接入 | 鲸熵汇 `DEFERRED`；其他留后续 |
| 商用认证 | 等保测评、PCI/收单认证、计量认证、L2 长稳结论 | T1 只准备风险输入，不冒充认证 |
| 多厂商全覆盖 | 同时完成多品牌硬件/五家支付实接 | 一个主机、一个支付沙箱；其余只建扩展档案 |
| 生产运维 | 生产部署、真实门店切换、SLA 承诺 | 禁止进入 T1 |
| 许可证 | 静默忽略商业许可证问题 | 可延后但保留 `T1-LIC-001 DEFERRED` |

## 5. 单项需求准入清单

每个工作项必须全部满足，任何一项为“否”则不得编码：

- [ ] RTM 存在唯一 `T1-*` Requirement ID，且状态为 `READY`；
- [ ] 指向明确的上游章节、ADR 和风险假设；
- [ ] 写明范围、非目标、输入、输出和删除/废弃方式；
- [ ] 验收可自动执行或可复核，包含成功与故障路径；
- [ ] 明确证据等级：STATIC / FAKE / SANDBOX / REAL_DEVICE；
- [ ] 涉及设备时，型号、Android/固件、SDK 版本、授权、实机和负责人齐备；
- [ ] 涉及支付时，测试商户/终端、接口版本、回调网络、授权和技术联系人齐备；
- [ ] 涉及租户时，可信租户上下文、越权矩阵和审计断言明确；
- [ ] 涉及本地数据时，事务边界、不变量、崩溃点和恢复判定明确；
- [ ] 涉及升级时，旧/新版本矩阵、备份、失败点、兼容窗口和回退明确；
- [ ] 仅使用合成或授权脱敏数据；没有生产密钥或真实资金；
- [ ] 新依赖已固定版本并完成用途、许可证、安全和替代方案审查；
- [ ] 有实现者、独立复核者、时间盒和停止条件；
- [ ] CI/本地可生成不可篡改摘要和测试证据；
- [ ] 不实现正式业务，不扩大到 T2。

`READY` 不是已授权编码；它只表示需求本身具备设计准备度。当前阶段总门禁仍为 `NO-GO`。

## 7. 需求退出与状态迁移

- `READY -> IN_PROGRESS`：项目发起人确认 T1，工作项通过准入清单，负责人开始执行。
- `BLOCKED -> READY`：阻断输入完整、验证通过、RTM 和风险台账更新并经相应负责人确认。
- `IN_PROGRESS -> VERIFIED`：实现和全部测试通过，证据上传，独立复核完成。
- `VERIFIED -> ACCEPTED`：T1 退出评审签署；不能由实现者单独更新。
- 任意状态 `-> BLOCKED`：外部输入失效、范围不清、资金/租户/数据安全风险无法安全处理。
- 任意状态 `-> DEFERRED`：只可由项目发起人批准，并写变更记录；不得用于隐藏失败。

## 8. 变更控制

- 四周内新增风险域默认拒绝，除非替换同等或更大工作量并由项目发起人批准。
- 修改资金、租户、离线事实、设备契约或升级策略必须新建/更新 ADR，不得只改任务描述。
- 外部厂商临时要求不得直接写入核心层；先映射到稳定适配契约。
- 所有批准变更追加到 `change-log.md`，不改写历史行。
- T1 结束不会自动启动 T2；正式业务必须单独下达指令并重新做需求准入。
