## 1. 支付接入策略

商业目标不是把十家机构同时写进核心，而是建立“支付能力层—路由层—机构适配层”：首发覆盖微信支付、支付宝、银联/云闪付，从十家候选中选择一主一备服务商，后续按商户地区、费率、稳定性和服务能力扩展。T1 目标不是十家完整集成，而是：

1. 对十家建立可审计 Provider Profile、官方资料入口和能力差异；
2. 按状态完整性、沙箱和支持评分选出五家，用五个 Fake 运行同一套契约测试，证明核心不需要 provider 分支；
3. 只选择一家资料、授权和支持最完整的真实沙箱做端到端；
4. 商业 V1 从候选池确定一个主服务商和一个备服务商，至少主服务商完成正式接入；备服务商在具备真实沙箱和商务条件后进入灾备/切换验证；
5. 后续每新增合作方均复用相同准入、契约、沙箱和商业验收。

“公开文档存在”“Fake 通过”“沙箱通过”“生产获准”是四个不同阶段，不得合并表述。

## 2.1 首发支付能力，而非十家同时接入

| 能力层 | 首发优先级 | 建议实现方式 | 商业验收底线 |
|---|---|---|---|
| 微信支付 | P0 必须覆盖 | 优先由主/备聚合服务商提供；直营通道作为后续可插拔 Provider | B扫C/C扫B、查询、撤销/退款、回调、对账和 UNKNOWN 收敛 |
| 支付宝 | P0 必须覆盖 | 同上，不在核心写支付宝特殊状态 | 与微信相同的统一支付不变量 |
| 银联二维码/云闪付 | P0 必须覆盖 | 主/备服务商或[中国银联二维码开放能力](https://open.unionpay.com/tjweb/acproduct/list?apiSvcId=468) | 主扫/被扫、查询、撤销/退货、通知、对账 |
| 银行卡刷卡/非接 | 社区超市 P0、便利店 P1 | 通过合规收单终端/ECR 接口，不让 Flutter 直接处理卡号/PIN/EMV | 终端认证、原交易查询、撤销/退货、对账；POS 不持有卡敏感数据 |
| 数字人民币 | P1 预留 | 通过支持的银行/收单服务商 Provider | 以真实合作资料重新准入，不凭概念实现 |
| 门店储值/礼品卡 | P1，独立资金域 | 不是第三方聚合支付；单独状态机、余额账本与合规评审 | 不与支付机构交易状态混写 |
| 京东/美团/抖音等生态支付 | P2/连接器驱动 | 优先由聚合服务商或对应连接器承接 | 不在支付核心写渠道特殊分支 |
| 国际卡/海外钱包 | 海外版 P2 | 未来按目标国家评估 Stripe、Adyen 等；不进中国商业 V1 | 当地合规、币种税务、拒付和对账另立项目 |

因此，“系统应该支持”定义为统一契约和路由可扩展；“商业首发必须上线”定义为三大扫码能力 + 按业态决定的银行卡 ECR；“接入十家机构”不是首发目标。

| 层级 | 候选 | 处理建议 |

## 3. Provider Profile 强制字段

每家创建一个版本化档案，至少包含：

### 3.1 商务、合规与责任

- 法定主体、业务品牌、合作协议/保密协议状态；
- 服务类型、资金流和清结算责任；
- 支持的支付渠道、地区、行业、商户类型、费率/结算周期（只入受控商务库）；
- 商户进件、门店、终端、操作员模型；
- 风控限制、单笔/日限额、频控和禁限售行业；
- 数据处理、日志留存、隐私、安全事件和审计责任；
- 商务负责人、技术负责人、7×24 支持、升级和生产变更通知渠道。

### 3.2 环境与网络

- 沙箱/联调/生产环境的 base URL、DNS、TLS 版本、证书链；
- 是否需要固定出口 IP、VPN、mTLS、证书或硬件终端；
- 测试商户号、门店号、终端号、应用 ID 的申请与有效期；
- 回调公网 HTTPS、域名/IP 白名单、端口、证书和联调工具；
- 合作方时钟/时间戳容差、时区、报文编码、最大报文；
- 限流维度、阈值、`Retry-After`、维护窗口和沙箱稳定性说明。

### 3.3 接口与状态

- API 名称/版本：付款码支付、主扫预下单、交易查询、撤销、退款、退款查询、关单、对账下载；
- 请求 ID、商户订单号、合作方交易号、终端流水号的唯一和长度规则；
- 金额单位、币种、小数处理、零/负数/上限；
- 同步返回、异步回调、查询、对账的状态枚举和优先级；
- `PROCESSING/UNKNOWN` 定义、推荐查询节奏、最终超时和人工处置；
- 幂等范围、重复请求返回、同键不同参数、退款幂等；
- 回调重复、乱序、重放、验签、ACK 规范；
- 错误码、可重试性、风控/业务/系统/协议错误分类；
- 对账文件格式、生成时间、重取、校验、差异处理和历史期限。

### 3.4 加密与密钥

- 签名/加密算法、规范化字符串、字符集、证书格式；
- 测试密钥生成、交换、存储、轮换、吊销、过期和应急流程；
- 请求/响应/回调验签样例和官方测试向量；
- 敏感字段定义、掩码规则、禁止日志字段；
- SDK 版本、来源、SHA-256、许可证、native ABI、漏洞和替代 REST 方案。

## 6. T1 支付验收范围

真实沙箱至少执行：

- 正常支付成功、明确失败、处理中、客户端超时和未知；
- 同幂等键同参数重复、同键不同参数冲突；
- 查询收敛成功/失败/仍处理中；
- 回调先于同步响应、重复 10 次、乱序、延迟、错误签名、过期重放；
- 退款成功、明确失败、超时/UNKNOWN、重复退款、超额拒绝和退款查询；
- 对账正常、平台单边、合作方单边、金额/状态差异；
- 本地“后续动作失败”不改变已经成功的支付事实；
- 全流程无自动二次扣款命令。

付款用官方测试介质/虚拟金额；若沙箱无法生成某故障，代理注入结果单独标记 `FAKE`，不能混在 `SANDBOX PASS` 中。

## 7. 支付密钥与数据安全

- GitHub Environment Secret 使用 `T1_<PROVIDER>_SANDBOX_*` 引用名，值不可导出到普通日志；
- 默认不允许来自 fork 的 PR 访问沙箱 Secret；需要人工批准的受保护环境；
- 沙箱 Job 不与普通 PR 自动并发执行，避免额度/状态污染；
- 所有请求/响应记录只留字段白名单和摘要，付款码、Token、签名、证书、手机号全部清除；
- callback 原文只在临时加密隔离区用于定位，证据保留脱敏派生物；
- 项目结束立即吊销测试密钥、回调白名单和账号权限，并留吊销证据。
