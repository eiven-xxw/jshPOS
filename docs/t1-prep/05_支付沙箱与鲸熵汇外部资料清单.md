> 文档编号：JSH-POS-T1P-005
> 版本：1.0

> 需求：`T1-PAY-001`、`T1-PAY-002`、`T1-JSH-001`

## 1. 支付接入策略

商业目标是可扩展接入不少于五家主流第三方支付；T1 目标不是五家完整集成，而是：

1. 对五家建立可审计 Provider Profile 和统一适配差异；
2. 五个 Fake 运行同一套契约测试，证明核心不需要 provider 分支；
3. 只选择一家资料、授权和支持最完整的真实沙箱做端到端；
4. 后续每新增合作方均复用相同准入、契约、沙箱和商业验收。

“公开文档存在”“Fake 通过”“沙箱通过”“生产获准”是四个不同阶段，不得合并表述。

## 3. Provider Profile 强制字段

每家创建一个版本化档案，至少包含：

### 3.1 商务、合规与责任

- 法定主体、业务品牌、合作协议/保密协议状态；
- 服务类型、资金流和清结算责任；
- 支持的支付渠道、地区、行业、商户类型、费率/结算周期（只入受控商务库）；
- 商户进件、门店、终端、操作员模型；
- 风控限制、单笔/日限额、频控和禁限售行业；
- 数据处理、日志留存、隐私、安全事件和审计责任；
- 商务负责人、技术负责人、7×24 支持、升级和生产变更通知渠道。

### 3.2 环境与网络

- 沙箱/联调/生产环境的 base URL、DNS、TLS 版本、证书链；
- 是否需要固定出口 IP、VPN、mTLS、证书或硬件终端；
- 测试商户号、门店号、终端号、应用 ID 的申请与有效期；
- 回调公网 HTTPS、域名/IP 白名单、端口、证书和联调工具；
- 合作方时钟/时间戳容差、时区、报文编码、最大报文；
- 限流维度、阈值、`Retry-After`、维护窗口和沙箱稳定性说明。

### 3.3 接口与状态

- API 名称/版本：付款码支付、主扫预下单、交易查询、撤销、退款、退款查询、关单、对账下载；
- 请求 ID、商户订单号、合作方交易号、终端流水号的唯一和长度规则；
- 金额单位、币种、小数处理、零/负数/上限；
- 同步返回、异步回调、查询、对账的状态枚举和优先级；
- `PROCESSING/UNKNOWN` 定义、推荐查询节奏、最终超时和人工处置；
- 幂等范围、重复请求返回、同键不同参数、退款幂等；
- 回调重复、乱序、重放、验签、ACK 规范；
- 错误码、可重试性、风控/业务/系统/协议错误分类；
- 对账文件格式、生成时间、重取、校验、差异处理和历史期限。

### 3.4 加密与密钥

- 签名/加密算法、规范化字符串、字符集、证书格式；
- 测试密钥生成、交换、存储、轮换、吊销、过期和应急流程；
- 请求/响应/回调验签样例和官方测试向量；
- 敏感字段定义、掩码规则、禁止日志字段；
- SDK 版本、来源、SHA-256、许可证、native ABI、漏洞和替代 REST 方案。

## 5. 首家沙箱选择评分

| 维度 | 权重 | 硬门槛/评分重点 |
|---|---:|---|
| 状态与补偿完整性 | 25 | 查询、退款、对账、UNKNOWN、回调幂等齐全 |
| 沙箱可测试性 | 20 | 测试码/工具、故障态、稳定性、数据清理 |
| 文档与样例 | 15 | 固定版本、测试向量、错误码、变更日志 |
| 技术支持 | 15 | 有明确联系人、联调窗口和问题升级 |
| 安全与密钥 | 10 | 标准算法、轮换/吊销、mTLS/验签清晰 |
| 商业适配 | 10 | 便利店/零食店/社区超市、终端和门店模型 |
| SDK/依赖风险 | 5 | 可优先 REST；SDK 许可和漏洞可控 |

建议总分至少 80，且以下任一情况一票否决：需要生产密钥/真实资金、无原交易查询、超时被明确视为失败、重复请求不受控、回调无法验签、无法提供测试商户/终端、数据/合规责任不清。

实际首家合作方尚未决定。建议同时向至少易宝、汇付、拉卡拉发起沙箱资料申请，以“第一家完整达到硬门槛”进入 T1，而不是按品牌印象决定。

## 6. T1 支付验收范围

真实沙箱至少执行：

- 正常支付成功、明确失败、处理中、客户端超时和未知；
- 同幂等键同参数重复、同键不同参数冲突；
- 查询收敛成功/失败/仍处理中；
- 回调先于同步响应、重复 10 次、乱序、延迟、错误签名、过期重放；
- 退款成功、明确失败、超时/UNKNOWN、重复退款、超额拒绝和退款查询；
- 对账正常、平台单边、合作方单边、金额/状态差异；
- 本地“后续动作失败”不改变已经成功的支付事实；
- 全流程无自动二次扣款命令。

付款用官方测试介质/虚拟金额；若沙箱无法生成某故障，代理注入结果单独标记 `FAKE`，不能混在 `SANDBOX PASS` 中。

## 7. 支付密钥与数据安全

- GitHub Environment Secret 使用 `T1_<PROVIDER>_SANDBOX_*` 引用名，值不可导出到普通日志；
- 默认不允许来自 fork 的 PR 访问沙箱 Secret；需要人工批准的受保护环境；
- 沙箱 Job 不与普通 PR 自动并发执行，避免额度/状态污染；
- 所有请求/响应记录只留字段白名单和摘要，付款码、Token、签名、证书、手机号全部清除；
- callback 原文只在临时加密隔离区用于定位，证据保留脱敏派生物；
- 项目结束立即吊销测试密钥、回调白名单和账号权限，并留吊销证据。

## 8. 鲸熵汇资料清单（DEFERRED）

按项目发起人指令，鲸熵汇作为连接器中心的普通连接器，待收银系统主体完成后再提供资料。当前 `T1-JSH-001 = DEFERRED`，T1 禁止猜测、模拟为真实协议或写专用核心分支。

届时一次性收集：

### 8.1 主体与责任

- 接口提供主体、产品/环境、业务负责人、技术负责人、安全联系人；
- 合作/数据处理协议、测试授权、支持 SLA、变更和停机通知；
- 双方数据主权、对账、客诉、退款和数据修复责任。

### 8.2 接口目录

- 商户/门店/终端绑定；商品、条码、分类、单位、价格；
- 库存查询/推送；订单创建/查询/取消；支付/退款状态；
- 配送/履约（如有）；对账、差异和补偿；
- Webhook/事件目录、Schema、版本、幂等、顺序和重放；
- 全量/增量、游标、分页、时间窗、历史数据和删除语义。

### 8.3 鉴权、安全与运行约束

- OAuth/API Key/mTLS/签名算法、Token 生命周期、轮换和吊销；
- IP/域名白名单、TLS、时间戳/nonce、防重放；
- 商户/门店/环境隔离和最小权限；
- 限流维度/阈值、429/Retry-After、并发和批量上限；
- 超时、重试、熔断、维护窗、SLA、状态页和事件通知；
- PII/敏感字段、留存、跨境、删除、脱敏和审计要求。

### 8.4 沙箱与验收

- 沙箱 base URL、账号、商户/门店、测试数据、密钥、回调公网要求；
- 成功/失败/重复/乱序/延迟/限流/断点/数据修复的模拟方式；
- 官方 Postman/OpenAPI/Schema、签名向量、错误码、示例和变更日志；
- 双方最小闭环、性能、对账差异、故障恢复、证据和签字标准；
- 上线审批、灰度、回退、版本兼容、生产凭据和支持值班。
