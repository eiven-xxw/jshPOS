## 1. 选型结论边界

T1 采用“一台主认证 Android 收银机 + 一套规定外设组合 + 厂商无关适配契约”。主流品牌先进入候选池，不在没有实机、SDK 和证据时宣称已支持。T1 实机目标是证明架构可行，商业 L2 认证、量产供货和 7 天长稳仍属于后续门禁。

当前主机和全部外设未确定，实机需求均为 `BLOCKED`。本文件给出采购/厂商必须一次性补齐的输入，而不是假定某个型号已经可用。

## 3. 建议技术底线

以下是 T1 选型门槛，不是对某设备的既成事实：

| 项目 | 硬门槛 | 优选 |
|---|---|---|
| Android | API 28+，与仓库 `minSdk = 28` 一致；能固定系统 build | Android 11+，厂商提供持续安全补丁 |
| ABI | `arm64-v8a`；所有厂商 native 库有 64 位版本 | 无仅 32 位私有依赖 |
| 内存/存储 | 不低于 4 GB RAM / 32 GB 存储，压力测试无系统杀进程异常 | 4 GB/64 GB 及以上，存储健康可诊断 |
| 网络 | 稳定 Wi-Fi；至少一个有线或蜂窝备选 | Ethernet + 双频 Wi-Fi + 4G/5G |
| 调试 | 可获取 `adb`/受控诊断、logcat 和系统信息 | 量产可关闭调试但保留签名诊断包 |
| 安装 | 支持签名 APK 安装、版本查询、安装失败可诊断 | 厂商 MDM/灰度/回退接口 |
| SDK | 固定版本、合法获取、文档/示例/错误码完整 | Maven 化、语义化版本、变更通知 |
| 供货 | 型号和关键配件能覆盖计划试点 | 3 年供货/备件/安全支持承诺 |

若候选为 2 GB RAM 或 Android 9 老型号，必须单独做 Flutter 内存、后台恢复和支持年限风险接受，不得因“能安装 APK”自动通过。

## 5. 评分与一票否决

### 5.1 评分

| 维度 | 权重 | 核心问题 |
|---|---:|---|
| SDK/系统开放度 | 25 | API、错误码、示例、版本、许可、诊断是否可控 |
| 外设匹配 | 20 | 两种打印、扫码、秤、钱箱、客显是否可统一适配 |
| 稳定与安全生命周期 | 15 | 固件、补丁、保活、升级/回滚是否有承诺 |
| 供货与成本 | 15 | 量产、备件、价格、停产通知、RMA |
| 性能与可诊断性 | 10 | Flutter/SQLite/打印压力与日志能力 |
| 厂商支持 | 10 | 技术联系人、SLA、问题修复和 SDK 变更通知 |
| 形态与门店体验 | 5 | 屏幕、占地、线缆、安装和操作 |

总分 100，建议主认证入围线 75；但通过分数不能覆盖一票否决。

### 5.2 一票否决

- 无合法 SDK 获取/分发权或只提供无法审计的来源；
- 只有 32 位 native 库且无明确升级计划；
- 无法固定/追踪固件，厂商可静默破坏兼容；
- 无法获取关键错误码、超时或恢复语义；
- 无稳定设备唯一标识策略或需要越权系统权限；
- 要求在应用中硬编码生产密钥/通用厂商密钥；
- 不允许商业分发、不提供漏洞修复或已明确停产；
- 关键外设故障只能重启/清库恢复；
- 样机无法复现量产配置。

## 6. 外设组合输入

### 6.1 打印方案 A：内置厂商打印

必填：打印头规格、纸宽/有效点宽、DPI、切刀、缺纸/开盖/过热状态、队列/回调、图片/二维码、字符集、浓度、最大任务、厂商 SDK 版本、钱箱脉冲、打印服务重启方式。

验证：连续打印、并发请求、重复 requestId、缺纸恢复、开盖、过热、服务进程重启、App/Engine 重启、断电后未知任务的人工确认语义。

### 6.2 打印方案 B：外置标准打印

首选输入：ESC/POS over LAN，固定厂商/型号/固件、IP 分配、端口、状态回读协议、纸宽、切刀、钱箱口、中文码页、二维码、网络超时、重连和安全边界。若门店无法保证 LAN，则在评审后改为 USB Host，并补 VID/PID、权限、热插拔和驱动输入。

仅发送字节成功不能证明物理打印成功；无状态回读时结果必须允许 `UNKNOWN`，并提供重打副本标记/人工确认，不得暗称“恰好一次打印”。

### 6.3 扫码

至少认证一种：主机内置扫描头/厂商服务，或 USB HID 扫码枪。必填：码制、输入模式、前后缀、编码、连扫频率、同码去抖责任、按键模拟冲突、焦点依赖、软触发、超时、热插拔、固件。

目标码制至少包含 EAN-13、EAN-8、UPC-A、Code 128、QR；称重条码的业务解析不在 T1，只验证原始值可靠传递。

### 6.4 电子秤

建议首个协议为经 USB-Serial 转接的 RS-232 稳定读数协议；最终以采购场景为准。必填：厂商型号、计量器具证书/适用法规、协议文档、波特率/校验位、帧、单位、小数位、稳定/负重/超载标志、发送模式、去皮、零点、USB 芯片 VID/PID、Android 权限、断连恢复。

T1 只证明技术读数和错误语义，不代替法定计量检定，也不实现正式称重计价。

### 6.5 钱箱

优先由内置/外置打印机 RJ11 脉冲控制。必填：电压、脉冲宽度、接口、开箱状态反馈、重复命令风险。无状态反馈时命令超时必须为 `UNKNOWN`，不得自动重复开箱。

### 6.6 客显

优先顺序：主机内置副屏 SDK、Android Presentation/虚拟显示、标准外置串口/USB 客显。必填：分辨率/字符集、显示 API、隐私遮罩、前后台生命周期、断连、刷新幂等、支付码/消费者隐私限制。T1 只显示合成商品和金额。

## 7. SDK 获取与入库流程

1. 采购/厂商在受控渠道提供下载地址、版本、发布日期、SHA-256 和许可；
2. 设备负责人和安全负责人核对来源、恶意代码、native ABI、权限、依赖和已知漏洞；
3. 法务/采购确认商业使用、分发、升级和保密边界；
4. SDK 不直接提交公开目录；按许可进入私有制品库，CI 用凭据拉取；
5. 建立最小原生样例证明 SDK 独立可运行，再封装 Kotlin 插件；
6. 固定 SDK 与固件兼容矩阵，任何升级走变更和实机回归；
7. 记录移除/替代策略，核心层不得依赖厂商类型。

## 8. 硬件认证分级

| 等级 | 定义 | 可对外表述 |
|---|---|---|
| L0 契约 | 文档/编译/Fake 契约通过 | “具备适配接口”，不得写支持型号 |
| L1 实验室 | 指定型号、固件、外设组合完成 T1 实机功能与恢复矩阵 | “实验室验证”，不得作为正式兼容承诺 |
| L2 商业认证 | 规定 7 天长稳、压力、升级、弱网、RMA 和版本冻结通过 | 仅可宣称证书列出的型号/固件/组合 |

T1 的退出目标最多到 L1；详细设计 36/商业 V1 要求的 L2 在后续完成。
