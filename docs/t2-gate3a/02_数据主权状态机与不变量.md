# Gate 3A 数据主权、状态机与不变量

## 1. 数据主权

- Order：原单成交快照 Owner，仅通过只读端口提供 `orderId/storeId/currency/paidAmount/lines`；
- Payment：支付意图、attempt、观察、状态历史、幂等、审计和 Outbox 的唯一写入 Owner；
- Refund：支付模块内的退款聚合，必须绑定原 payment 和 order；
- Reconciliation：账单来源行与内部匹配结果分别不可变，差异案例独立演进；
- Provider Adapter：未来只负责协议、签名和网络，不能定义核心状态语义。

## 2. 支付状态

`CREATED → PROCESSING → SUCCEEDED|FAILED|UNKNOWN|CANCELLED|CLOSED`。`UNKNOWN → SUCCEEDED|FAILED|CANCELLED|CLOSED` 只能来自原 attempt 的可信观察。`SUCCEEDED → PARTIALLY_REFUNDED → REFUNDED` 只由成功退款累计驱动。

`SUCCEEDED/PARTIALLY_REFUNDED/REFUNDED` 是已确认资金事实，任何 FAILED、超时或乱序回调都不得回退。支付处于 `UNKNOWN` 时禁止创建新 attempt；人工操作也只能查询或等待对账，不能重新生成扣款命令。

## 3. 观察合并

正式观察来源仅为 `SYNC_RESPONSE/QUERY/CALLBACK/STATEMENT`，只接受受信适配器内部端口。`FAKE_TEST` 仅是测试代码用于验证拒绝路径的保留枚举值，不进入正式 Schema 和数据库约束，运行时必须失败关闭。状态优先级按资金事实确定：确认成功最高；明确失败可终结未成功 attempt；未知不覆盖明确终态；到达时间不参与优先级。

相同 `observation_id` 与相同 hash 是重复；相同 ID 异 hash、成功金额/币种/商户/门店/终端不匹配、Provider 引用复用均进入 `CONFLICT` 安全记录，不改变聚合状态。

## 4. 退款状态与占额

`CREATED → PENDING_APPROVAL|PROCESSING → SUCCEEDED|FAILED|UNKNOWN|CANCELLED|CLOSED`，`UNKNOWN` 同样只能由原 refund request 的可信观察收敛。

占额状态为 `PROCESSING/UNKNOWN/SUCCEEDED`；创建或推进退款时，在支付聚合锁内计算：

- `sum(reserved_refund_amount_minor) + new_amount <= succeeded_payment_amount_minor`；
- 每个订单行 `sum(reserved_quantity) + new_quantity <= original_quantity`；
- 每行退款金额非负且合计严格等于退款总额；币种必须与原支付一致；
- 原单优惠不重新计算，退款分摊由原成交快照确定。

## 5. 对账状态

差异类型：`INTERNAL_ONLY/PROVIDER_ONLY/AMOUNT_MISMATCH/CURRENCY_MISMATCH/STATUS_MISMATCH/DUPLICATE_PROVIDER_REF/REFUND_MISMATCH`。案例状态：`OPEN → INVESTIGATING|WAITING_PROVIDER → RESOLVED → APPROVED → CLOSED`。

对账不能直接更新支付/退款状态；需要收敛资金事实时必须通过新的可信观察或经批准的专门修复命令，保留原始证据、操作者和审计链。
