# 一、核心设计决策

## 1.1 数据架构原则

1. **领域拥有数据。** 每张业务表只有一个领域模块拥有写权限，其他模块通过应用接口或领域事件读取结果。
2. **交易事实不可覆盖。** 订单、支付、退款、库存、积分、储值、现金和结算使用状态迁移、流水、冲正或调整表达变化。
3. **余额不是唯一事实。** 库存余额、积分余额、储值余额和应收应付余额必须能由受控流水核验。
4. **离线标识可生成。** POS离线创建的订单、支付引用、班次、打印任务和同步事件使用ULID，无需向服务端申请主键。
5. **平台身份遵循若依。** `sys_tenant.id`、用户、部门、角色等记录主键沿用`BIGINT`；业务隔离字段`tenant_id`沿用RuoYi-Vue-Plus的`VARCHAR(20)`租户编号。
6. **租户隔离贯穿全链路。** 表、索引、缓存、对象路径、异步任务、事件和日志均携带租户上下文。
7. **一致性按边界治理。** 单聚合使用本地事务；跨领域采用Outbox、幂等消费和补偿，不使用跨服务分布式事务。
8. **快照保证可重放。** 订单保存成交时商品、价格、优惠、税、会员权益和打印模板的必要快照。
9. **主数据版本化下发。** 商品、价格、促销和配置通过版本包或增量游标下发，终端校验后原子切换。
10. **数据库变更向前兼容。** 云端必须兼容仍在支持期内的POS版本，使用Expand-Migrate-Contract演进。

## 1.2 数据库形态

商业V1采用MySQL单逻辑库、模块化Schema命名的共享数据库模式：

- 所有租户业务表使用行级`tenant_id`隔离。
- 大客户可演进到独立数据库或独立实例，但逻辑模型和迁移版本保持一致。
- 交易库不承担复杂全文检索和大规模分析；达到阈值后使用只读副本、搜索或分析库。
- Redis不是交易事实来源；对象存储不替代数据库索引和元数据。
- 数据库Outbox是可靠事件的基础，消息队列只是传输通道。

## 1.3 标识体系

| 标识类型 | 数据类型 | 生成方 | 示例 | 用途 |
|---|---|---|---|---|
| 平台记录主键 | `BIGINT` | RuoYi服务端 | `1000001` | sys_tenant.id、user、dept、role |
| 业务租户编号 | `VARCHAR(20)` | RuoYi租户服务 | `000001` | 所有租户业务表的tenant_id和拦截器条件 |
| 领域聚合ID | `CHAR(26)` ASCII binary | 服务端或离线终端 | `01J5...` | 订单、支付、退款、库存单据 |
| 业务单号 | `VARCHAR(40)` | 编号服务/终端规则 | `SO202608150001` | 人工查找、打印、客服 |
| 外部对象ID | `VARCHAR(128)` | 第三方平台 | 平台订单号 | 映射与幂等，不作为内部主键 |
| 事件ID | `CHAR(26)` | 事件生产者 | ULID | Outbox、Inbox、Webhook幂等 |
| 设备ID | `CHAR(26)` | 设备激活服务 | ULID | POS实例身份，不等于硬件序列号 |

ULID必须使用大写规范形式并以ASCII二进制排序。业务单号不承载数据库关系，不得通过解析单号推导租户、门店或日期事实。

租户类型以[RuoYi-Vue-Plus 5.X官方建表脚本](https://raw.githubusercontent.com/dromara/RuoYi-Vue-Plus/5.X/script/sql/ry_vue_5.X.sql)为基线：`sys_tenant.id`为`BIGINT`，业务租户编号`tenant_id`为`VARCHAR(20)`。

## 1.4 时间与业务日期

- 数据库存储时间统一使用UTC语义的`DATETIME(3)`；JDBC会话时区固定为UTC。
- API使用ISO 8601并携带时区偏移。
- 所有交易同时保存`occurred_at`和`business_date`。
- `business_date`由门店营业日历和班次决定，可以不同于自然日期。
- 第三方时间同时保存原始时间、解析时区和平台标准时间；无法确定时区时进入异常队列。
- 客户端时间不可信。服务端记录`received_at`，并对明显漂移的`occurred_at`标记风险。

## 1.5 金额、价格、成本和数量

| 数据 | 存储规则 | 说明 |
|---|---|---|
| 应收、实收、退款、优惠 | `BIGINT`最小货币单位 | 人民币为分；字段名以`_minor`结尾 |
| 币种 | `CHAR(3)` | ISO 4217，如`CNY` |
| 标准单价 | `DECIMAL(19,6)` | 支持称重和税额中间计算 |
| 单位成本 | `DECIMAL(19,6)` | 移动加权计算，不直接展示为结算金额 |
| 数量 | `DECIMAL(19,6)` | 禁止浮点；商品可配置允许精度 |
| 税率/折扣率 | `DECIMAL(12,8)` | 0至1的小数语义 |
| 汇率 | `DECIMAL(19,8)` | 商业V1只启用CNY，结构预留 |

Java使用`BigDecimal`和金额值对象，Dart使用整数最小货币单位与受控Decimal实现。禁止在金额链路使用`float`、`double`或JavaScript Number进行最终计算。

## 1.6 状态字段

- 生命周期状态使用可读的`VARCHAR(32)`稳定代码，不使用含义不透明的魔法整数。
- 状态代码一经发布不得重解释；新增状态必须保持旧客户端可安全降级。
- `status`表示主状态；异常、风险、同步、履约等正交维度使用独立字段。
- 每次核心状态迁移写入状态历史或不可变业务流水，并带命令ID、操作者、原因和时间。

# 二、领域边界与数据所有权

## 2.1 有界上下文

| 领域 | 主要职责 | 核心聚合 | 主要表前缀 | 权威事实 |
|---|---|---|---|---|
| 平台与IAM | 租户、组织、用户、权限、套餐、审计 | Tenant、Store、DeviceGrant | `sys_`/`biz_` | 租户和身份 |
| 设备与同步 | 终端、激活、版本、数据包、游标、冲突 | Terminal、SyncPackage | `dev_`/`sync_` | 设备与同步状态 |
| 商品主数据 | 商品、SKU、条码、单位、门店范围 | Product、Sku | `prd_` | 商品身份和属性 |
| 价格 | 价格簿、门店价、发布版本 | PriceBook、PriceRelease | `prc_` | 基础成交价格候选 |
| 促销 | 活动、规则、优惠券、优惠分摊 | Campaign、PromotionSnapshot | `prm_` | 优惠规则与计算快照 |
| 订单与班次 | 销售、退货引用、挂单、班次、现金 | SalesOrder、Shift | `ord_`/`shf_` | 商品成交事实与应收 |
| 支付与退款 | 支付意图、尝试、退款、渠道事件、对账 | Payment、Refund | `pay_` | 资金指令与渠道结果引用 |
| 库存与成本 | 余额、流水、预占、盘点、成本 | StockLedger、Reservation | `inv_` | 库存数量和成本事实 |
| 采购供应链 | 供应商、采购、收货、调拨、补货 | PurchaseOrder、Transfer | `pur_`/`sup_` | 采购与流转单据 |
| 会员权益 | 会员、身份映射、积分、券、储值引用 | Member、PointsAccount | `mbr_` | 客户身份与权益账本 |
| 结算与往来 | 供应商、加盟商、渠道往来和结算 | SettlementStatement | `set_` | 业务结算事实 |
| 连接器 | 授权、映射、原始报文、运行任务 | ConnectorInstance、Mapping | `con_` | 外部映射和集成过程 |
| 报表语义 | 指标定义、聚合和导出任务 | MetricDefinition | `rpt_` | 指标口径，不回写交易 |

## 2.2 跨领域引用规则

- 领域之间只保存对方聚合ID和必要快照，不建立可级联删除的跨领域外键。
- 同库不代表可跨领域写表。Repository只能访问所属模块表。
- 报表可通过只读视图、查询服务或分析模型组合数据，不得反向更新交易表。
- 商品改名、条码变更、会员资料更新不得改变历史订单快照。
- 支付领域不修改订单表；订单应用层在接收支付事实后执行自身状态迁移。
- 库存领域不根据订单表轮询扣减；只消费明确的库存命令/事件并按业务键幂等。

## 2.3 聚合事务边界

| 聚合 | 一个事务内可以修改 | 禁止同事务直接修改 |
|---|---|---|
| SalesOrder | 订单头、行、调整、成交快照、订单状态历史、Outbox | 支付、库存、会员账本 |
| Payment | 支付意图、支付尝试、渠道事件引用、状态历史、Outbox | 订单、库存 |
| Refund | 退款单、退款尝试、状态历史、Outbox | 原订单行、库存流水 |
| StockLedger命令 | 库存流水、余额、成本流水、Outbox | 订单和支付表 |
| Reservation | 预占头、预占行、状态历史、Outbox | 外部订单表 |
| Shift | 班次、现金流水、交班汇总、Outbox | 支付渠道账单 |
| MemberAccount | 积分/储值流水、余额、Outbox | 订单与支付表 |

# 三、多租户、组织与门店模型

## 3.1 层级模型

```text
Tenant（SaaS隔离边界）
└─ Group/Company（经营主体，可选）
   ├─ Brand（品牌）
   ├─ Region（区域）
   ├─ Franchisee（加盟商/核算主体，可选）
   └─ Store（门店）
      ├─ Warehouse（门店仓/虚拟仓）
      └─ Terminal（POS/PDA/自助设备实例）
```

租户不是门店，部门树也不是库存组织。组织权限、经营核算、库存地点和设备归属必须分开建模。

## 3.2 平台与经营组织表

| 表名 | 说明 | 主键 | 关键约束 |
|---|---|---|---|
| `sys_tenant` | 若依租户基础表 | `BIGINT` | 平台权威，不复制租户状态 |
| `sys_user` | 若依用户 | `BIGINT` | 登录身份，不直接代表员工档案全部信息 |
| `sys_dept` | 若依权限组织 | `BIGINT` | 只用于权限组织树 |
| `biz_company` | 法人/经营主体 | ULID | `(tenant_id, company_code)`唯一 |
| `biz_brand` | 经营品牌 | ULID | `(tenant_id, brand_code)`唯一 |
| `biz_region` | 经营区域 | ULID | 支持区域树，禁止循环父子关系 |
| `biz_franchisee` | 加盟商/独立核算主体 | ULID | 可关联公司、结算策略和数据范围 |
| `biz_store` | 门店 | ULID | `(tenant_id, store_code)`唯一，保存时区和营业日历 |
| `biz_warehouse` | 仓库/库位上层地点 | ULID | `(tenant_id, warehouse_code)`唯一 |
| `dev_terminal` | 终端实例 | ULID | `(tenant_id, terminal_code)`唯一，绑定门店 |

## 3.3 租户字段约束

- 所有租户业务表必须有`tenant_id VARCHAR(20) NOT NULL`，类型与RuoYi 5.X租户拦截器和建表脚本保持一致。
- 唯一键必须把`tenant_id`放入范围，例如`UNIQUE(tenant_id, store_code)`。
- 对全局ULID主键仍保留`tenant_id`索引，用于查询裁剪、隔离和归档。
- 子表可以冗余`tenant_id`，并通过应用与测试保证和父表一致，避免仅靠父表Join才能隔离。
- 平台跨租户任务必须使用独立平台身份，显式声明目标租户并记录审计。
- 客户端提交的`tenant_id`只作为协议字段校验，最终值来自设备/令牌上下文。

# 四、通用字段与表设计规范

## 4.1 通用字段模板

业务主数据和交易表按适用场景使用以下字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `id` | `CHAR(26)`或平台`BIGINT` | 主键；领域表ULID使用ASCII binary |
| `tenant_id` | `VARCHAR(20)` | 非空，RuoYi租户编号，进入索引与权限上下文 |
| `record_version` | `BIGINT` | 乐观锁，初始1，每次业务修改递增 |
| `created_at` | `DATETIME(3)` | UTC，数据库默认当前时间 |
| `created_by` | `BIGINT NULL` | 平台用户ID；设备自动任务可为空并另记actor |
| `updated_at` | `DATETIME(3)` | UTC，业务更新时刷新 |
| `updated_by` | `BIGINT NULL` | 最后修改用户 |
| `is_deleted` | `TINYINT` | 仅适用可软删除主数据，默认0 |
| `deleted_at` | `DATETIME(3) NULL` | 软删除时间 |
| `trace_id` | `VARCHAR(64) NULL` | 仅在需要定位创建来源的关键事实保存 |

交易账本不使用`is_deleted`表示撤销。撤销、冲正、作废和关闭必须通过业务状态和反向流水表达。

## 4.2 Actor模型

核心操作记录统一Actor信息：

| 字段 | 说明 |
|---|---|
| `actor_type` | `USER`、`DEVICE`、`SYSTEM`、`OPEN_API`、`CONNECTOR` |
| `actor_id` | 对应身份ID的字符串形式 |
| `actor_name_snapshot` | 操作时显示名快照，不作为鉴权依据 |
| `reason_code` | 标准原因码 |
| `reason_text` | 必要补充说明，受长度和敏感信息限制 |

## 4.3 编码与排序规则

- 数据库字符集使用`utf8mb4`。
- 业务自然语言字段使用经评审的中文友好排序规则。
- ULID、幂等键、签名摘要、外部精确ID使用ASCII或二进制排序规则，保持大小写敏感。
- 条码默认按字符串保存，保留前导零；禁止存为数字。
- 手机号按标准化后的国家码和号码分列或形成标准E.164值。

## 4.4 删除规则

| 数据类型 | 删除策略 |
|---|---|
| 商品、供应商、门店等主数据 | 停用优先；无引用时才允许软删除 |
| 订单、支付、退款、库存、账本 | 永不物理删除；使用状态、冲正和归档 |
| 临时导入文件 | 按保留策略删除对象和元数据 |
| 原始Webhook/连接器报文 | 按合同、安全和排障期限归档或删除 |
| 隐私资料 | 依法执行匿名化/删除请求，同时保留不可关联的法定交易凭证 |

# 五、商品、价格与促销数据模型

## 5.1 商品主数据

| 表名 | 聚合/用途 | 关键字段或约束 |
|---|---|---|
| `prd_spu` | 商品概念 | `name`、`category_id`、`brand_id`、`product_type`、状态 |
| `prd_sku` | 可销售/库存SKU | `spu_id`、`sku_code`、`stock_unit_id`、称重/批次/效期属性 |
| `prd_barcode` | 条码与秤码规则 | `(tenant_id, barcode, scope_type, scope_id)`有效范围内唯一 |
| `prd_category` | 分类树 | 唯一编码、父节点、防循环、排序 |
| `prd_brand` | 商品品牌 | 与经营品牌`biz_brand`分离 |
| `prd_unit` | 单位 | 精度、是否允许小数 |
| `prd_unit_conversion` | 单位换算 | 分子分母或高精度换算，禁止浮点 |
| `prd_store_scope` | 门店可售范围 | SKU、门店、上架/停售、起止时间 |
| `prd_supplier_item` | 供应商商品关系 | 供应商货号、采购单位、箱规、起订量 |
| `prd_change_version` | 主数据发布版本 | 版本、摘要、发布时间、适用范围 |

商品名称、规格、单位、税率等在订单行中保存成交快照。历史订单不得依赖当前`prd_sku`还原。

## 5.2 价格模型

| 表名 | 用途 | 关键约束 |
|---|---|---|
| `prc_price_book` | 总部、区域、门店、会员等价格簿 | `(tenant_id, price_book_code)`唯一 |

# 十一、索引、并发与性能规范

## 11.1 索引原则

- 索引从真实查询和租户过滤出发，不为每个字段机械建索引。
- 高频租户查询的联合索引通常以`tenant_id`开头，后接高选择性范围字段。
- 唯一约束必须在数据库实现，不能只依赖应用先查后插。
- 外部ID、幂等键、订单号、支付号、条码等精确查找使用二进制/大小写敏感排序。
- 大文本、JSON和低选择性状态字段不单独建立无效索引。
- 上线前对核心SQL执行`EXPLAIN ANALYZE`，保存基准数据量和执行计划。

## 11.2 并发控制

| 场景 | 策略 |
|---|---|
| 主数据普通编辑 | `record_version`乐观锁 |
| 订单状态迁移 | 条件更新`WHERE id=? AND status=? AND record_version=?` |
| 支付回调 | 渠道事件唯一键 + 支付状态机条件更新 |
| 库存扣减 | 锁定余额行或原子条件更新 + 同事务流水 |
| 库存预占 | 幂等键 + 可用量条件更新 + 预占流水 |
| Outbox认领 | 短租约/跳过锁定记录，处理完成后确认 |
| 编号生成 | 服务端号段或终端安全序列；主键不依赖编号 |

禁止在乐观锁失败后无条件覆盖。调用方必须重新读取并按当前状态决定重试、拒绝或进入冲突处理。

## 11.3 分页与导出

- 交易明细优先使用稳定游标分页，如`(occurred_at, id)`。
- 页码分页只用于变化较小的管理列表。
- 大导出创建异步任务并从只读副本/分析层读取。
- 导出任务记录查询条件、数据范围、操作者、文件摘要、到期和下载审计。

## 11.4 容量与分区

商业V1不预先分库分表。满足以下任一条件时通过ADR评估归档、分区或分片：

- 单表达到影响备份、迁移或核心查询的实际阈值。
- 单租户占用形成明显热点或需要专属SLA。
- 报表负载持续影响交易P95。
- 法律、合同或数据驻留要求独立存储。

分片键不得只考虑写入均匀，还必须满足租户隔离、门店查询、对账、归档和迁移。

# 十二、事件、审计与可追溯性

## 12.1 领域事件字段

| 字段 | 规则 |
|---|---|
| `event_id` | ULID，全局唯一 |
| `event_type` | 过去式事实 + 版本，如`order.paid.v1` |
| `tenant_id` | 从服务端上下文写入 |
| `aggregate_type/id/version` | 支持顺序和幂等检查 |
| `occurred_at` | 事实发生时间 |
| `trace_id` | 跨调用关联 |
| `schema_version` | Payload契约版本 |
| `payload` | 只包含消费者必要数据，不泄漏敏感字段 |

## 12.2 审计分类

- 安全审计：登录、MFA、设备激活、权限和密钥变更。
- 管理审计：商品、价格、促销、配置和套餐变更。
- 交易审计：改价、抹零、退款、无单退货、库存调整和交班差异。
- 数据审计：导入、导出、迁移、合并、匿名化和删除请求。
- 运维审计：远程命令、版本升级、诊断包和人工数据修复。

审计日志与业务状态历史分工明确：审计说明“谁做了什么”，领域流水说明“业务事实如何变化”。二者都不能用普通应用日志替代。

## 12.3 人工数据修复

- 禁止直接在生产库执行无记录的UPDATE修复交易。
- 修复必须有工单、影响分析、备份、双人复核、可重放脚本和结果核对。
- 能通过业务调整单或冲正解决时，不使用SQL修改事实。
- 紧急SQL执行后必须补录审计、事件和核验报告，并在24小时内复盘。

# 十三、数据安全、隐私与保留

## 13.1 数据分级

| 等级 | 示例 | 保护要求 |
|---|---|---|
| L4高度敏感 | 密钥、支付证书、设备私钥 | 不进普通表；KMS/安全存储；严格访问与轮换 |
| L3敏感个人信息 | 身份证、精确地址、支付敏感引用 | 字段加密、最小化、强审计和脱敏展示 |
| L2个人信息/商业敏感 | 手机、会员、采购价、毛利 | 权限、脱敏、导出水印和保留控制 |
| L1内部 | 配置、一般日志、字典 | 内部访问和完整性保护 |
| L0公开 | 已公开商品信息 | 防篡改和来源治理 |

## 13.2 加密与密钥

- 传输使用TLS；数据库磁盘和备份启用存储加密。
- 应用字段加密使用信封加密和版本化密钥，密文保存算法/密钥版本。
- 搜索敏感精确值时使用标准化后HMAC索引，不保存可逆明文索引。
- 密钥不写入代码、配置仓库、日志、诊断包和普通数据库备份。

## 13.3 保留与归档

具体期限由法律、合同、财税和业务需要确认并写入文档39。技术实现必须支持：

- 按租户、数据类型和日期配置保留策略。
- 归档前生成数量、金额、摘要和对象清单。
- 归档数据只读、加密、可检索、可审计恢复。
- 删除任务幂等并产生不可篡改证明。
- 合法冻结（Legal Hold）期间暂停删除。

# 十四、数据库迁移与版本兼容

## 14.1 Flyway目录

```text
db/migration/
├─ platform/
├─ masterdata/
├─ order/
├─ payment/
├─ inventory/
├─ member/
├─ sync/
└─ connector/
```

迁移版本在最终打包时形成全局单调序列，文件名包含版本、模块和动作，如`V20260815_031__order_add_refund_status.sql`。

## 14.2 迁移规则

- 已进入共享环境的脚本不得修改，只能新增修复脚本。
- 先加可空列/新表并双写，再迁移存量，再切读，最后在后续版本收缩旧结构。
- 同一版本不得删除旧POS仍访问的字段、枚举和接口。
- 新非空字段必须提供默认、回填或分阶段约束策略。
- 大表DDL必须评估元数据锁、复制延迟、中断恢复和回滚窗口。
- 迁移前后执行数量、金额、摘要和孤儿引用核对。

## 14.3 多版本兼容

- 服务端维护最低支持POS协议版本和强制升级条件。
- 新状态对旧客户端必须映射到安全可读状态；不能让旧客户端把未知状态当成功。
- 数据包Schema包含版本和最小客户端版本。
- 事件消费者至少支持当前和上一个仍在投递窗口内的Schema版本。

# 十五、数据质量与对账规则

## 15.1 通用质量维度

| 维度 | 检查示例 |
|---|---|
| 完整性 | 非空字段、订单行存在、支付引用存在 |
| 唯一性 | 条码、业务号、外部ID、幂等键 |
| 一致性 | tenant一致、金额守恒、状态与流水一致 |
| 准确性 | 商品单位、税率、价格、成本来源 |
| 及时性 | POS同步延迟、连接器游标、对账账期 |
| 可追溯性 | 来源、版本、actor、trace、原始报文引用 |

## 15.2 每日自动核验

- 订单应收、支付净额、退款累计和订单支付状态一致。
- 库存余额与流水累计/抽样重算一致。
- 现金理论余额与班次现金流水一致。
- 积分、券和储值余额与账本一致。
- Outbox无超时积压，Inbox无异常重复Payload。
- 支付渠道账单与系统支付/退款匹配。
- 各租户核心表不存在tenant为空或父子tenant不一致。

核验失败必须进入异常中心，记录规则版本、影响范围、首次/最近发生时间和处理结果。

# 十六、禁止事项

- 禁止以数据库自增ID作为离线订单主键。
- 禁止使用浮点数保存或计算金额、成本和数量。
- 禁止订单、支付、退款、库存共用一个万能状态字段。
- 禁止通过删除支付/库存流水修正结果。
- 禁止跨领域Mapper直接更新其他模块表。
- 禁止只在Controller或前端检查租户和权限。
- 禁止以Redis、消息队列或日志作为唯一交易事实。
- 禁止对未知支付结果自动再次发起扣款。
- 禁止把当前商品、价格和促销数据当作历史订单快照。
- 禁止无幂等键处理POS重传、Webhook和库存命令。
- 禁止生产手工改表代替Flyway迁移。
- 禁止未加密保存支付密钥、设备私钥和连接器凭证。
