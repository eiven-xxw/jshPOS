# 文档说明

## 1. 编写目的

本文定义价格候选、促销条件、规则优先级、叠加互斥、优惠预算、优惠券、手工折扣、金额舍入、订单行分摊、退货回退、离线规则包与计算可解释性的统一规格。

商业目标：

- 云端、POS 和第三方接单使用同一促销语义；
- 同一输入和规则版本得到完全一致的结果；
- 优惠总额、行分摊和应收金额精确守恒；
- 退货按成交时分摊回退，不因当前活动变化多退或少退；
- 复杂促销可解释、可审计、可灰度、可回滚；
- 离线终端只执行受支持且签名有效的规则；
- 运营配置错误不会直接形成无限折扣或预算穿透。

## 2. 非目标

商业 V1 不把促销引擎建设为通用脚本平台，不允许租户上传任意代码。表达式必须来自白名单 DSL 和版本化算子，保证安全、确定性和跨端一致。

## 3. 依赖关系

- 订单金额、状态与退货退款遵循 POS-DD-032。
- 商品、价格簿、金额、数量和快照字段遵循 POS-DD-031。
- POS 离线包、游标与原子切换遵循 POS-DD-035。
- 库存赠品、套装和退货入库遵循 POS-DD-033。

# 一、核心原则

## 1.1 确定性

计算结果只取决于：

- pricing_input；
- price_book_version；
- promotion_release_version；
- coupon_token 或权益快照；
- engine_version；
- 明确的门店业务时间与时区。

禁止依赖：

- 运行时随机数；
- 未冻结的当前系统时间；
- 无版本远程查询结果；
- Map/Set 非稳定迭代顺序；
- float、double 或 JavaScript Number 最终金额；
- 客户端可篡改的会员等级、券余额或预算值。

同一规范输入重放必须得到相同 promotion_fingerprint、line_adjustments 和 payable_amount_minor。

## 1.2 价格与优惠分层

价格处理分为：

1. 基础价格候选选择；
2. 行级促销；
3. 组合、阶梯与买赠；
4. 订单级门槛促销；
5. 优惠券和会员权益；
6. 手工折扣；
7. 应收舍入。

“特价”属于成交基价候选，“满减”属于优惠调整。两者必须分开保存，避免报表无法区分降价与促销费用。

## 1.3 快照优先

订单提交时必须保存：

- 原始标价；
- 选中基础价及来源；
- 所有候选、命中与未命中原因；
- 规则版本和引擎版本；
- 每个调整项及其分摊；
- 会员、券、渠道和业务时间快照；
- 最终应收、舍入差额与计算指纹。

后续退货、对账、报表和客诉使用成交快照，不根据当前规则重算历史订单。

## 1.4 租户、标识与可靠发布

- tenant_id 使用 VARCHAR(20)，从认证或设备授权上下文取得，进入规则、版本、预算、券、缓存键、数据包和事件。
- 活动、规则、调整、分摊、券令牌和发布事件使用 ULID。
- 促销发布、暂停、撤销和预算变更在本地事务内写状态历史、审计与 Outbox。
- 规则包和跨端计算输入使用规范化 JSON，并保存 payload_hash 供幂等与完整性校验。
- 下游消费者使用 Inbox 防重；重复发布事件不得重复激活版本或占用预算。

# 二、金额与数量

## 2.1 类型

| 数据 | 类型 | 规则 |
|---|---|---|
| 成交金额、优惠、税、应收 | BIGINT 最小货币单位 | CNY 为分，字段以 _minor 结尾 |
| 标准单价和中间价 | DECIMAL(19,6) | 支持称重、税和单位换算 |
| 数量 | DECIMAL(19,6) | 受 SKU quantity_scale 限制 |
| 比例 | DECIMAL(12,8) | 例如 0.85000000 表示八五折 |
| 预算与限额 | BIGINT 最小货币单位 | 事务或令牌控制 |

## 2.2 不变量

- line_gross_amount_minor 大于等于 0。
- line_discount_amount_minor 大于等于 0。
- line_net_amount_minor = line_gross_amount_minor - line_discount_amount_minor，且不得小于 0。
- order_discount_amount_minor 等于所有订单级优惠分摊之和。
- total_discount_amount_minor 等于所有 adjustment 分摊之和。
- payable_amount_minor = gross_amount_minor - total_discount_amount_minor + fee_amount_minor + tax_adjustment_minor + rounding_minor。
- payable_amount_minor 不得小于 0。
- 所有分摊后的金额之和必须精确等于原优惠金额。

# 四、价格候选

## 4.1 候选来源

| 候选类型 | 示例 | 默认优先级 |
|---|---|---:|
| MANUAL_OVERRIDE | 主管授权改价 | 10 |
| CONTRACT_PRICE | 企业客户协议价 | 20 |
| MEMBER_PRICE | 会员等级价 | 30 |
| STORE_SPECIAL_PRICE | 门店特价 | 40 |
| CHANNEL_PRICE | 外卖/电商渠道价 | 50 |
| STORE_PRICE_BOOK | 门店价格簿 | 60 |
| REGION_PRICE_BOOK | 区域价格簿 | 70 |
| TENANT_LIST_PRICE | 租户标准价 | 80 |

数字越小优先级越高。实际优先级可配置，但发布版本内必须固定。

## 4.2 选价规则

1. 过滤租户、门店、渠道、时间、会员、单位和 SKU 不适用候选。
2. 校验候选价格生效版本与签名。
3. 按 priority 升序。
4. priority 相同按 specificity_score 降序。
5. 再按 price_minor 升序。
6. 最后按 price_rule_id 的 ASCII 升序稳定决胜。

租户可配置“最高优先级”或“同级最低价”，但必须在 price_policy_version 中冻结。

## 4.3 价格保护

- 低于最低售价、最低毛利或 MAP 策略时需要审批或阻断。
- 手工改价不得规避促销互斥，必须作为价格来源参与后续计算。
- 负价格禁止。
- 免费商品以 0 元成交基价或 GIFT 调整表达，但必须记录原因。
- 称重商品先用 DECIMAL 计算数量乘单价，再按货币舍入规则得到行毛额。

# 五、促销规则模型

## 5.1 Campaign 与 Rule

Campaign 表达运营活动，Rule 表达计算规则。一个活动可有多个规则，但每条规则必须独立版本化。

规则通用字段：

| 字段 | 说明 |
|---|---|
| rule_id | ULID |
| rule_code | 租户内稳定编码 |
| rule_type | 白名单规则类型 |
| priority | 数字越小越先处理 |
| exclusive_group | 互斥组 |
| stack_mode | EXCLUSIVE、STACKABLE、BEST_OF_GROUP、STOP_AFTER_APPLY |
| scope | SKU、SPU、类目、品牌、标签、全单 |
| eligibility | 门店、渠道、会员、时间、数量、金额等条件 |
| benefit | 折扣、减额、赠品或固定价 |
| usage_limit | 单单、单会员、单日、总量或预算 |
| offline_policy | OFFLINE_ALLOWED、ONLINE_ONLY、TOKEN_REQUIRED |
| effective_from/to | 带时区生效窗口 |
| release_version | 发布版本 |

## 5.2 商业 V1 规则类型

| rule_type | 含义 | 示例 |
|---|---|---|
| SPECIAL_PRICE | 促销固定价 | 指定 SKU 9.9 元 |
| PERCENT_OFF | 百分比折扣 | 第二件八折的基础算子 |
| AMOUNT_OFF | 固定减额 | 单品减 5 元 |
| NTH_ITEM_DISCOUNT | 第 N 件优惠 | 第二件半价 |
| BUY_X_GET_Y | 买赠 | 买 2 赠 1 |
| BUNDLE_PRICE | 组合价 | A+B 套餐 19.9 |
| TIERED_QUANTITY | 数量阶梯 | 3 件九折、5 件八折 |
| THRESHOLD_AMOUNT_OFF | 满额减 | 满 100 减 20 |
| THRESHOLD_PERCENT_OFF | 满额折 | 满 200 九折 |
| GIFT | 赠品 | 满额赠指定 SKU |
| COUPON_AMOUNT | 券减额 | 20 元券 |
| COUPON_PERCENT | 券折扣 | 九折券 |
| MEMBER_BENEFIT | 会员权益 | 会员专享 95 折 |
| MANUAL_DISCOUNT | 手工折扣 | 主管授权减 10 元 |
| ROUNDING | 应收抹零 | 现金抹分 |

商业 V1 不支持任意 JavaScript、Groovy、SpEL 或数据库 SQL 表达式。

## 5.3 条件算子

白名单条件：

- 等于、不等于、包含、不包含；
- 大于、大于等于、小于、小于等于；
- 日期区间、星期、时段；
- 门店、区域、渠道；
- SKU、SPU、类目、品牌、标签；
- 会员等级、会员标签；
- 数量、品类数、行数、金额；
- 首购、生日月等服务端已验证布尔事实。

条件树限制：

- 最大深度、节点数和列表项数量必须配置；
- 所有字符串比较采用明确大小写和 Unicode 规范化；
- 时间使用门店时区和冻结的 business_time；
- 不允许规则运行时进行任意外部网络调用。

# 六、计算流水线

## 6.1 固定步骤

1. 规范化输入并校验版本。
2. 解析商品、单位和税快照。
3. 选择每行基础价格。
4. 计算行毛额。
5. 评估 SPECIAL_PRICE、行级减额与折扣。
6. 评估 NTH_ITEM、BUY_X_GET_Y、BUNDLE_PRICE、数量阶梯。
7. 计算阶段净额。
8. 评估订单门槛优惠。
9. 评估优惠券与会员权益。
10. 评估手工折扣。
11. 执行互斥与最优解选择。
12. 把订单级优惠分摊到行。
13. 计算税、费用和应收舍入。
14. 校验所有不变量并输出解释树、快照和指纹。

步骤顺序是协议的一部分。任何调整必须提升 engine_version 并进行历史回放比较。

## 6.2 候选评估与稳定决胜

规则先按 priority 升序评估。对 BEST_OF_GROUP 的候选组合：

1. 选择顾客优惠金额最大的有效组合；
2. 优惠相同时选择业务 priority 总值更小的组合；
3. 再选择应用规则数量更少的组合；
4. 最后按规则 ID 拼接字符串 ASCII 升序。

引擎必须输出被排除候选及原因，例如 EXCLUSIVE_CONFLICT、THRESHOLD_NOT_MET、BUDGET_EXHAUSTED。

## 6.3 互斥与叠加

| stack_mode | 行为 |
|---|---|
| STACKABLE | 可与允许的规则继续叠加 |
| EXCLUSIVE | 应用后排除同 scope 的其他折扣 |
| BEST_OF_GROUP | 在同 exclusive_group 中选择最优 |
| STOP_AFTER_APPLY | 应用后停止指定阶段后续规则 |

每个规则还必须声明：

- can_stack_with_price_override；
- can_stack_with_coupon；
- can_stack_with_member_benefit；
- can_stack_with_manual_discount；
- applies_on_original_amount 或 applies_on_net_amount。

缺省为不叠加，避免配置遗漏造成过度优惠。

## 6.4 阶段基数

每个 Adjustment 保存：

- base_amount_minor；
- benefit_amount_minor；
- before_amount_minor；
- after_amount_minor；
- rule_id、campaign_id、stage；
- scope_line_ids；
- exclusivity_decision；
- budget_token；
- reason/explanation。

百分比折扣必须明确基于原价还是阶段净额。默认基于当前阶段净额。

# 七、常见规则算法

## 7.1 百分比折扣

discount = round(base_amount_minor × rate)

rate 使用 DECIMAL(12,8)，舍入模式默认 HALF_UP，具体由 currency_policy_version 决定。折后金额不得小于价格保护下限。

## 7.2 固定减额

- 优惠不超过当前适用基数。
- 订单固定减额按第九章分摊。
- 如果预算剩余小于规则优惠，默认整笔不应用；是否允许部分使用必须显式配置 partial_budget_allowed。

## 7.3 第 N 件折扣

同一商品组内的件序必须稳定：

1. 按可分割数量展开逻辑单位或使用等价数学算法。
2. 默认按成交单价升序选择优惠件，使顾客优惠可预测。
3. 单价相同时按 line_no、line_id 排序。
4. 称重商品默认不支持逐件第 N 件，除非配置重量步长。

## 7.4 买 X 赠 Y

- 购买组与赠送组必须显式定义。
- 自选赠品需在结算前固定赠品 SKU。
- 赠品以 GIFT adjustment 把净额降为 0，不删除商品行。
- 库存照常扣减，成本照常结转。
- 未领取赠品是否允许折现默认否。
- 赠品缺货的替代品、延期赠或取消优惠必须由活动策略明确。

## 7.5 组合价

- 引擎对候选商品按稳定顺序分组。
- 同一数量单位不能被两个组合重复消费，除非明确允许。
- 组合优惠 = 组成商品当前阶段金额之和 - bundle_price。
- 优惠按组合内各行阶段金额比例分摊。
- 大规模组合求解必须设置候选上限和超时，不得阻塞收银。

## 7.6 满额优惠

门槛基数必须声明：

- 原始标价总额；
- 基础价总额；
- 行级优惠后净额；
- 排除商品后的合格金额。

默认使用“行级和组合促销后的合格净额”，不含礼品卡充值、运费、已作为赠品的金额和法规禁止参加的商品。

# 八、优惠券、会员与预算

## 8.1 优惠券状态

| 状态 | 含义 |
|---|---|
| ISSUED | 已发放可用 |
| HELD | 为订单短时冻结 |
| REDEEMED | 订单成交后已核销 |
| RELEASED | 订单取消或冻结超时后释放 |
| EXPIRED | 已过期 |
| VOID | 作废 |

离线使用券必须有签名 coupon_token，包含：

- coupon_id、tenant_id、member_id；
- 适用范围和最大优惠；
- token_id、issued_at、expires_at；
- 可用次数与离线风险额度；
- 服务端签名。

同一 token_id 只能成功消费一次。多设备离线冲突按先到云端的有效成交占用，后到交易进入权益差异处置，但不得静默修改已收现金订单金额。

## 8.2 冻结与核销

- 订单进入 PENDING_PAYMENT 前可冻结券。
- 支付失败并重新编辑时释放或延长冻结。
- 订单 CONFIRMED 后核销。
- 支付 UNKNOWN 时不得提前释放。
- 订单取消必须释放。
- 退货是否返券取决于券策略和退货比例，结果写权益账本。

## 8.3 预算

促销预算包括：

- 总预算；
- 日预算；
- 门店预算；
- 会员或订单次数限制；
- 商品数量限制。

在线预算使用数据库原子占用或额度服务，必须带 budget_reservation_id。订单取消释放，确认后转为 consumed。离线促销只能使用已下发的签名预算令牌或不需要强预算的规则。

## 8.4 会员价和会员折扣

- 会员价属于价格候选。
- 会员折扣属于 Adjustment。
- 等级、标签和权益版本必须保存快照。
- 会员身份解绑或等级变化不改变历史订单。
- 匿名化后保留不可逆 member_ref_hash 与权益快照，以满足审计同时降低隐私暴露。

# 九、优惠分摊

## 9.1 分摊目标

分摊用于：

- 订单行净额；
- 部分退货的可退金额；
- 税、收入、成本和毛利报表；
- 品牌、供应商、加盟商或平台承担优惠；
- 连接器订单对账。

每个 adjustment 必须保存从优惠来源到订单行的分摊明细。

## 9.2 最大余数法

待分摊金额 D，合格行权重 w_i：

1. W = 所有 w_i 之和。
2. 原始份额 r_i = D × w_i ÷ W。
3. 基础份额 a_i = floor(r_i)。
4. 余数 R = D - 所有 a_i 之和。
5. 按 r_i - a_i 降序分配每次 1 个最小货币单位。
6. 小数余数相同按 line_no、line_id ASCII 升序。

必须保证：

- 所有 a_i 大于等于 0；
- a_i 不超过该行可分摊上限；
- 所有 a_i 之和等于 D；
- 输入顺序变化不改变结果。

## 9.3 权重

- 默认使用本阶段优惠前的合格行净额。
- 行净额为 0 的行权重为 0，除非规则明确使用数量权重。
- 赠品不参与其他订单优惠分摊。
- 固定价组合在组合内部先分摊，再参与后续订单级优惠。
- 禁止优惠的商品不进入权重集合。
- 某行达到折扣下限后，剩余优惠在其他合格行重新分配。

## 9.4 分摊记录

| 字段 | 说明 |
|---|---|
| allocation_id | ULID |
| adjustment_id | 优惠调整 |
| order_line_id | 订单行 |
| allocated_amount_minor | 分摊金额 |
| allocation_base_minor | 权重基数 |
| quantity_basis | 数量权重快照 |
| algorithm | LARGEST_REMAINDER_V1 等 |
| tie_breaker | 稳定决胜摘要 |
| sponsor_type/id | 承担方 |
| refundable | 是否参与退款 |

## 9.5 多承担方

平台、品牌、商户、供应商共同承担优惠时：

1. 先按合同确定 sponsor share。
2. 每个 sponsor 份额使用最大余数法保证总额一致。
3. 再把 sponsor 份额分摊至订单行。
4. sponsor 分摊总和、行分摊总和均等于 adjustment 总额。
5. 退货按原 sponsor allocation 反向回退。

# 十、应收舍入与税

## 10.1 舍入

商业 V1 CNY 默认：

- 电子支付精确到分，不抹零。
- 现金抹零由租户策略决定，作为 ROUNDING adjustment 单独保存。
- rounding_minor 可以正或负，但受绝对值上限控制。
- 找零基于舍入后的应收。
- 不得通过修改最后一行商品价格隐藏舍入。

## 10.2 税

- 含税价/未税价由租户税策略确定。
- 行税基必须使用优惠后的应税净额。
- 优惠是否影响销项税按税务策略分类。
- 税舍入可按行或按单，但 policy_version 必须固定。
- 税额分摊与调整保存独立明细。
- 跨地区、复杂税制不在商业 V1 国内单币种默认范围，但字段应预留。

# 十一、退货与优惠回退

## 11.1 基本原则

- 不重新运行当前促销。
- 使用原订单行的成交数量、行净额、allocation 和规则快照。
- 已退数量和已退优惠累计记账。
- 最后一次可退数量承接最小货币单位余数。
- 退款总额不超过原订单净支付可退余额。

## 11.2 行级回退

订单行原数量 Q、原行实付 N、已退累计 R，当前退货数量 q：

current_refund = floor(N × q ÷ Q) 或按原单位片段 allocation 计算；

当 q 等于最后剩余可退数量时：

current_refund = N - R。

精确算法由 return_allocation_algorithm 固化，不允许不同端各自实现不同舍入。

## 11.3 门槛优惠

默认采用“保留原订单优惠分摊”：

- 每次退货退回该行原实付净额；
- 不因退货后剩余商品不达门槛而重新追缴优惠；
- 若租户要求门槛重算，必须作为明确政策，生成 clawback adjustment 并在顾客确认前展示；
- 法规、行业和平台规则优先于租户配置。

商业 V1 推荐不追缴，减少争议并保持实现稳定。

## 11.4 买赠

策略必须在活动发布时选择：

| 策略 | 行为 |
|---|---|
| RETURN_GIFT_REQUIRED | 退购买品导致资格失效时必须退赠品 |
| DEDUCT_GIFT_VALUE | 未退赠品时从退款扣除其快照价值 |
| ALLOW_KEEP_GIFT | 允许保留，不追缴 |
| MANUAL_REVIEW | 进入主管审批 |

赠品价值使用原活动定义或成交快照，不使用当前零售价。

## 11.5 套装

- 整套退：按组合内原分摊金额回退。
- 部分退：按活动发布的 component_return_policy。
- 不允许部分退的套装必须在售前和小票清晰提示。
- 组合内优惠余数由最后可退组件承接。

## 11.6 优惠券返还

- 未使用完的多次券可按策略恢复次数。
- 单次券整单全退可返原券、发等值新券或不返，必须配置。
- 部分退默认不返券，只退原行净实付。
- 已过期券返还时可以延长短期有效期，但需要新 token 和审计。
- 外部平台券由连接器返回平台处置结果，不由本系统擅自发券。

# 十三、发布、灰度与回滚

## 13.1 规则生命周期

| 状态 | 含义 |
|---|---|
| DRAFT | 可编辑，不参与交易 |
| VALIDATING | 静态检查和样例回放 |
| APPROVED | 审批通过，等待发布 |
| SCHEDULED | 已计划生效 |
| ACTIVE | 正式生效 |
| PAUSED | 暂停新计算，历史不变 |
| ENDED | 正常结束 |
| REVOKED | 紧急撤回，需说明原因 |

ACTIVE 版本不可原地修改。调整规则必须创建新 revision 和 release_version。

## 13.2 发布门禁

必须检查：

- 生效时间和门店范围；
- 优惠上限、预算和次数；
- 互斥组完整；
- 价格下限和毛利风险；
- 规则复杂度；
- 离线兼容性；
- 样例和历史订单回放差异；
- 买赠库存；
- 退货政策；
- 审批人与发布人职责分离。

## 13.3 灰度

灰度可按：

- 租户测试环境；
- 门店白名单；
- 终端组；
- 会员稳定哈希比例；
- 指定渠道。

同一订单计算期间不得跨版本。灰度版本写入快照。

## 13.4 回滚

- 回滚是停止新订单使用该版本，不改变历史订单。
- 已下发离线包通过撤销清单和新版本替代。
- 严重规则错误可配置在线阻断和 POS 风险提示。
- 离线终端超过规则包有效期后，受影响规则自动不可用。

# 十六、性能、缓存与安全

## 16.1 性能目标

- 20 行普通 POS 订单本地计算 P95 小于 50 ms；
- 云端报价 P95 小于 150 ms，不含外部权益调用；
- 100 行复杂订单 P95 小于 500 ms；
- 规则包加载与原子切换不阻塞当前结算；
- 规则发布后目标门店 95% 在 5 分钟内收到新版本；
- 单次计算设置 CPU 时间、候选数和组合数上限。

## 16.2 缓存

- 按 tenant_id + store_id + release_version 缓存。
- 缓存键必须包含渠道、会员策略版本和币种策略。
- ACTIVE 版本不可变，采用版本指针切换而不是删除缓存。
- Redis 仅作缓存，不是规则事实源。
- POS 使用双槽规则包，校验后原子切换 active slot。

## 16.3 安全

- 规则 DSL 只允许白名单算子，不执行用户代码。
- 发布、暂停、撤销、预算变更均审计。
- 管理后台预览结果不能代替服务端发布校验。
- 敏感会员标签只参与服务端计算，终端下发最小必要派生事实。
- 券和离线预算令牌使用非对称签名并支持密钥轮换。
- 防止通过重复试算探测他人会员权益，报价接口需限频与授权。

# 十七、验收测试

## 17.1 黄金样例

每个规则类型至少覆盖：

- 边界数量和金额；
- 门槛刚好达到与差 1 分；
- 时间边界和跨午夜；
- 同级规则决胜；
- 互斥和叠加；
- 预算不足；
- 券冻结、核销、释放；
- 价格下限；
- 称重数量；
- 离线包过期。

黄金样例必须由 Java 服务端与 Dart 引擎读取同一 JSON，逐字段比较。

## 17.2 属性测试

自动生成订单验证：

- 应收永不为负；
- 优惠不超过适用基数；
- 所有分摊精确守恒；
- 行顺序变化不改变语义结果；
- 同一输入和版本重放完全一致；
- 任何组合不突破价格保护和预算令牌；
- 多次部分退货累计金额等于整行全退金额；
- sponsor 分摊与 adjustment 分摊双重守恒；
- 不使用 float、double 或 JavaScript Number 最终计算。

## 17.3 差分测试

- Java 参考实现与 Dart 实现差分；
- 新 engine_version 与旧版本历史订单回放；
- 在线与离线同输入差分；
- 发布前规则与生产影子计算差分；
- 第三方连接器报价与平台标准契约差分。

## 17.4 故障场景

1. 预算占用成功但订单提交失败。
2. 券冻结后 POS 断网。
3. 订单支付 UNKNOWN 导致券长时间冻结。
4. 新规则包下载中途损坏。
5. 终端时钟漂移一天。
6. 同一券在两台离线 POS 使用。
7. 活动紧急撤销但部分门店离线。
8. 组合求解超过时间预算。
9. 最后 1 分分摊在多行竞争。
10. 退货跨越多次部分退和赠品策略。

# 十九、商业 V1 决策摘要

1. 使用白名单、版本化、确定性的促销 DSL，不运行租户自定义代码。
2. Java 与 Dart 实现必须通过同一黄金样例和差分测试。
3. 价格候选、促销调整、税与舍入分层保存。
4. 互斥、叠加和稳定决胜顺序是冻结协议。
5. 订单级优惠采用最大余数法分摊，保证最小货币单位守恒。
6. 退货使用原成交 allocation，不按当前活动重新计算。
7. 优惠券和预算采用冻结、核销、释放账本；离线必须使用签名令牌。
8. ACTIVE 规则不可原地修改，以新版本发布和版本指针回滚。
9. 促销结果必须可解释、可指纹核验、可历史回放。
10. 商业 V1 默认不追缴退货后门槛优惠，买赠和套装按活动策略处理。

本规范批准后，计算步骤、规则代码、叠加语义、舍入方式、分摊算法、快照结构和退货回退口径成为商业 V1 冻结契约；任何改变必须提升引擎或契约版本并通过跨端差分验收。
