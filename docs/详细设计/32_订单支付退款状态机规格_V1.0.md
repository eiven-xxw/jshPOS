# 文档说明

## 1. 编写目的

本文定义销售订单、支付、支付尝试、退款、退货与订单履约之间的状态、命令、事件、守卫条件、幂等规则、事务边界、异常恢复和验收标准。目标不是描述页面按钮，而是给后端、Flutter POS、连接器、测试、财务与实施团队一套不可歧义的交易语义。

本规范解决以下商业风险：

- 同一笔支付因超时重试而重复扣款；
- 支付已成功但订单仍显示未支付，或者订单已完成但库存未扣；
- 退款已受理但原订单、支付净额、库存和优惠回退口径不一致；
- 离线现金订单回传后重复入账；
- 第三方回调乱序、重复或缺失导致状态倒退；
- 店员通过取消、改价或退货绕过审批和审计；
- 报表直接按页面状态统计，导致营业额、实收、退款和净销口径不稳定。

## 2. 规范级别

| 级别 | 含义 |
|---|---|
| 必须 | 资金、订单事实、审计和幂等底线，不得通过配置关闭 |
| 应当 | 商业 V1 默认实现；例外需要 ADR、风险评估和回归用例 |
| 可以 | 按行业、支付渠道、租户套餐或交付阶段启用 |

## 3. 术语

| 术语 | 定义 |
|---|---|
| 销售订单 | 对商品、数量、价格、优惠、税、应收和交易主体的不可变成交快照 |
| 支付 | 针对订单应收发起的一项资金履约意图，可包含多次渠道尝试 |
| 支付尝试 | 一次具体渠道请求，例如一次扫码付被扫、一次聚合支付下单 |
| 退款 | 针对一笔或多笔成功支付发起的资金返还指令 |
| 退货单 | 针对原订单行发起的商品、库存和优惠回退业务单据 |
| 未知态 | 请求结果暂时无法确认，不等于失败，也不允许盲目重新扣款 |
| 冲正 | 针对异常资金或账务事实创建反向记录，不覆盖原记录 |
| 净支付额 | 成功支付金额减成功退款金额 |
| 命令 ID | 一次业务意图的全局唯一 ULID，用于幂等和审计 |
| 聚合版本 | record_version，状态每次成功迁移递增，用于乐观并发控制 |

## 4. 上下游关系

- 数据类型、tenant_id、ULID、金额、时间、Outbox 与表命名遵循 POS-DD-031。
- 优惠金额和退货优惠回退遵循 POS-DD-034。
- 销售出库、退货入库、预占消耗遵循 POS-DD-033。
- 离线本地提交、回传和冲突处理遵循 POS-DD-035。
- 渠道请求与回调适配通过 POS-DD-037 的标准支付数据契约实现。

# 一、总体设计原则

## 1.1 正交状态，不使用一个万能状态

订单必须至少保存以下互相独立的维度：

| 维度 | 字段 | 说明 |
|---|---|---|
| 业务生命周期 | order_status | 草稿、待收款、已确认、已完成、已取消、已关闭 |
| 支付进度 | payment_status | 未支付、部分支付、已支付、部分退款、已退款 |
| 履约进度 | fulfillment_status | 无需履约、待履约、处理中、已完成、已取消 |
| 退货退款摘要 | refund_status | 无、处理中、部分完成、全部完成 |
| 同步进度 | sync_status | 仅用于终端/云端数据同步，不改变交易事实 |
| 风险状态 | risk_status | 正常、待复核、阻断；不得复用订单状态表达 |

支付、退款和库存分别拥有自己的状态机。订单只消费其他领域发布的权威事件，任何模块不得越权直接修改对方状态字段。

## 1.2 单向状态与显式补偿

- 状态只能沿本规范允许的边迁移，不得根据界面需要任意回退。
- 已成功、已完成的资金事实不得改回失败或删除。
- 发生误操作时创建退款、冲正、差异调整或作废记录。
- 第三方状态与内部状态分开保存；内部状态由渠道事件映射后迁移。
- 未知态必须通过查询、回调或人工对账消解，不得自动视为失败。

## 1.3 金额与数量不变量

- 所有结算金额使用 BIGINT 最小货币单位，字段以 _minor 结尾。
- 单价中间值使用 DECIMAL(19,6)，数量使用 DECIMAL(19,6)。
- order.payable_amount_minor 不得小于 0。
- 所有成功支付金额之和减成功退款金额之和，等于订单净支付额。
- 成功退款累计不得超过对应支付的 refundable_amount_minor。
- 订单行可退数量不得超过成交数量减已成功退货数量。
- 任何金额比较必须在同一 currency 下进行；商业 V1 订单仅允许一种结算币种。

## 1.4 标识与幂等

- 订单、支付、退款、尝试、命令、事件均使用 ULID，数据库类型 CHAR(26)。
- tenant_id 必须是 VARCHAR(20)，从认证上下文取得，并与消息体值交叉校验。
- 同一业务意图必须复用同一个 command_id 和 idempotency_key。
- 对已处理的相同键、相同请求摘要返回原结果；相同键但请求摘要不同，返回 IDEMPOTENCY_KEY_REUSED 并触发安全告警。
- 外部渠道单号只用于映射，不作为内部主键。

# 二、销售订单状态机

## 2.1 订单状态代码

| 状态 | 是否终态 | 含义 |
|---|---:|---|
| DRAFT | 否 | 本地或云端购物车，可修改商品、数量、会员和促销 |
| PENDING_PAYMENT | 否 | 订单快照已冻结，等待收款；普通店员不得再改行项目 |
| CONFIRMED | 否 | 应收已由允许的支付事实覆盖，订单成交事实已确认 |
| COMPLETED | 是 | 所有必需后置任务已创建，订单进入正常完结态 |
| CANCELLED | 是 | 成交前取消；不得产生销售收入 |
| CLOSED | 是 | 异常、超时或管理关闭，保留原因和处置记录 |

说明：

- CONFIRMED 是跨领域编排检查点，不等于页面展示“支付成功”。
- COMPLETED 表示订单已生成销售出库命令、票据任务与领域事件；异步消费者尚未处理完成不回退订单。
- 已确认订单不得取消，只能通过退货退款流程反向处理。

## 2.2 支付摘要状态

| 状态 | 判定 |
|---|---|
| UNPAID | 成功支付为 0，成功退款为 0 |
| PARTIALLY_PAID | 0 小于净支付额且小于订单应付 |
| PAID | 净支付额大于等于订单应付，且未发生成功退款 |
| PARTIALLY_REFUNDED | 已有成功退款，累计退款小于累计成功支付 |
| REFUNDED | 累计成功退款等于可退支付金额，订单净支付额为 0 |

payment_status 是订单聚合保存的可校验摘要，不是支付领域事实源。更新必须由 payment.succeeded.v1、refund.succeeded.v1 等权威事件驱动，并定期与支付账本对账。

## 2.3 退货退款摘要状态

| 状态 | 含义 |
|---|---|
| NONE | 未创建有效退货退款 |
| PROCESSING | 存在审批中、渠道处理中或未知态退款 |
| PARTIAL | 原订单只有部分数量或金额成功退回 |
| FULL | 原订单全部可退数量和资金已完成回退 |

## 2.4 订单迁移矩阵

| 当前状态 | 命令 | 目标状态 | 守卫条件 | 权威事件 |
|---|---|---|---|---|
| 不存在 | CreateOrder | DRAFT | 设备、门店、班次有效；command_id 未使用 | order.created.v1 |
| DRAFT | AddOrUpdateOrderLine | DRAFT | 商品可售；数量与价格精度合法 | order.line_changed.v1 |
| DRAFT | ApplyPromotionSnapshot | DRAFT | 规则版本可用；计算签名有效 | order.priced.v1 |
| DRAFT | SubmitOrderForPayment | PENDING_PAYMENT | 至少一行；应收非负；快照完整 | order.submitted.v1 |
| DRAFT | CancelOrder | CANCELLED | 无成功支付；无有效库存出库 | order.cancelled.v1 |
| PENDING_PAYMENT | RecordPaymentSucceeded | PENDING_PAYMENT 或 CONFIRMED | 支付事件幂等；净支付重新计算 | order.payment_applied.v1 |
| PENDING_PAYMENT | ConfirmZeroPayableOrder | CONFIRMED | 应付为 0；优惠规则允许零元单 | order.confirmed.v1 |
| PENDING_PAYMENT | CancelOrder | CANCELLED | 无成功支付，未知态支付已消解 | order.cancelled.v1 |
| CONFIRMED | CompleteOrder | COMPLETED | 已创建销售出库命令、票据任务和 Outbox | order.completed.v1 |
| PENDING_PAYMENT | CloseOrder | CLOSED | 超时或异常审批；不存在未决扣款 | order.closed.v1 |
| 任一非终态 | ForceCloseOrder | CLOSED | 管理员双人复核；生成处置任务 | order.closed.v1 |

禁止迁移：

- COMPLETED、CANCELLED、CLOSED 不得回到 DRAFT。
- PENDING_PAYMENT 存在 PROCESSING 或 UNKNOWN 的电子支付尝试时不得取消。
- CONFIRMED 不得通过 CancelOrder 撤销。
- 订单不能因支付退款而从 COMPLETED 回退；退款状态通过 payment_status 与 refund_status 表达。

## 2.5 订单提交冻结点

SubmitOrderForPayment 成功时必须在一个本地数据库事务中：

1. 校验 record_version。
2. 重新执行服务端或本地已签名规则包的价格校验。
3. 固化商品、单位、税、价格、优惠、会员、销售员、来源渠道、门店、终端和业务日快照。
4. 写入 DRAFT 到 PENDING_PAYMENT 状态历史。
5. 生成 order.submitted.v1 Outbox。
6. 递增 record_version。

进入 PENDING_PAYMENT 后，如需改商品或优惠，必须执行 ReopenOrderForEdit：

- 仅在无成功支付、无处理中或未知态支付时允许；
- 释放已冻结优惠券和库存预占；
- 创建新的 pricing_revision；
- 返回 DRAFT，并记录原因；
- 不复用已创建的电子支付尝试。

## 2.6 零元单

零元单不得伪造一笔 0 元支付。满足下列条件后可直接 CONFIRMED：

- 优惠分摊后 payable_amount_minor 等于 0；
- 促销快照通过签名和版本校验；
- 租户启用零元单权限；
- 不存在储值、积分等需要资金账本确认的抵扣；
- 输出 order.zero_payable_confirmed.v1 审计事件。

## 2.7 拆单、并单与挂单

- DRAFT 可以挂单，挂单仅保存草稿，不占用永久优惠预算。
- 并单必须创建新 DRAFT，并在 lineage 表记录源订单；不得直接拼接两个已提交订单。
- 拆单必须按行与数量创建新订单，并重新计算促销；如业务要求保留原优惠，必须保存显式 transfer_adjustment。
- 已产生支付的订单不允许并单或拆单。
- 堂食桌台转台、并台属于履约关系变更，不得修改订单成交金额。

# 三、支付状态机

## 3.1 支付聚合状态

| 状态 | 是否终态 | 含义 |
|---|---:|---|
| CREATED | 否 | 支付意图已创建，尚未向渠道提交 |
| PROCESSING | 否 | 已向渠道发送或等待顾客操作 |
| UNKNOWN | 否 | 超时、断网或回调不确定，最终结果未知 |
| SUCCEEDED | 否 | 渠道或现金权威确认成功，可继续发生退款 |
| FAILED | 是 | 权威确认失败，未产生成功扣款 |
| CANCELLED | 是 | 支付意图在确认未扣款后取消 |
| CLOSED | 是 | 经查询、对账或人工处置关闭，不再重试扣款 |
| PARTIALLY_REFUNDED | 否 | 成功支付已部分退款 |
| REFUNDED | 是 | 成功支付可退金额已全部退回 |

SUCCEEDED 不是绝对终态，因为其后允许退款；但成功扣款事实不可撤销或覆盖。

## 3.2 支付尝试状态

| 状态 | 含义 |
|---|---|
| CREATED | 本地尝试记录已创建 |
| SENT | 请求已发出，尚未收到渠道受理 |
| ACCEPTED | 渠道已受理或等待用户完成 |
| CONFIRMED | 渠道确认支付成功 |
| FAILED | 渠道确认失败 |
| TIMED_OUT | 请求超时，必须转 UNKNOWN 流程 |
| UNKNOWN | 状态无法确认，等待主动查询或回调 |
| CANCELLED | 渠道确认撤销或关闭 |

支付聚合可以有多次尝试，但同一时刻只允许一个可能扣款的活动尝试。新尝试前必须确认旧尝试为 FAILED、CANCELLED 或 CLOSED。

## 3.3 支付迁移矩阵

| 当前状态 | 命令/输入 | 目标状态 | 守卫条件 | 事件 |
|---|---|---|---|---|
| 不存在 | CreatePayment | CREATED | 金额大于 0；订单可支付；幂等键唯一 | payment.created.v1 |
| CREATED | StartPayment | PROCESSING | 渠道可用；无活动尝试 | payment.processing.v1 |
| CREATED | RecordCashPayment | SUCCEEDED | 现金权限、班次开启、金额合法 | payment.succeeded.v1 |
| PROCESSING | ChannelSuccess | SUCCEEDED | 签名和金额校验通过 | payment.succeeded.v1 |
| PROCESSING | ChannelFailure | FAILED | 渠道明确失败 | payment.failed.v1 |
| PROCESSING | TimeoutOrDisconnect | UNKNOWN | 未取得权威失败结果 | payment.unknown.v1 |
| UNKNOWN | QuerySuccess/CallbackSuccess | SUCCEEDED | 渠道单号、金额、商户校验通过 | payment.succeeded.v1 |
| UNKNOWN | QueryFailure | FAILED | 渠道明确不存在或失败 | payment.failed.v1 |
| UNKNOWN | ManualReconciliationClose | CLOSED | 双人复核、证据附件、差异任务 | payment.closed.v1 |
| CREATED | CancelPayment | CANCELLED | 未发出渠道请求 | payment.cancelled.v1 |
| PROCESSING | CancelConfirmed | CANCELLED | 渠道确认关闭且未扣款 | payment.cancelled.v1 |
| SUCCEEDED | RefundSucceededPartial | PARTIALLY_REFUNDED | 成功退款累计小于可退额 | payment.refund_applied.v1 |
| SUCCEEDED/PARTIALLY_REFUNDED | RefundSucceededFull | REFUNDED | 成功退款累计等于可退额 | payment.refunded.v1 |

## 3.4 支付创建约束

CreatePayment 必须校验：

- tenant_id、store_id、order_id 与当前授权上下文一致；
- 订单处于 PENDING_PAYMENT；
- payment_amount_minor 大于 0 且不超过剩余应收，除非是允许找零的现金支付；
- currency 与订单一致；
- tender_type、channel_code 和 terminal_id 有效；
- 相同订单、相同 idempotency_key 不得创建第二笔支付；
- 电子支付请求必须携带不可变 channel_request_no；
- 现金支付必须绑定已开启班次。

## 3.5 混合支付

- 每一种支付方式创建独立 Payment 聚合。
- 订单 remaining_payable_minor 等于 payable_amount_minor 减成功支付总额。
- 电子支付默认禁止超额；现金可以按配置收取大于剩余应收的 tendered_amount_minor，并单独记录 change_amount_minor。
- 任意一笔支付为 UNKNOWN 时，POS 必须锁定“再次发起同额电子支付”，只能查询、撤销或由授权人员进入异常处置。
- 最后一笔支付成功使净支付覆盖应收后，订单才可 CONFIRMED。
- 混合支付退款必须明确退款到原支付媒介；不允许默认把电子支付退为现金。

## 3.6 现金支付

现金支付不调用外部渠道，但仍必须创建 Payment 和现金流水：

- Payment 从 CREATED 原子迁移到 SUCCEEDED；
- 写入 shf_cash_movement，类型为 SALE_RECEIPT；
- 收款、找零分别保存，不以实收减找零的单字段替代；
- 打印失败不回滚现金成功事实；
- 现金抽屉打开命令失败记录设备事件，不自动撤销订单；
- 退现金时写 REFUND_PAYOUT 现金流水并受班次余额与权限控制。

## 3.7 电子支付未知态处理

出现以下任一情况必须进入 UNKNOWN：

- HTTP、SDK 或设备调用超时；
- POS 断网或进程终止，无法确认结果；
- 渠道返回“处理中”；
- 回调签名通过但金额、商户或订单映射暂不一致；
- 撤销请求无权威确认。

处置顺序：

1. 使用原 channel_request_no 主动查询。
2. 接收并幂等处理渠道回调。
3. 按 5 秒、15 秒、30 秒、1 分钟、5 分钟退避查询，具体受渠道限频约束。
4. 超过渠道 SLA 后进入对账待处理队列，订单保持不可再次电子扣款。
5. 只有渠道明确失败/不存在，或人工依据渠道后台证据关闭后，才允许新支付。

“超时即失败”属于严重缺陷，商业 V1 验收必须拦截。

## 3.8 回调与查询合并

- 回调、主动查询和同步补偿统一转换为 ChannelPaymentObserved 命令。
- 以 tenant_id + channel_code + channel_trade_no 建立唯一约束。
- 同一渠道事件重复到达返回成功，不重复生成业务事件。
- SUCCEEDED 后到达 FAILED 不得状态倒退，只记录矛盾事件并告警。
- FAILED 后到达可验证的 SUCCEEDED，允许提升为 SUCCEEDED，但必须记录 late_success 风险标记并通知订单编排。
- 金额、币种或商户不匹配时进入 QUARANTINED 渠道事件队列，不改变支付状态。

# 四、退款与退货状态机

## 4.1 退款状态

| 状态 | 是否终态 | 含义 |
|---|---:|---|
| CREATED | 否 | 已创建退款草案并冻结可退额度 |
| PENDING_APPROVAL | 否 | 等待授权审批 |
| PROCESSING | 否 | 已向渠道提交或正在执行现金退款 |
| UNKNOWN | 否 | 退款结果不确定，需要查询或对账 |
| SUCCEEDED | 是 | 渠道或现金账本确认退款成功 |
| FAILED | 是 | 权威确认失败，释放可退额度 |
| CANCELLED | 是 | 提交渠道前取消 |
| CLOSED | 是 | 异常处置后关闭，保留原因 |

## 4.2 退货业务状态

| 状态 | 含义 |
|---|---|
| DRAFT | 选择原订单行、退货数量、原因和处理方式 |
| PENDING_APPROVAL | 触发金额、时限、无票或敏感商品审批 |
| APPROVED | 审批通过，冻结可退数量和金额 |
| REFUND_PROCESSING | 退款执行中或未知 |
| COMPLETED | 资金与库存处理指令均已建立，退货业务完成 |
| REJECTED | 审批拒绝 |
| CANCELLED | 执行前取消 |
| EXCEPTION | 资金、库存或凭证存在需人工处置的差异 |

退货单与退款单不是同一对象：一张退货单可按原支付方式拆成多张退款单；纯差价退款可以没有实物入库；仅换货可产生退货与新销售而不产生净退款。

## 4.3 退款迁移矩阵

| 当前状态 | 命令/输入 | 目标状态 | 守卫条件 | 事件 |
|---|---|---|---|---|
| 不存在 | CreateRefund | CREATED/PENDING_APPROVAL | 原支付成功；金额和数量可退 | refund.created.v1 |
| CREATED | SubmitForApproval | PENDING_APPROVAL | 命中审批策略 | refund.approval_requested.v1 |
| PENDING_APPROVAL | ApproveRefund | CREATED | 审批人与收银员满足职责分离 | refund.approved.v1 |
| CREATED | ExecuteRefund | PROCESSING | 可退额度冻结成功；渠道参数完整 | refund.processing.v1 |
| PROCESSING | ChannelRefundSuccess | SUCCEEDED | 金额、原交易、币种校验通过 | refund.succeeded.v1 |
| PROCESSING | ChannelRefundFailure | FAILED | 渠道明确失败 | refund.failed.v1 |
| PROCESSING | TimeoutOrDisconnect | UNKNOWN | 最终结果不确定 | refund.unknown.v1 |
| UNKNOWN | QueryRefundSuccess | SUCCEEDED | 权威查询成功 | refund.succeeded.v1 |
| UNKNOWN | QueryRefundFailure | FAILED | 渠道明确失败/不存在 | refund.failed.v1 |
| CREATED/PENDING_APPROVAL | CancelRefund | CANCELLED | 未向渠道发送 | refund.cancelled.v1 |
| UNKNOWN | ManualCloseRefund | CLOSED | 双人复核和对账证据 | refund.closed.v1 |

## 4.4 可退额度

每笔成功支付保存：

- paid_amount_minor；
- succeeded_refund_amount_minor；
- pending_refund_amount_minor；
- refundable_amount_minor。

约束：

refundable_amount_minor = paid_amount_minor - succeeded_refund_amount_minor - pending_refund_amount_minor

创建退款时在数据库事务内原子增加 pending_refund_amount_minor；成功后从 pending 转为 succeeded；失败、取消或合规关闭后释放 pending。任何时点都不得出现负数。

## 4.5 退货数量与优惠回退

- 可退数量按原订单行、原单位精度和累计成功退货数量校验。
- 金额使用原订单的 promotion_snapshot 与 allocation 明细，不按当前售价或当前活动重算。
- 多次部分退货使用累计分摊算法；最后一次可退数量承接舍入余数。
- 赠品、套装、买赠和门槛优惠按 POS-DD-034 的回退策略计算。
- 已核销券的恢复由权益领域处理；不能恢复时必须生成不可恢复原因与补偿策略。
- 退款成功后才能确认资金回退；库存是否入库由商品状态、退货原因和质检结果决定，二者不得互相伪造成功。

## 4.6 无原单退款

商业 V1 默认禁止无原单电子退款。允许无原单退货时必须：

- 使用独立权限和审批流；
- 设置单笔、单日、员工与门店限额；
- 记录顾客身份的最小必要信息；
- 退款方式默认门店储值或现金，具体受法规和租户政策约束；
- 以当前可验证价格创建估值快照，不伪造原订单；
- 标记 NO_ORIGINAL_RECEIPT 并进入风险报表；
- 高风险商品、礼品卡、预付卡和虚拟权益默认禁止。

## 4.7 换货

换货实现为“原单退货 + 新销售订单”，通过 exchange_group_id 关联：

- 原订单优惠回退保持原规则；
- 新订单按换货时价格策略计算；
- 差额通过新支付或退款处理；
- 库存分别产生 SALE_RETURN_IN 和 SALE_OUT；
- 不允许直接修改原订单行数量或金额。

## 5.4 事件处理规则

- 生产者在聚合事务内写业务表、状态历史和 sync_outbox。

- 消费者不得依赖全局事件到达顺序，只能依赖同一聚合 aggregate_version。
- 收到更高版本但缺少前序版本时进入 gap 队列并拉取聚合快照。

# 六、事务边界与编排

## 6.1 本地事务

每个聚合命令在一个数据库事务中完成：

1. 幂等记录占位或读取。
2. SELECT FOR UPDATE 或 record_version 条件更新。
3. 校验当前状态和守卫条件。
4. 写聚合、明细、状态历史和业务流水。
5. 写 Outbox。
6. 固化命令结果摘要。
7. 提交后异步投递。

不允许在持有数据库锁期间调用支付渠道、打印机或连接器。

## 6.2 收银成功编排

标准 POS 销售流程：

1. 订单提交为 PENDING_PAYMENT。
2. 支付领域创建并执行 Payment。
3. payment.succeeded.v1 到达订单模块。
4. 订单重新计算净支付额；达到应收后迁移为 CONFIRMED。
5. 订单事务内写 order.confirmed.v1，并创建库存扣减命令和票据任务。
6. 库存模块幂等处理 SALE_OUT，打印模块独立重试。
7. 订单完成必要任务创建后迁移为 COMPLETED。

库存扣减业务失败时：

- 订单成交与支付事实不得回滚；
- 库存命令进入 EXCEPTION，按负库存策略或人工差异处理；
- 不得自动发起退款，除非明确配置并通过业务编排审批。

## 6.3 退款编排

1. 退货单冻结可退数量和优惠分摊额度。
2. 退款单冻结原支付可退额度。
3. 渠道执行成功，发布 refund.succeeded.v1。
4. 支付聚合累计退款并更新 PARTIALLY_REFUNDED/REFUNDED。
5. 订单更新 payment_status 与 refund_status 摘要。
6. 退货领域按处置结果发送 SALE_RETURN_IN、DAMAGE_OUT 或不入库命令。
7. 权益领域处理积分、券与储值回退。
8. 任一异步步骤失败进入补偿队列，不撤销已成功资金事实。

# 七、并发、幂等与数据库约束

## 7.1 乐观锁

核心更新必须形如：

~~~sql
UPDATE pay_payment
SET status = :next_status,
    record_version = record_version + 1,
    updated_at = UTC_TIMESTAMP(3)
WHERE tenant_id = :tenant_id
  AND id = :payment_id
  AND status = :current_status
  AND record_version = :expected_version;
~~~

影响行数为 0 时重新读取：

- 已达到相同目标且命令已处理，返回原结果；
- 状态已被其他命令合法推进，返回 STATE_CONFLICT；
- 聚合不存在或租户不匹配，统一返回资源不可见。

## 7.2 唯一约束

至少建立：

- ord_order：tenant_id + order_no；
- ord_order：tenant_id + device_id + local_order_no；
- pay_payment：tenant_id + idempotency_key；
- pay_payment_attempt：tenant_id + channel_code + channel_request_no；
- pay_channel_event：tenant_id + channel_code + channel_event_id；
- pay_refund：tenant_id + idempotency_key；
- pay_refund：tenant_id + channel_code + channel_refund_no；
- inbox：tenant_id + consumer_name + event_id。

## 7.3 防重结果保存

幂等记录保存：

- command_id；
- idempotency_key；
- request_hash；
- aggregate_id；
- response_code；
- response_body 的最小安全快照；
- first_seen_at、last_seen_at、expires_at；
- actor、device_id、trace_id。

支付与退款幂等记录保留期不得短于财务对账和争议期。

## 8.1 权限动作

| 动作 | 默认角色 | 额外控制 |

# 十、离线与弱网规则

## 10.1 离线能力矩阵

| 操作 | 默认策略 |
|---|---|
| 现金销售 | 允许，使用本地 ULID、规则包和事务 Outbox |
| 现金退货 | 默认禁止；可按租户额度、原单本地可验证和主管授权开放 |
| 电子支付 | 默认禁止离线发起 |
| 已发起电子支付断网 | 进入 UNKNOWN，只允许查询与恢复 |
| 挂单 | 允许，本地保存，不作为成交 |
| 零元单 | 规则包有效且未过期时可以 |
| 储值、积分抵扣 | 默认禁止离线，除非有签名额度令牌和风险预算 |
| 无原单退款 | 离线禁止 |

## 10.2 本地原子提交

离线现金成交必须在 SQLite 一个事务内写入：

- 订单、订单行、成交快照；
- 现金 Payment 成功记录；
- 班次现金流水；
- 本地库存变更或待执行命令；
- 打印任务；
- Outbox 事件；
- 本地幂等结果。

任何一项失败均回滚本地事务。打印机硬件执行在事务提交后进行。

## 10.3 回传处理

- 云端保留客户端生成的 order_id、payment_id 和 event_id。
- 相同 event_id 与 payload_hash 重复回传返回 DUPLICATE。
- 相同 event_id 但 payload_hash 不同，拒绝并冻结设备同步。
- 云端按服务端规则进行结构、租户、设备、金额和规则包版本复核。
- 商业允许但发生主数据冲突的订单仍作为历史成交接收，并标记 DATA_REVIEW，不擅自改价。
- 云端不得为“修正数据”重新生成第二笔订单。

# 十一、对账与异常处置

## 11.1 三方对账

每日按 tenant_id、store_id、channel_code、business_date 对比：

- 内部成功支付与退款账本；
- 渠道账单与手续费；
- 订单应收和净支付摘要。

差异类型至少包括：

- 内部成功、渠道缺失；
- 渠道成功、内部缺失；
- 金额或币种不一致；
- 重复渠道单号；
- 未知态超 SLA；
- 退款成功但支付累计未更新；
- 订单支付摘要与支付账本不一致。

## 11.2 异常修复

- 优先补录权威渠道事件并重放消费者。
- 不直接 UPDATE 成功金额或状态。
- 必须通过 ReconcilePayment、RecordExternalSuccess、CreateAdjustment 等受控命令。
- 修复命令保存证据、审批人和前后差异。
- 修复后自动重跑订单、支付、退款和报表对账。

# 十三、验收测试

## 13.1 状态机覆盖

每条合法迁移至少覆盖：

- 正常成功；
- 重复命令；
- 旧 record_version；
- 非法当前状态；
- 权限不足；
- 同租户并发；
- 跨租户访问；
- Outbox 投递失败后重试。

每条禁止迁移必须有负向用例。

## 13.2 资金故障注入

必须覆盖：

1. 渠道请求已扣款但 POS 超时。
2. 回调先于同步响应到达。
3. 成功回调重复 100 次。
4. FAILED 后收到可验证的晚到 SUCCESS。
5. SUCCESS 后收到 FAILED。
6. 退款超时后查询成功。
7. 进程在渠道返回后、数据库提交前崩溃。
8. 数据库提交后、响应终端前崩溃。
9. Outbox 已写但消息中间件不可用。
10. 同一幂等键以不同金额重复请求。
11. 两个终端并发退同一订单行。
12. 支付和取消命令并发到达。

## 13.3 属性不变量

自动化属性测试至少验证：

- 任意合法事件序列不会产生负应收、负可退金额或超退数量；
- 成功支付事实不会被后续失败事件覆盖；
- 同一命令重放 N 次只产生一次资金与业务效果；
- 所有订单净支付摘要可由支付和退款账本重算；
- 所有终态都有状态历史、命令 ID 和 Outbox；
- tenant_id 不会因客户端输入改变；
- 金额链路不存在 float、double 或 JavaScript Number 最终计算。

# 十四、研发交付清单

## 14.1 后端

- Order、Payment、PaymentAttempt、Refund、Return 聚合和仓储；
- 显式状态迁移器与守卫，不使用任意字符串更新；
- 幂等服务、Outbox/Inbox、渠道事件隔离区；
- 查询/回调合并、未知态调度和对账命令；
- 审批、权限、审计和异常处置 API；
- 状态机单元、集成、并发与故障注入测试。

## 14.2 Flutter POS

- 依据服务端能力矩阵控制按钮，而不是自行推断可操作状态；
- 对 UNKNOWN 使用明确页面和恢复入口；
- command_id、idempotency_key 在业务意图未改变时持久化复用；
- 防重复点击只能改善体验，不能替代服务端幂等；
- 离线现金成交使用 SQLite 原子事务和 Outbox；
- 不展示“支付失败”直到取得权威失败结果。

## 14.3 运维与财务

- 未知支付、未知退款和差异对账工作台；
- P0/P1 告警、渠道健康度和积压监控；
- 日结、班结与渠道账单的统一口径；
- 人工处置 SOP、双人复核和证据保留策略。

# 十五、商业 V1 决策摘要

1. 订单、支付、退款采用独立聚合与正交状态，禁止万能状态。
2. 电子支付超时进入 UNKNOWN，禁止把超时当失败后直接重新扣款。
3. 支付、退款、回调、同步均必须端到端幂等。
4. 订单成交后不得删除或改回草稿，只能以退货、退款、冲正或调整表达。
5. 优惠和退货金额使用成交快照与原始分摊，不按当前促销重算。
6. 离线商业 V1 默认仅支持现金销售、挂单和受控零元单。
7. 状态、流水、历史、Outbox 与审计必须在同一聚合事务中提交。
8. 所有摘要状态都必须能由权威账本重算并通过日常对账验证。

本规范批准后，状态代码、事件名称、金额语义、幂等键和未知态处置成为商业 V1 冻结接口；变更必须通过 ADR、数据迁移、兼容性评估与回归验收。
