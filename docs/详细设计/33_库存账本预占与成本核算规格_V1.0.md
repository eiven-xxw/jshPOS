# 文档说明

## 1. 编写目的

本文定义库存数量事实、余额投影、库存预占、销售扣减、退货入库、采购收货、调拨、盘点、批次效期和移动加权成本的统一规则。它是库存服务、POS 本地库存、订货、连接器、财务成本和经营报表的实现与验收基线。

核心目标：

- 任一库存余额可以从不可变流水重放或核验；
- 同一业务指令重试不会重复扣减或重复入库；
- 库存预占与实物库存分开，能正确释放、消耗和过期；
- 销售成本、退货成本和调拨成本有稳定、可审计口径；
- 弱网、离线、多终端并发和渠道订单不会造成静默覆盖；
- 盘点、负库存与人工调整都形成清晰责任链。

## 2. 规范级别

| 级别 | 含义 |
|---|---|
| 必须 | 数量、成本、租户隔离、幂等和审计底线 |
| 应当 | 商业 V1 的默认工程实现 |
| 可以 | 适用于生鲜、医药、批次、序列号或大型客户的扩展 |

## 3. 依赖关系

- tenant_id 使用 VARCHAR(20)，聚合与事件使用 ULID CHAR(26)。
- 数量使用 DECIMAL(19,6)，单位成本使用 DECIMAL(19,6)，结算金额使用 BIGINT 最小货币单位。
- 销售、退货与退款业务状态遵循 POS-DD-032。
- 离线命令与同步冲突遵循 POS-DD-035。
- 优惠只影响成交净额，不直接重写库存单位成本，具体遵循 POS-DD-034。

# 一、库存领域边界

## 1.1 权威事实

库存领域拥有：

- 库存流水 inv_stock_ledger；
- 库存余额 inv_stock_balance；
- 预占及预占明细 inv_reservation；
- 成本余额与成本流水 inv_cost_balance、inv_cost_ledger；
- 批次、效期、序列号和库存状态；
- 盘点快照、盘点差异与调整；
- 库存异常、对账与重建任务。

库存领域不拥有：

- 订单价格、支付状态与退款结果；
- 商品名称、条码和类目主数据；
- 采购合同和供应商往来；
- 外部平台订单状态。

其他领域只能发送命令或消费库存事件，不得直接更新 inv_ 表。

## 1.2 库存聚合

| 聚合 | 主键 | 职责 |
|---|---|---|
| StockDimensionBalance | ULID 或稳定维度键 | 某租户、仓库、SKU、批次、库存状态的数量余额 |
| Reservation | ULID | 一次订单、渠道或调拨的预占生命周期 |
| StockCommand | ULID | 一次入库、出库、移库、调整的幂等业务指令 |
| CostBalance | ULID 或稳定维度键 | 某成本组织、仓库和 SKU 的移动加权数量与金额 |
| Stocktake | ULID | 盘点范围、冻结快照、实盘和差异确认 |

库存流水为不可变事实；余额是受控投影，不是唯一事实来源。

# 二、库存维度与数量口径

## 2.1 库存维度键

库存余额的最小维度：

| 维度 | 必填 | 说明 |
|---|---:|---|
| tenant_id | 是 | VARCHAR(20)，来自认证和设备上下文 |
| warehouse_id | 是 | 仓库或门店虚拟仓 ULID |
| sku_id | 是 | SKU ULID |
| stock_status | 是 | 可售、冻结、残次、在检、报废等 |
| batch_id | 否 | 启用批次管理时必填 |
| owner_id | 否 | 寄售、联营或多货主库存 |
| bin_id | 否 | 启用库位管理时使用 |

stock_dimension_key 必须由规范化维度计算稳定哈希，且建立 tenant_id + warehouse_id + sku_id + stock_status + batch_id + owner_id + bin_id 的等价唯一约束。空值必须规范化，避免 NULL 唯一语义产生重复余额行。

## 2.2 数量字段

| 字段 | 定义 |
|---|---|
| on_hand_qty | 当前实物账面数量 |
| reserved_qty | 已激活但未消耗的预占数量 |
| frozen_qty | 质检、争议、监管或人工冻结数量 |
| safety_stock_qty | 经营安全库存，仅影响可售口径 |
| in_transit_qty | 已发出但未收货的在途数量 |
| available_to_sell_qty | 可供销售数量 |

商业 V1 标准公式：

available_to_sell_qty = on_hand_qty - reserved_qty - frozen_qty - safety_stock_qty

说明：

- in_transit_qty 不计入 on_hand_qty，目的仓收货后才转为在手。
- 残次、报废、在检使用独立 stock_status，不与可售数量混合。
- 安全库存可按 SKU、门店、渠道分别配置；渠道发布量可以在可售基础上再减渠道缓冲。
- 报表必须明确使用 on_hand、available_to_sell 或 in_transit，不得笼统称“库存”。

## 2.3 单位换算

- 库存基础单位由 SKU 定义，所有流水保存 base_qty。
- 销售单位、采购单位和包装单位通过不可变换算快照转换。
- 换算率使用 DECIMAL(19,6)，不得使用浮点数。
- 非整包装拆零必须受 SKU quantity_scale 约束。
- 历史流水保留交易单位、交易数量、换算率和基础单位数量，不受后续单位变更影响。

# 三、库存流水

## 3.1 流水不变量

每条 inv_stock_ledger 必须满足：

- ledger_id 为 ULID；
- tenant_id、warehouse_id、sku_id 与 stock_dimension_key 一致；
- source_type + source_id + source_line_id + movement_type 在业务语义下唯一；
- quantity_before + quantity_delta = quantity_after；
- quantity_delta 不为 0，纯备注不得创建库存流水；
- 相同 stock_command_id 重试不产生新流水；
- 流水不得 UPDATE 数量、不得 DELETE；
- 更正通过反向流水与新正确流水完成；
- 同一余额维度的 ledger_seq 严格递增。

## 3.2 移动类型

| movement_type | 数量方向 | 来源 | 成本处理 |
|---|---:|---|---|
| SALE_OUT | 负 | 已确认销售订单行 | 按出库时移动平均成本 |
| SALE_RETURN_IN | 正 | 原单退货 | 优先使用原销售成本 |
| PURCHASE_RECEIPT_IN | 正 | 采购收货行 | 计入采购及分摊成本 |
| PURCHASE_RETURN_OUT | 负 | 采购退货 | 按关联收货成本或当前策略 |
| TRANSFER_OUT | 负 | 调拨发出 | 锁定发出成本 |
| TRANSFER_IN | 正 | 调拨收货 | 继承发出成本并加可资本化费用 |
| STOCKTAKE_GAIN | 正 | 盘盈 | 当前平均或批准估值成本 |
| STOCKTAKE_LOSS | 负 | 盘亏 | 当前移动平均成本 |
| DAMAGE_OUT | 负 | 报损/报废 | 当前成本并记录损耗科目 |
| STATUS_TRANSFER_OUT | 负 | 可售转冻结/残次 | 与对应入流水成对 |
| STATUS_TRANSFER_IN | 正 | 状态转入 | 成本保持不变 |
| MANUAL_ADJUST_IN | 正 | 审批调整 | 必须说明成本来源 |
| MANUAL_ADJUST_OUT | 负 | 审批调整 | 当前成本 |
| OPENING_BALANCE_IN | 正 | 初始化/迁移 | 迁移批次成本 |
| REVERSAL | 正或负 | 冲正原流水 | 精确反向原数量与成本 |

预占不改变 on_hand_qty，因此不创建上述实物流水；预占使用独立 reservation ledger 或状态历史。

## 3.3 流水字段

| 字段 | 类型 | 说明 |
|---|---|---|
| id | CHAR(26) | ULID |
| tenant_id | VARCHAR(20) | 租户编号 |
| ledger_seq | BIGINT | 同库存维度递增序号 |
| stock_dimension_key | CHAR(64) | 规范化维度哈希 |
| quantity_before | DECIMAL(19,6) | 变动前 |
| quantity_delta | DECIMAL(19,6) | 本次变动 |
| quantity_after | DECIMAL(19,6) | 变动后 |
| unit_cost | DECIMAL(19,6) | 本次成本口径 |
| cost_amount | DECIMAL(19,6) | 数量乘单位成本后的高精度金额 |
| source_type | VARCHAR(32) | ORDER、RETURN、RECEIPT 等 |
| source_id | CHAR(26) | 来源聚合 |
| source_line_id | CHAR(26) | 来源行 |
| stock_command_id | CHAR(26) | 幂等命令 |
| occurred_at | DATETIME(3) | 业务发生时间 UTC |
| business_date | DATE | 门店/仓库业务日 |
| actor_type/id | VARCHAR | 操作者 |
| reason_code | VARCHAR(32) | 标准原因 |
| reversal_of_id | CHAR(26) NULL | 被冲正流水 |

## 3.4 原子更新

对单一库存维度的变动，必须在一个事务中：

1. 以 tenant_id + stock_dimension_key 锁定余额行。
2. 检查 stock_command_id 是否已处理。
3. 校验负库存、冻结、批次和精度规则。
4. 计算 quantity_before、delta、after。
5. 插入不可变流水。
6. 更新余额与 record_version。
7. 更新成本余额与成本流水。
8. 写 Outbox 和命令结果。

不得先更新余额后异步补流水，也不得仅写流水而没有可恢复的余额投影更新策略。

# 四、预占模型

## 4.1 预占用途

预占用于：

- 外卖/电商订单待履约；
- 门店自提；
- 调拨申请；
- B2B 订货；
- 尚未完成支付但需要短时锁货的场景。

普通前台即时销售默认可在成交时直接出库，不强制预占；高并发渠道订单应先预占再消耗。

## 4.2 预占状态

| 状态 | 是否终态 | 含义 |
|---|---:|---|
| CREATED | 否 | 已创建，尚未占用余额 |
| ACTIVE | 否 | 已计入 reserved_qty |
| PARTIALLY_CONSUMED | 否 | 部分数量已转为实物出库 |
| CONSUMED | 是 | 全部转为出库 |
| RELEASED | 是 | 主动释放未消耗数量 |
| EXPIRED | 是 | 超时自动释放 |
| CANCELLED | 是 | 激活前取消 |

## 4.3 预占迁移

| 当前状态 | 命令 | 目标状态 | 守卫条件 |
|---|---|---|---|
| 不存在 | CreateReservation | CREATED | 来源唯一；数量大于 0 |
| CREATED | ActivateReservation | ACTIVE | 可售数量足够或允许受控超占 |
| ACTIVE | ConsumeReservation | PARTIALLY_CONSUMED/CONSUMED | 消耗量不超过剩余预占 |
| PARTIALLY_CONSUMED | ConsumeReservation | PARTIALLY_CONSUMED/CONSUMED | 同上 |
| ACTIVE/PARTIALLY_CONSUMED | ReleaseReservation | RELEASED | 释放未消耗部分 |
| ACTIVE/PARTIALLY_CONSUMED | ExpireReservation | EXPIRED | expires_at 已到且无续期 |
| CREATED | CancelReservation | CANCELLED | 尚未激活 |

终态不可恢复。需要再次锁货时创建新 Reservation，并关联 replaces_reservation_id。

## 4.4 预占原子操作

激活：

~~~sql
UPDATE inv_stock_balance
SET reserved_qty = reserved_qty + :qty,
    record_version = record_version + 1
WHERE tenant_id = :tenant_id
  AND stock_dimension_key = :dimension_key
  AND record_version = :expected_version
  AND (:allow_oversell = 1 OR
       on_hand_qty - reserved_qty - frozen_qty - safety_stock_qty >= :qty);
~~~

消耗必须在同一事务内：

- reserved_qty 减少消费数量；
- on_hand_qty 减少相同数量；
- 预占行 consumed_qty 增加；
- 插入 SALE_OUT 或其他对应实物流水；
- 记录 reservation.consumed.v1 和 stock.changed.v1。

释放或过期只减少 reserved_qty，不改变 on_hand_qty。

## 4.5 预占过期

- expires_at 使用服务端 UTC 时间。
- 终端时间不得决定云端预占是否过期。
- 扫描任务按 tenant_id 分片，并使用 SKIP LOCKED 或等价机制避免重复。
- ExpireReservation 命令必须幂等。
- 支付正在 UNKNOWN 时，预占应按渠道最大确认窗口续期，不得先释放再导致支付成功无货。
- 已进入拣货、称重或制作流程的订单是否自动过期由履约策略决定。

## 4.6 渠道库存发布

第三方渠道可售量不得直接等于 on_hand_qty。建议：

channel_sellable_qty = max(0, available_to_sell_qty - channel_buffer_qty - unpublished_reservation_qty)

发布规则：

- 以 tenant_id + channel + store + sku 为幂等键；
- 小变动可按阈值合并，售罄必须高优先级立即发布；
- 发布失败只影响渠道投影，不回滚内部库存；
- 外部平台回执与内部版本分别保存；
- 禁止外部库存值回写覆盖内部余额；
- 连接器只提交 ReserveStock、ReleaseReservation 等标准命令。

# 五、负库存与超卖策略

## 5.1 策略级别

| 策略 | 行为 | 适用 |
|---|---|---|
| DENY | 可售不足时拒绝 | 默认零售、受监管商品 |
| ALLOW_WITH_PERMISSION | 主管授权后允许 | 门店紧急销售 |
| ALLOW_AND_ALERT | 允许并立即产生异常 | 主数据或到货延迟场景 |
| CHANNEL_BUFFER | 外部发布预留缓冲 | 外卖、电商 |

策略按租户、门店、仓库、类目和 SKU 继承，SKU 最具体规则优先。

## 5.2 负库存成本

允许负库存时：

- 出库仍按当前移动平均成本计价；
- 无历史成本时使用最近采购成本或批准标准成本；
- 标记 cost_estimated = 1；
- 后续入库不得静默改写已确认销售成本；
- 可通过成本差异调整流水把估计与实际差异计入指定期间；
- 负库存持续超过阈值必须告警并进入门店任务。

商业 V1 默认 DENY；离线门店可以在有限额度内 ALLOW_AND_ALERT，但回传后必须进入差异审计。

# 六、移动加权平均成本

## 6.1 成本组织

成本口径必须配置 cost_scope：

- WAREHOUSE：每仓每 SKU 独立；
- STORE：门店下仓库汇总；
- COMPANY：公司级统一移动平均。

商业 V1 推荐 WAREHOUSE，能够解释调拨和门店毛利。启用后不得在同一财务期间随意改变；变更需要期末切换和期初重建。

## 6.2 成本余额

| 字段 | 类型 | 说明 |
|---|---|---|
| cost_scope_id | CHAR(26) | 成本组织 |
| sku_id | CHAR(26) | SKU |
| cost_qty | DECIMAL(19,6) | 参与成本计算的数量 |
| cost_amount | DECIMAL(19,6) | 高精度库存成本总额 |
| avg_unit_cost | DECIMAL(19,6) | 移动平均单位成本 |
| record_version | BIGINT | 并发版本 |
| last_ledger_seq | BIGINT | 已处理成本流水序号 |

始终以 cost_amount 作为高精度事实，avg_unit_cost 是计算结果。金额展示和总账接口再按币种规则舍入为最小货币单位。

## 6.3 采购入库

当旧数量大于等于 0：

new_cost_amount = old_cost_amount + inbound_qty × inbound_unit_cost + allocated_cost

new_cost_qty = old_cost_qty + inbound_qty

new_avg_unit_cost = new_cost_amount ÷ new_cost_qty

其中：

- inbound_unit_cost 来自采购收货的含税/不含税口径配置；
- freight、关税、加工费等只有满足财务策略才计入 allocated_cost；
- allocated_cost 的分摊必须保存分摊方法和来源单；
- new_cost_qty 为 0 时 avg_unit_cost 保留最近有效成本或置为 0，策略必须统一。

## 6.4 销售出库

销售出库：

- issue_unit_cost = 出库事务开始时的 avg_unit_cost；
- issue_cost_amount = base_qty × issue_unit_cost；
- cost_qty 与 cost_amount 同步减少；
- 订单行保存 cost_snapshot，不等后续重算；
- 出库后移动平均成本原则上不因出库而变化，舍入差异在剩余量为 0 时结清。

## 6.5 销售退货

优先级：

1. 能关联原订单行和原 SALE_OUT 流水时，使用原出库单位成本。
2. 原订单包含多批次时，按原批次分配退回。
3. 无法取得原成本时，使用当前移动平均成本并标记 COST_ESTIMATED。
4. 无原单退货使用批准的估值策略，并进入成本差异报表。

部分退货成本使用原行累计算法，最后一次可退数量承接小数余数，确保累计退货成本不超过原销售成本。

## 6.6 调拨成本

调拨发出时锁定 transfer_unit_cost：

- TRANSFER_OUT 按发出仓成本减少；
- 在途记录保存数量与成本；
- TRANSFER_IN 使用发出成本，加目的地允许资本化的费用；
- 短溢、破损通过独立差异流水处理；
- 目的仓不得按收货时自己的平均成本伪造调拨成本；
- 调拨取消必须根据是否发出、是否在途、是否收货采用不同反向流程。

## 6.7 采购退货与价格更正

- 能关联收货批次时使用原收货成本。
- 已消耗部分导致无法原样退回时，差异进入采购价差。
- 已关账期间不得回写历史成本流水；在当前开放期间创建成本调整。
- 供应商返利、后返、费用票据是否影响库存成本由会计政策决定，并保存 policy_version。

## 6.8 舍入

- 数量与单位成本计算全过程保留 DECIMAL 精度。
- 成本总额至少 DECIMAL(19,6)，禁止 double。
- 单行销售成本可保留 6 位小数；汇总到财务凭证时按币种舍入。
- 分摊余数采用最大余数法，稳定排序为 source_line_no、sku_id、ledger_id。
- 任何累计分摊必须保证分摊后总额精确等于待分摊总额。

# 七、批次、效期与序列号

## 7.1 批次

启用批次的 SKU：

- 所有入库必须指定 batch_no、production_date、expiry_date 中的适用字段；
- 库存余额按 batch_id 分开；
- 出库默认 FEFO，效期相同时 FIFO；
- 人工指定批次需要权限和审计；
- 已过期批次自动转为不可售状态，不自动删除数量；
- 批次号修改通过别名或受控更正，不覆盖已发生流水。

## 7.2 保质期

- 预警天数支持租户、类目、SKU 继承。
- 临期可售、折价、禁售和报损是不同策略。
- POS 规则包应包含批次禁售或最短剩余保质期规则。
- 离线终端必须用已签名数据包判断；规则包过期后对受监管品采取阻断。

## 7.3 序列号

序列号商品：

- 基础数量精度固定为 0；
- 每个序列号在租户范围内唯一；
- 状态包括 IN_STOCK、RESERVED、SOLD、RETURNED、DAMAGED、VOID；
- 出入库流水必须引用序列号；
- 退货校验原序列号，换货产生新旧序列号关系；
- 商业 V1 可以不开放，但数据模型需预留。

# 八、盘点

## 8.1 盘点状态

| 状态 | 含义 |
|---|---|
| DRAFT | 定义仓库、SKU、批次和盘点方式 |
| SNAPSHOTTED | 已冻结账面快照 |
| COUNTING | 初盘中 |
| RECOUNT_REQUIRED | 差异超过阈值，要求复盘 |
| PENDING_APPROVAL | 等待差异审批 |
| CONFIRMED | 差异已批准 |
| POSTED | 已创建盘盈盘亏流水 |
| CANCELLED | 入账前取消 |

## 8.2 盘点模式

- 全盘：仓库范围内所有 SKU；
- 循环盘点：按 ABC 分类或风险抽样；
- 动态盘点：允许期间业务继续，需以 ledger_seq 校准；
- 静态盘点：冻结库存操作窗口；
- 盲盘：盘点员不显示账面数量。

## 8.3 动态盘点算法

1. 创建 snapshot_seq 与 snapshot_qty。
2. 记录盘点实数和 count_at。
3. 汇总 snapshot_seq 之后至 count_at 的有效库存移动。
4. 得到 adjusted_book_qty。
5. variance_qty = counted_qty - adjusted_book_qty。
6. 差异超过数量或金额阈值进入复盘/审批。
7. POST 时以最新余额再次校验，并创建 STOCKTAKE_GAIN/LOSS。

不得直接把余额更新为盘点数而不写差异流水。

## 8.4 盘点职责分离

- 盘点创建、计数、复盘和批准可按风险要求分离。
- 高价值 SKU 盘亏必须双人批准。
- 修改计数必须保留原值、修改人、原因与时间。
- 盘点单入账后不可编辑，只能创建后续纠正盘点。

# 九、离线库存

## 9.1 本地策略

Android POS 使用 SQLite 保存：

- 当前门店可售 SKU 的库存投影；
- 最新 masterdata_version 和 inventory_cursor；
- 本地离线销售造成的 pending_delta；
- 已提交 Outbox 与服务端处理结果；
- 本地库存命令幂等记录。

展示可售量：

local_effective_available = cloud_snapshot_available + local_pending_delta - local_pending_reservation

该值是操作提示，不是云端权威库存。

## 9.2 离线销售

- 默认只对当前终端本地缓存有授权的门店仓执行。
- 离线销售在本地事务内写 SALE_OUT pending ledger。
- 多终端同时离线可能产生超卖，租户必须配置离线负库存额度和 SKU 禁售名单。
- 高价值、序列号、受监管、储值卡等商品默认禁止离线销售。
- 回传云端时保留客户端 stock_command_id；重复事件不重复扣减。
- 云端库存不足时，已完成的现金成交不能被无声丢弃，应接受为差异或按策略进入人工处置。

## 9.3 云端回放

云端按以下顺序处理：

1. 验证租户、门店、设备、班次和事件签名。
2. 检查 event_id、payload_hash 与 stock_command_id。
3. 按 occurred_at 记录业务时间，但用 received_at 决定处理审计顺序。
4. 执行当前余额上的幂等扣减。
5. 若导致负库存且设备拥有离线额度，接受并标记 OFFLINE_OVERSELL。
6. 超出额度时接受交易事实但库存命令进入 EXCEPTION，由实施策略决定补偿。
7. 返回最新库存游标和差异信息。

# 十、并发与锁

## 10.1 锁顺序

一次命令涉及多个维度时，必须按以下稳定顺序加锁：

tenant_id → warehouse_id → sku_id → stock_status → batch_id → bin_id

应用层先对维度键排序，再按排序结果锁行，降低死锁。

## 10.2 并发策略

- 单维度高频扣减使用数据库原子条件更新或短事务行锁。
- 不用 Redis 锁替代数据库余额条件和幂等唯一键。
- 发生死锁或 record_version 冲突时，可在命令级安全重试。
- 重试必须复用 stock_command_id。
- 批量任务分片，每个事务控制行数和锁时间。
- 余额行首次创建使用唯一约束与插入冲突处理，不能先查后插而无保护。

## 10.3 热点 SKU

可采用：

- 库存维度分仓；
- 短批处理与命令队列；
- 高峰期渠道发布节流；
- 预占分桶投影。

但最终权威余额仍必须可由统一账本核验，不能形成多个无法对账的“库存真相”。

# 十二、对账、重建与归档

## 12.1 日常对账

至少执行：

- 余额 quantity 与流水累计一致；
- reserved_qty 与 ACTIVE/PARTIALLY_CONSUMED 预占剩余量一致；
- cost_qty、cost_amount 与成本流水一致；
- SALE_OUT 与已完成订单行匹配；
- SALE_RETURN_IN 与成功退货处置匹配；
- 调拨发出、在途和收货数量成本闭环；
- 负库存、冻结过期、未知批次和孤儿流水检查；
- 渠道发布库存与内部可售量差异监控。

## 12.2 重建

- 重建只能生成新的投影版本，不覆盖原流水。
- 按 tenant_id、warehouse_id、sku_id 分片。
- 使用 checkpoint ledger_seq，支持暂停与续跑。
- 重建完成后比较旧投影、新投影和账本，差异需审批切换。
- 切换通过原子版本指针完成。
- 重建期间写入新流水必须同时进入增量追赶队列。

## 12.3 归档

- 流水保留期满足财务、税务和争议要求。
- 热表可按业务日期和租户规模分区或归档。
- 归档前生成数量与成本校验清单、哈希和可恢复索引。
- 归档对象不可单独删除导致订单、退货或凭证无法追溯。

# 十四、安全与审计

- tenant_id 必须进入所有唯一键、查询条件、缓存键、事件和对象存储路径。
- 客户端提交的成本默认不可信；采购成本、调拨成本和盘点估值由服务端权限校验。
- 人工调整必须记录 before、delta、after、金额影响、原因、附件和审批。
- 盘亏、报损、负库存放行和成本重估属于高风险动作。
- 库存流水不得软删除；归档必须保留可验证哈希。
- 批量导入支持 dry-run、错误报告、批次回滚指令和操作审计。
- 导出库存和成本数据应用数据范围权限与水印/审计策略。

# 十五、性能与容量

## 15.1 目标

商业 V1 建议目标：

- 单 SKU 单仓库存命令 P95 小于 100 ms，不含跨域消息传输；
- 普通门店批量收货 500 行在 5 秒内完成或异步可见；
- POS 库存查询 P95 小于 200 ms；
- 库存事件 Outbox 延迟 P95 小于 5 秒；
- 日对账在门店次日营业前完成；
- 单租户千万级流水仍可按订单、SKU、仓和日期定位。

## 15.2 索引

核心索引：

- inv_stock_balance：tenant_id + warehouse_id + sku_id + stock_status + batch_id；
- inv_stock_ledger：tenant_id + stock_dimension_key + ledger_seq；
- inv_stock_ledger：tenant_id + source_type + source_id + source_line_id；
- inv_reservation：tenant_id + source_type + source_id；
- inv_reservation：tenant_id + status + expires_at；
- inv_cost_ledger：tenant_id + cost_scope_id + sku_id + ledger_seq；
- stocktake_line：tenant_id + stocktake_id + sku_id + batch_id。

索引必须结合真实查询计划和数据分布验证，不以“索引越多越好”为原则。

# 十六、验收测试

## 16.1 数量不变量

必须自动验证：

- before + delta = after；
- 余额等于起初量加所有有效流水；
- reserved_qty 等于所有活动预占未消耗量；
- 消耗预占同时减少 reserved 和 on_hand；
- 释放预占只减少 reserved；
- 同一命令重放 100 次只有一次效果；
- 禁止策略下 available_to_sell 不因并发扣减变负；
- 跨租户无法读取、锁定或修改库存。

## 16.2 成本不变量

- 入库后 cost_amount 守恒；
- 出库使用事务时成本快照；
- 退货累计成本不超过原销售成本；
- 调拨发出、在途、收货成本闭环；
- 数量归零时舍入差异有确定处置；
- 无 float、double 参与最终数量与成本；
- 重建结果与在线投影一致。

## 16.3 故障注入

1. 写流水后、更新余额前进程崩溃，验证事务回滚。
2. 提交数据库后、响应调用方前崩溃，验证幂等返回。
3. Outbox 中断 30 分钟后恢复，验证事件不丢不重做业务。
4. 两百个并发扣减争抢同一 SKU。
5. 预占消耗与过期任务并发。
6. 调拨收货重复提交。
7. 动态盘点期间持续销售和收货。
8. 离线两台 POS 同时销售最后一件商品。
9. 批次已过期但终端规则包未及时更新。
10. 成本流水出现缺口后执行重建和告警。

## 16.4 业务验收场景

- 即时现金销售；
- 渠道下单预占、取消释放、履约消耗；
- 部分发货和部分释放；
- 原单部分退货；
- 买赠退货的商品与赠品处置；
- 采购分批收货、退货和价格更正；
- 跨仓调拨短溢；
- 全盘、循环盘点与盲盘；
- 报损、冻结、解冻和状态转换；
- 离线销售回传形成受控负库存。

# 十八、商业 V1 决策摘要

1. 不可变库存流水是数量事实，余额是可重建投影。
2. 预占只影响 reserved_qty，不直接修改 on_hand_qty。
3. 所有库存命令必须以 ULID 幂等，事务内写流水、余额、成本和 Outbox。
4. 商业 V1 默认禁止负库存；离线放行必须有额度、名单和异常审计。
5. 成本默认采用仓级移动加权平均，退货优先使用原销售成本。
6. 调拨成本从发出仓继承，不按目的仓当前成本重估。
7. 盘点差异必须通过盘盈盘亏流水入账，不直接覆盖余额。
8. 数量与成本全链路使用 Decimal，禁止浮点计算。
9. 外部渠道库存是发布投影，不得回写覆盖内部账本。
10. 账本、余额、预占、成本和订单必须每日自动对账。

本规范批准后，库存维度、移动类型、成本公式、预占状态和幂等键成为商业 V1 冻结契约；任何变更必须评估历史重算、财务口径、离线兼容和连接器影响。
