# T2-E2E-003 设计准入与独立验证

## 1. 准入结论

`T2-CORE-001 → T2-API-001 → T2-DAT-001 → T2-INT-001` 已依序 `VERIFIED` 后，`T2-E2E-003` 才进入实现。其唯一目标是把已接受商业 V1 能力组成内部候选，不新增领域算法，也不解除任何外部阻断。

## 2. 执行模型

同一 GitHub Actions run 必须产生并汇总以下独立证据：

| 组件 | 正式执行证据 |
| --- | --- |
| Server | `ruoyi-admin` 模块化单体全量测试、可执行 JAR 内 Owner 装配、应用端口和事件协作 |
| Web | 生产构建、正式 API 组件测试、类型和 ESLint |
| Flutter POS | Linux/Windows 全量测试；正式会话绑定组合根经 loopback HTTP 下载签名包并使用文件 SQLite 完成现金交易 |
| MySQL | MySQL 8.4 空环境前向迁移、重复执行、元数据和租户约束 |
| SQLite | 文件数据库迁移、签名商品/促销包、开关班、成交事实、现金、促销快照与 Outbox |

候选执行分类固定为 `FORMAL_COMPONENT_EXECUTION_PLUS_CONTRACT_RECONCILIATION`。服务端 Owner 测试和 MySQL、Web、POS 正式运行链均实际执行；三业态跨组件结果使用已冻结合成向量逐字段核对。它不是一条连接真实支付、真实设备和真实门店的现场全栈链，不能升级为 `FULL_ALPHA/PILOT/PRODUCTION`。

## 3. 正式 POS 装配不变量

1. 设备凭据只从安全材料端口读取；HWD 未解阻时默认提供者明确失败关闭。
2. `tenant_id`、门店和设备标识只能来自终端认证响应，所有 HTTP 请求不得发送 `X-Tenant-Id` 作为授权依据。
3. 员工认证后才创建 `${tenant}-${store}-${device}.sqlite3`；商品包、促销包必须同时通过 SHA-256、Ed25519、租户、门店和版本链校验。
4. 认证成功而本地装配失败时撤销刚建立的员工会话，不保留半可用业务运行时。
5. 开班、订单、行、促销成交快照、现金、班次效果和 Outbox 沿用既有原子事务；打印只生成任务和预览。
6. 退货仓库使用服务端一致的 ULID；退款 `UNKNOWN` 只查询原命令。

## 4. 三业态与故障矩阵

- 两个虚构租户分别覆盖便利店、零食折扣店和社区超市，共六条销售旅程与六条部分/最终退货旅程。
- 固定 12 个 Gate 6G seed 覆盖装配失败、TLS、ULID 漂移、安全凭据缺失、跨租户、ACK 丢失、同键异内容、进程终止、SQLite 写失败、快照篡改、投影重建和坏发布物。
- P0/P1 必须为 0；任一必需测试缺失、跳过或证据摘要不符即失败。

## 5. 验证结论

最终候选提交 `ac04afbc2236038fb73f99ba3a3ecd418ac7f5c5` 的 GitHub run [`32456191093`](https://github.com/eiven-xxw/jshPOS/actions/runs/32456191093) 已满足治理、Server、MySQL、双平台 POS、Web、运行栈烟测、内部候选、安全和证据十类 Job 全绿。Linux/Windows 各记录 166 个成功 Flutter 测试，22 个必需 Server Owner 套件覆盖 42 个指定测试，Web 6 个指定测试通过；六条销售、六条退货、12 个固定 seed 均通过，P0/P1 为 0。

因此 `T2-E2E-003` 结论为 `PASS / VERIFIED`，Gate 6G 建议 `CONDITIONAL PASS` 并等待项目发起人确认。证据上限仍为 `INTERNAL_V1_CORE_CANDIDATE`，外部执行计数全部为 0。
