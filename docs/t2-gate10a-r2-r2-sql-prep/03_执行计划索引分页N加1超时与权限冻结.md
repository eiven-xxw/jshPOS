# 执行计划、索引、分页、N+1、超时与权限冻结

## 执行计划证据

每条查询必须保存：规范化 SQL 摘要、参数类型和值域、`SHOW INDEX`、表基数、优化器配置、
`EXPLAIN FORMAT=JSON`、`EXPLAIN ANALYZE FORMAT=TREE`、实际返回行和 JDBC 查询数。不同 GitHub
执行器间不比较绝对耗时；以计划形态、扫描/返回比和查询数为权威。

## 共同预算

- 可信 `tenant_id` 必须存在；适用查询必须包含门店、仓库、单据或会员范围；
- 跨租户返回 0、权限绕过 0、`SELECT *` 0；
- 100k 事实表不得出现不可解释全表扫描；扫描/返回比目标不超过 20；
- 交互/锁定查询会话超时 2 秒，单据明细 1 秒，数据包/导出 10 秒；
- FEFO 与积分锁定必须具备稳定排序，超时或死锁必须回滚并复用原业务身份。

## 已观察放大红基线

1. 报表导出分别存在 3 条“按门店一次查询”的路径，门店上限为 50；
2. 支付对账在账单引用循环内逐条执行内部事实查询；
3. 临期查询取得最多 500 个候选后逐条读取策略；
4. 销售、库存成本和支付对账三个交互查询只有 31 日范围，没有显式分页契约。

上述事实只建立整改输入。批量端口、分页响应或索引若改变兼容/Schema，必须先提交独立 CR。
