# Gate 3 正式支付开发解阻清单与下一步指令

> 文档编号：JSH-POS-T2-S3-G3-008
> 日期：2026-08-16
> 当前状态：`PREPARED / NOT ADMITTED`
> 适用需求：`T2-PAY-001`、`T2-PAY-002`、`T2-PAY-003`、`T2-REF-001`、`T2-REC-001`

## 1. 当前边界

- `T2-PAY-001`、`T2-PAY-003`、`T2-REF-001`、`T2-REC-001` 继续 `DRAFT`；本文件不是开发准入。
- `T2-PAY-002` 继续 `BLOCKED`；资料齐备后必须提交独立解阻评审，未经项目发起人确认不得发起任何 Provider 网络调用。
- 支付 Fake 只用于确定性契约测试，不作为 `SANDBOX`、真实资金、渠道验收或商业验收证据。
- 禁止真实资金、生产商户、生产密钥、未脱敏账单和真实消费者数据进入开发、CI 或测试环境。

## 2. 必须由业务侧提供的解阻资料

### 2.1 首接 Provider 决策

必须明确一个“首接且可获得授权沙箱”的 Provider，不能仅填写品牌名。输入至少包括：

| 输入 | 必填内容 | 验收方式 |
|---|---|---|
| 合作主体 | 签约主体、渠道/服务商身份、产品名称 | 商务负责人书面确认 |
| 接入模式 | 聚合码、主扫、被扫、刷脸、银行卡或终端 SDK 的实际准入子集 | 与本期 POS 场景逐项映射 |
| 沙箱商户 | sandbox merchant/app/store/terminal 标识及有效期 | 能在非生产环境完成鉴权 |
| 终端约束 | 是否绑定 SN、门店、收银机、IP 或报备终端 | 沙箱配置清单 |
| 技术资料 | 官方接口目录、版本、错误码、签名、证书、回调、查询、退款、账单、限流 | 文档版本和获取日期可追溯 |
| 技术联系人 | Provider 技术支持人、工单渠道和响应时间 | 可完成一次联调问题闭环 |
| 商务联系人 | 费率、结算周期、拒付/差错/退款责任、上线审批 | 商务/财务负责人确认 |

候选池保持“直连渠道 + 聚合收单”双轨评估：微信支付、支付宝、银联体系，以及拉卡拉、汇付、易宝、富友、通联等具备线下收单能力的合作方。候选数量不等于已接入数量；只有取得授权沙箱、正式文档和可联调联系人后才具备 `T2-PAY-002` 解阻资格。

### 2.2 沙箱凭据与网络

- 只接受专用非生产账号、证书和密钥；生产凭据不得复制、降级或脱敏后使用。
- 凭据必须进入受控 Secret Store/GitHub Environment，不写入仓库、文档、日志、测试快照、APK 或工单正文。
- 提供沙箱 API 域名、固定 IP/白名单要求、TLS/mTLS、证书链、签名算法、时间窗、nonce、重放策略和限流值。
- 提供独立 HTTPS 回调域名、证书、WAF/网关规则、请求体大小、超时和 Provider 重试策略。
- 明确时钟同步要求；支付请求、查询、回调和账单时间统一保存 Provider 原始时间及平台 UTC 时间。

### 2.3 业务与测试向量

- 支持的支付方式、币种、最小/最大金额、单日限额、门店/终端限制。
- 成功、明确失败、受理中、超时未知、撤销、全额退款、部分退款、退款未知的沙箱触发方法。
- 回调先于同步响应、重复回调、乱序回调、查询先成功后回调失败等固定向量。
- 日账单/交易账单/退款账单样例及字段字典；样例必须是沙箱或脱敏合成数据。
- Provider 订单号、商户订单号、退款号、渠道流水号的长度、字符集、唯一性和有效期。

## 3. 工程准入前置件

以下项目全部完成后，Provider 无关核心需求才可从 `DRAFT` 逐项进入 `READY/IN_PROGRESS`：

1. 支付、退款、查询/回调合并和对账状态机的不变量、终态与非法回退已冻结；
2. 创建支付意图、确认、查询、关闭、退款、账单下载接口的 OpenAPI/Schema 和错误码已冻结；
3. 金额使用最小货币单位整数，退款累计金额和数量不超过原单可退上限；
4. 商户订单号、支付意图 ID、Provider 请求号、回调事件 ID 和退款 ID 的幂等主权已冻结；
5. `UNKNOWN` 只允许查询/可信回调/对账收敛，禁止重新生成订单或支付命令；
6. 回调验签、重放防护、金额/币种/商户/终端比对、原始证据哈希和审计已设计；
7. Provider 端口与适配器边界、超时预算、重试预算、熔断、限流和人工修复已设计；
8. 数据库迁移、唯一键、乐观锁、Outbox/Inbox、回退和前向修复已设计；
9. 权限矩阵覆盖收款、查询、关单、退款申请/审批、差错处理、账单和人工修复；
10. Fake 固定向量、沙箱测试矩阵、故障注入和证据等级标识已完成；
11. CI 保持治理、服务端、Flutter、MySQL、租户攻击、安全、SBOM、许可证、覆盖率和证据门禁；
12. 安全评审确认系统不采集银行卡敏感认证数据，不在日志/审计中记录付款码、密钥或完整渠道报文敏感字段。

## 4. `T2-PAY-002` 单独解阻条件

只有同时满足下列条件，才可以提交 `T2-PAY-002` 解阻评审：

- 首接 Provider、产品和接入模式已唯一确定；
- 授权沙箱账号、测试终端、官方文档版本和技术联系人齐备；
- 非生产 Secret Store、回调域名和网络白名单已配置并由安全负责人复核；
- Provider 适配器只依赖冻结的支付端口，不把渠道字段渗透进订单领域；
- 沙箱测试计划明确每次调用的合成订单、期望状态、证据文件和清理方式；
- 真实资金和生产端点存在自动阻断，CI 默认网络为 deny；
- 项目发起人对独立《支付沙箱解阻评审报告》作出明确 `GO`。

资料部分齐备只能保持 `BLOCKED_WITH_PROGRESS`，不能改成 `READY`，也不能创建绿色占位。

## 5. 推荐实施顺序

1. **Gate 3A：Provider 无关核心。** 仅实现 `T2-PAY-001`、`T2-PAY-003`、`T2-REF-001`、`T2-REC-001` 经准入的领域状态机、端口、持久化、契约和 Fake 回归；默认没有外网入口。
2. **Gate 3B：首家 Provider 沙箱适配。** 仅在 `T2-PAY-002` 单独解阻后实现一个沙箱适配器，完成支付、查询、回调、退款和账单的闭环证据。
3. **Gate 3C：第二 Provider 与适配器认证。** 首家沙箱稳定后，再用相同认证套件接入后续 Provider；禁止同时铺开五家导致状态语义分叉。

## 6. Gate 3 Go/No-Go

`GO` 必须同时满足：S3 已由项目发起人确认并把 `T2-SYN-001` 更新为 `ACCEPTED`；Gate 3 需求逐项准入完成；无开放 P0 设计缺陷；支付 Provider 运行时边界清晰。若只具备 Provider 无关资料，可对 Gate 3A `CONDITIONAL GO`，但 `T2-PAY-002` 仍 `BLOCKED`。

以下任一项触发 `NO-GO`：要求使用生产密钥/真实资金验证、无法可靠查询未知状态、回调无验签或防重放、无法提供账单、退款缺原单/金额上限、租户/商户/门店/终端主权不清、Provider 要求客户端保存敏感密钥、或 CI 必须开放不受控公网才能通过。
