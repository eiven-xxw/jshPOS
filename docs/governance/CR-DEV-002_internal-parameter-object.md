# CR-DEV-002 内部方法参数对象规范

> 状态：APPROVED  
> 提出日期：2026-08-16  
> 生效日期：2026-08-16  
> 变更类型：工程治理增强  
> 影响范围：新增或实质修改的服务端内部业务方法

## 1. 变更请求

项目发起人建议：内部方法的参数超过一定数量时，创建内部传输类，以增强扩展性和可维护性；授权在分析合理性后登记到开发规范。

## 2. 分析结论

采纳该建议，但将“内部 DTO”修订为更准确的“参数对象”。原因如下：

- 长参数列表容易发生位置交换、漏传、默认值不一致和调用点同步修改，尤其在金额、状态、幂等和可信上下文参与时风险更高；
- 具名不可变对象可以把共同变化的参数和组合校验集中表达，降低方法签名扩散；
- DTO 表示跨边界数据传输。领域或应用内部若全部命名为 DTO，会模糊接口模型、应用命令和领域值对象的边界；
- 单纯把无关参数塞进一个大对象只会转移复杂度，因此必须同时约束内聚性、不可变性、命名和拆分职责；
- 参数数量只是风险信号，不能替代对同类型参数、布尔开关、可选参数组合及类职责的判断。

最终采用“5 个及以上业务参数默认触发参数对象”的评审阈值。该阈值在可执行性和避免过度封装之间取得平衡；4 个以内仍须按语义评审，存在多个同类型参数、两个及以上布尔开关或共同变化参数时可以提前触发。

## 3. 决策规则

1. 自研内部业务方法出现 5 个及以上业务参数时，默认使用不可变、具名且职责内聚的参数对象。
2. 应用用例使用 `Command/Query`，领域内部使用值对象或具名参数对象；只有 REST、消息、连接器或进程边界模型称 DTO。
3. 参数对象不得使用通用 Map、数组、布尔标志集合或无关字段拼盘代替清晰模型；无法内聚时拆分方法或类职责。
4. 可信租户、权限、门店数据范围和操作者上下文不得混入客户端可构造 DTO，也不得因 Bean 拷贝而被覆盖。
5. 框架规定签名、第三方接口、序列化模型、数据记录载体和依赖注入构造器允许评审例外；构造器依赖过多应通过职责拆分解决。
6. 规则对新增或实质修改代码生效，存量代码按触达范围治理；资金、退款、库存、租户、幂等和审计相关长参数列表优先整改并保留行为回归证据。

## 4. 影响分析

| 维度 | 结论 |
|---|---|
| 商业范围 | 不新增功能，不改变 Gate 3A 准入范围 |
| 资金/库存状态机 | 不改变业务事实；相关重构必须以回归测试证明不变量保持 |
| 租户与权限 | 强化可信上下文边界，禁止客户端 DTO 成为授权来源 |
| API/事件 | 不要求修改既有外部契约；外部模型继续遵守版本化和兼容规则 |
| 数据库/迁移 | 无 Schema 或 Flyway 变化 |
| 依赖/许可证 | 不新增依赖 |
| 回滚 | 可回退本 CR 的文档条款；代码重构按各需求独立回滚 |
| RTM | 工程治理 CR，不改变业务需求状态；由变更日志追踪 |

## 5. 替代方案

- 不设阈值、完全依赖评审经验：执行一致性较差，不采纳。
- 一律最多 3 个参数：对简单内部算法和稳定调用过于机械，不采纳。
- 沿用常见静态分析的更高阈值后才处理：对本项目资金、租户和幂等代码的易错风险响应偏晚，不采纳。
- 所有内部模型统一命名 DTO：会破坏分层语义，不采纳。
