# CR-T2G9R3-026：G9A-R3D 可信 POS 会话联合旅程

## 变更结论

- 变更类型：既有 `G9A-UI-P1-001` 缺陷的最小运行时修复；
- Requirement：复用既有 POS、班次、组合支付、退货退款与换货 Requirement，不新增 ID；
- 范围：`FLT-01..06` 的同一可信会话联合测试，以及班次现金失败命令的会话级身份连续性；
- 禁止项：不新增 API、Controller、依赖、数据库、迁移、支付 Provider 或设备命令。

## 失败证据

首轮测试先完成一次现金动作，再让第二次动作失败，随后退出现金页并重新进入。失败命令首次使用
`…:2`，重新进入后旧页面私有序号从零开始，恢复请求错误地变为 `…:1`。这证明原实现只能满足
单页内重试，不能满足 ADR-071 规定的跨页原命令恢复。

## 最小修复

新增会话内 `ShiftOperationIdentityRegistry`，以可信班次、业务日和规范化操作内容共同确定作用域：

1. `PosSessionShell` 为一次员工会话持有唯一登记表并注入现金页；
2. 失败时保留原键，页面退出和重建不清除；
3. 命令成功后释放对应键；关班或安全退出成功后清空整个会话登记表；
4. 登记表不保存金额事实，不写 SQLite，不替代服务端幂等和最终授权。

## 验证

- 六个 Flutter 正式页面在同一可信租户、门店、终端、员工、班次和业务日下依次挂载；
- 收银工作台默认正式端口未装配时保持失败关闭；组合支付电子份额不执行网络；
- 现金失败跨页返回后第三次调用与第二次失败调用使用完全相同的幂等键；
- R3C 班次现金既有回归同步通过。

`R3D-JNT-P1-003` 可标记 `CLOSED_IN_BATCH`，整体 `G9A-UI-P1-001` 仍保持 `OPEN`，等待
R3D-R4 全量联合门禁和项目发起人确认。
