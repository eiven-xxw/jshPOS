# CR-T2G9R4-020：G9A-R4 发布关联标识夹具修复

## 1. 触发证据

- 候选提交：`6ed349e8e6837a291df1b0b5ad85cda1c12be9d7`
- GitHub Actions Run：`32915032795`
- 失败 Job：`formal-runtime`（`98017532167`）
- Artifact：`t2-g9a-r4-formal-runtime`（`9587981072`），SHA-256
  `414bc4f2e294743c0435bf54ad9555d19bf1a10f3acdb1eae984db69b6f94559`
- MySQL 根因：`Data too long for column 'correlation_id' at row 1`

该候选的治理双平台、Server、Web、Flutter 双平台与 Android/Database 均通过。正式运行栈
已经通过发布版本及兼容窗口校验，随后在持久化发布创建事实时失败关闭。

## 2. 已确认根因

Release Owner 的发布事实把关联标识持久化为 `CHAR(26)` ULID。G9A-R4 的 Release 专用
请求只发送 `X-Idempotency-Key`，遗漏平台统一的 `X-Correlation-ID`；HTTP 过滤器因此生成
36 字符 UUID，最终被 MySQL 8.4 严格拒绝。其他 G9A-R4 正式写请求已通过 `api_headers`
提供稳定 ULID，缺陷只存在于 Release 专用头构造与后续固定故障夹具。

## 3. 最小修复

1. 先增加 Release 写命令必须同时携带专用幂等头和 26 位 ULID 关联头的可执行失败回归；
2. 增加合成 Release 专用头生成器，校验既有幂等格式与 ULID；
3. 后置旅程的发布创建、F01 重复/冲突和 F12 失败关闭复用原稳定关联身份；
4. 不修改全局过滤器、Release Java、Controller、OpenAPI、状态机、数据库或已发布迁移；
5. 不重跑失败 Job，新提交从头运行完整 G9A-R4 CI。

## 4. 状态与边界

- `G9A-E2E-P1-001` 继续 `OPEN`；
- V87 仍是相对 G9A-R4 基线唯一允许新增的 Flyway 前向迁移；
- 外部 BLOCKED、UAT/REL DRAFT、LIC/JSH DEFERRED 与零执行边界不变；
- 完整 CI 通过且经项目发起人确认前，不关闭 Finding，不启动完整 Alpha 或生产发布。
