## 1. 触发证据

- 候选提交：`33a1cee91c483a32b5cef1a27e310b62c8db7472`
- GitHub Actions Run：`32914408462`
- 失败 Job：`formal-runtime`（`98015681942`）
- 失败位置：`r4-community-release-create`
- 服务端结果：HTTP `200`、业务码 `400`、`UPG-COMP-004: 应用最高版本格式无效`

该候选的治理双平台、Server、Web、Flutter 双平台与 Android/Database 均通过，V87 的

越过发布版本号失败点，随后在同一创建命令的兼容窗口校验失败关闭。

## 2. 已确认根因

G9A-R4 合成夹具把 `maxAppVersion` 写为通配文本 `1.0.x`，但 Release Owner 已接受契约
要求兼容窗口的八个版本字段全部使用数字版本格式。正式后置旅程与固定故障夹具复制了
同一非法窗口；Release Owner 拒绝该输入符合既有规则。

## 3. 最小修复

1. 先增加兼容窗口八字段的可执行失败回归；
2. 生成仅覆盖当前虚构终端的最小窗口：应用版本 `1.0.0..1.0.0`，协议、Schema 和系统
   版本均为 `1.0..1.0`；
3. 正式后置旅程和固定故障 seed 共用同一窗口，避免测试夹具漂移；
4. 不修改 Release Java 规则、状态机、API、OpenAPI、事件、数据库或已发布迁移；
5. 不重跑失败 Job，新提交从头运行完整 G9A-R4 CI。

- `G9A-E2E-P1-001` 继续 `OPEN`；
