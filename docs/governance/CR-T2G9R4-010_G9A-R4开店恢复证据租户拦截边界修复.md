# CR-T2G9R4-010：G9A-R4 开店恢复证据租户拦截边界修复

## 1. 触发证据

- 候选提交：`c97570f`
- GitHub Actions Run：`32891461231`
- 失败 Job：`formal-runtime`（`97945077205`）
- 正式运行栈 Artifact：`t2-g9a-r4-formal-runtime`，下载归档 SHA-256 `827674d79c04d9bf05fd85f62d0daf1d2a35fa86464e4f54853c4ac58da5506f`
- 稳定错误：社区超市开店检查经正式 HTTP 返回 `code=500`；服务端日志显示 `Unknown column 'd.tenant_id' in 'where clause'`。

该候选已完成三业态 Flutter 正式旅程、关班同步和会员创建，失败发生在 Onboarding Owner 通过 Resilience Owner 只读端口核验恢复演练证据时。

## 2. 根因与租户安全影响

`bak_backup_set` 是可覆盖多个租户的全局备份集合目录，租户范围保存在服务端生成的 `tenant_ids_csv` 与范围摘要中；`bak_restore_drill` 通过 `backup_id` 归属该集合。两张已发布表按设计均没有逐行 `tenant_id`。

`StoreOnboardingBackupMapper` 的 SQL 已使用参数化 `FIND_IN_SET(#{tenantId}, b.tenant_ids_csv)` 校验可信租户是否在备份范围内，但通用 MyBatis-Plus 租户插件仍为联结两侧注入 `d.tenant_id` 和 `b.tenant_id`，从而在正式 MySQL 失败。直接给历史表补列或放宽整个模块的租户保护都会扩大影响面，均不准入。

## 3. 批准的最小修复

- 仅在 `StoreOnboardingBackupMapper` 这一条全局目录只读边界上显式关闭自动租户列与数据权限列注入；
- 应用服务继续强制租户管理员权限，并且 `tenantId` 只能来自 `TrustedTenantContext`；
- SQL 继续以绑定参数检查 `b.tenant_ids_csv`，禁止字符串插值、客户端 tenant 或无范围查询；
- 增加静态回归，强制 Mapper 注解、参数化租户范围检查以及禁止 `${tenantId}`；
- 不修改已发布迁移、表结构、备份/恢复状态机、业务 API 或其他 Mapper 的租户插件行为。

该修复复用 `T2-BAK-001`、`T2-ONB-001`、`T2-INT-001` 和 `T2-E2E-004`，不新增业务能力或 Requirement ID。

## 4. 回归与证据边界
