## 4. 已否决的规避方案

- 把 Java 创建事件改成版本 `1`：会使事件版本与聚合版本不一致，并与后续提交事件版本重叠；改变已接受事件语义。
- 同时把调拨头初始版本改成 `1`：改变客户端乐观锁、状态机和既有 API 契约。
- Mapper 入库时把 `0` 偷换为 `1`：数据库列与事件正文不一致，破坏审计和重放。
- 删除创建事件：静默删除已接受能力，破坏事件消费者和审计链。
- 在 E2E 脚本直接改约束或关闭约束检查：属于数据库后门，不能形成正式产品证据。

上述方案均不准入。

## 5. 建议批准的最小前向修复

在获得项目发起人确认后：

1. 新增唯一 Flyway 版本（建议 `V202608260087`），先删除
   `ck_trf_outbox_version`，再以同名约束重建为 `aggregate_version >= 0`；
2. 历史迁移文件保持字节不变，不新增表、列、索引或业务能力；
3. 新增先红后绿的迁移策略测试和 MySQL 8.4 集成测试，证明：
   - 版本 `0` 的 `inventory.transfer.created.v1` 可写入；
   - 负版本仍被拒绝；
   - 版本 `1+` 的后续事件、唯一键、不可变触发器和 Flyway validate 不退化；
   - 空库迁移、既有 V86 环境升级、重复执行和安全前向修复通过；
4. 更新 Release 迁移目录和 G9A-R4 范围检查，使其只允许这一个已审批的新增迁移，
   仍禁止修改任何基线迁移；
5. 从新提交完整重跑 G9A-R4 全部 CI，不重跑失败 Job，不降低门禁；
6. 仅当三业态、22 Owner、12 个故障 seed、12 组守恒和全量 CI 全绿后，提交周门禁报告；
   项目发起人确认前 Finding 仍为 `OPEN`。

## 6. 风险、回退与证据边界

- DDL 风险：检查约束重建可能持有元数据锁；当前仅内部候选环境，仍需在迁移测试中记录耗时和失败行为。
- 兼容性：放宽范围仅从正整数到非负整数，与已接受 Transfer 事件 Schema 完全一致；负数继续失败关闭。
- 回退：数据库只允许前向修复；若迁移失败，应用启动失败关闭，不回写历史迁移，也不删除调拨事实。
- 本 CR 不解除 `T2-PAY-002/HWD-001/PRN-001/PAR-001`，不改变
  `T2-UAT-001/REL-001`、`T2-LIC-001/JSH-001` 状态。
