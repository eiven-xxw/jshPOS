# 后端持久化、组件复用与中文注释开发规范

> 文档编号：JSH-POS-DEV-STD-001
> 状态：Accepted
> 生效日期：2026-08-16
> 适用范围：鲸熵汇收银系统全部新增或实质修改的服务端代码

## 1. 决策结论

项目发起人提出的三项建议全部采纳，但按本规范增加架构、安全与可维护性边界：

1. 简单 SQL 使用 MyBatis-Plus，复杂 SQL 使用 Mapper XML；
2. 可以按需复用 Hutool 和其他成熟稳定组件，避免重复制造通用轮子；
3. 核心代码、领域实体和持久化实体必须具备有效中文注释。

当前服务端基线已经通过 RuoYi-Vue-Plus 集成 MyBatis-Plus 和 Hutool，本决策不新增第二套 ORM 或工具体系，只统一未来代码的使用方式。依赖版本以服务端父 POM 和锁定的 SBOM 为准。

## 2. SQL 分流判定

### 2.1 使用 MyBatis-Plus

同时满足以下条件时，优先使用 `BaseMapper` 和 Lambda Wrapper：

- 单表查询或单表写入；
- 条件数量有限、语义清晰，没有复杂分支；
- 不涉及聚合、窗口函数、复杂子查询或特殊锁；
- 不依赖特定执行计划或数据库方言；
- 字段映射直接，能够保持类型安全和可读性。

优先使用 Lambda 形式引用字段，避免字符串列名。分页必须有稳定排序；批量写入必须限制批次大小。核心状态更新仍须经过应用/领域不变量校验，不能把 `updateById` 当成状态机。

### 2.2 使用 Mapper XML

出现任一情况即使用 Mapper XML：

- 两表及以上关联；
- 聚合、分组、子查询、CTE、窗口函数或 UNION；
- 大量动态条件导致 Wrapper 难以阅读或审查；
- 需要乐观锁之外的显式锁、一致性读或数据库特性；
- 报表、导出、批处理或对执行计划敏感；
- 需要专用结果映射、字段别名或精确控制 SQL。

XML SQL 必须显式列字段、使用 `resultMap`、具备稳定排序，并说明租户条件、数据范围、索引预期和锁语义。禁止 `SELECT *`、字符串拼接输入和无条件全表更新/删除。

### 2.3 分层与租户底线

- MyBatis-Plus、XML Mapper 和 Persistence Object 属于基础设施层；领域层不得依赖它们。
- Controller 只能调用应用服务，禁止直接调用 Mapper。
- 核心模块通过 Repository/应用端口封装持久化；禁止跨模块 Mapper 修改别的领域表。
- `tenant_id` 只能取自可信服务端上下文。即使租户拦截器已生效，XML、Wrapper、原生 SQL、任务、批处理、缓存、导入导出仍须独立验证隔离。
- Mapper 变更必须覆盖跨租户攻击、空可信上下文 fail-closed、权限/数据范围和必要的执行计划测试。

## 3. 成熟组件选用规则

### 3.1 可以复用

字符串、集合、编码、IO、格式转换等没有领域语义的通用能力，可以优先使用 JDK、Spring、Hutool 或仓库已有成熟组件。已有组件满足需求时，不新增功能重复的依赖，也不创建 `CommonUtils`、`BizUtils` 一类无限膨胀的万能工具类。

### 3.2 必须评审

新增组件或新增传递依赖前必须说明：

- 具体用途以及现有能力为什么不足；
- 固定版本、维护状态和安全响应能力；
- 许可证及商业使用风险；
- 传递依赖、制品体积和运行时影响；
- 可替代方案、退出/升级成本；
- 对 Secret、PII、资金、租户和网络边界的影响。

合入前必须通过依赖差异、SBOM、漏洞、许可证和 Secret 门禁。Hutool 只按需使用受 BOM 管理的细分模块，禁止新增 `hutool-all`。

### 3.3 禁止用法

- 不得把领域规则写成通用工具方法；
- 不得用 Bean 拷贝直接改变订单、支付、退款、库存、审计等聚合状态；
- 不得用通用数值转换处理资金精度、数量换算或优惠分摊；
- 不得用默认系统时区代替门店业务时区和业务日；
- 不得绕过项目密码学、签名、脱敏和随机数规范；
- 不得在业务代码中使用临时 HTTP 工具绕过统一超时、重试、幂等、日志脱敏和可观测性；
- 不得仅为了少写几行代码引入大型组件。

支付、密码学、序列化兼容、数据库迁移和设备 SDK 优先采用官方或经过专项评审的实现，不能仅因 Hutool 提供同名能力就直接替换。

## 4. 中文注释规则

### 4.1 必须注释

- 聚合、实体、值对象、状态机及每个状态枚举值；
- 领域服务、应用用例、Repository/Mapper 和关键事务方法；
- 幂等键、冻结点、Outbox/Inbox、UNKNOWN、冲正和人工修复逻辑；
- 外部 API/事件契约、复杂 SQL、迁移和兼容/回退逻辑；
- 非显然的并发、锁、重试、缓存和安全处理。

### 4.2 实体注释最小内容

- 类级中文注释：实体业务职责、所属领域和数据主权；
- 金额字段：币种、最小货币单位或精度/舍入规则；
- 数量字段：计量单位、精度和换算语义；
- 时间字段：UTC、门店业务时区或业务日语义；
- ID 字段：生成方、唯一范围和是否可离线生成；
- 状态字段：状态机来源、合法值和终态含义；
- 哈希、版本、游标和幂等字段：稳定性、比较方式和不可变要求。

框架继承的通用审计字段不要求在每个实体重复解释，但本领域改变了其语义时必须说明。

### 4.3 注释质量

中文注释重点解释业务原因、不变量、边界和失败语义，不逐行翻译代码，不为 getter/setter 或显然赋值制造噪声。标识符、数据库字段和契约字段继续使用英文。代码调整后必须同步更新注释；错误或过期注释视为代码缺陷。

## 5. 代码评审核对表

- [ ] SQL 已按简单/复杂标准正确选择 MyBatis-Plus 或 XML；
- [ ] 没有复杂注解 SQL、超长 Wrapper、`SELECT *` 或不稳定分页；
- [ ] 可信租户、数据范围、权限和跨租户测试完整；
- [ ] 核心更新没有绕过状态机、不变量、版本和事务；
- [ ] 新组件有必要性、许可证、安全、SBOM 和替代方案证据；
- [ ] 没有新增 `hutool-all`、万能工具类或临时 HTTP 调用；
- [ ] 核心类、实体字段、状态、复杂 SQL 和失败语义有有效中文注释；
- [ ] 注释与代码、Schema、OpenAPI、迁移和测试保持一致。

## 6. 存量代码处理

本规范自生效日起约束新增代码和实质修改的代码。存量代码不做无业务收益的大规模机械重写；当文件因需求或缺陷被修改时，在同一职责范围内逐步补齐分层、SQL、组件和注释要求。涉及租户、资金、库存、支付、同步或安全缺陷的存量问题不得以“历史代码”为由延期。
