# 后端持久化、组件复用、参数对象与中文注释开发规范

> 文档编号：JSH-POS-DEV-STD-001
> 状态：Accepted
> 生效日期：2026-08-16
> 修订日期：2026-09-05（CR-T2LOC-001）
> 适用范围：鲸熵汇收银系统全部新增或实质修改的服务端代码

## 1. 决策结论

项目发起人提出的五项建议全部采纳，但按本规范增加架构、安全与可维护性边界：

1. 简单 SQL 使用 MyBatis-Plus，复杂 SQL 使用 Mapper XML；
2. 可以按需复用 Hutool 和其他成熟稳定组件，避免重复制造通用轮子；
3. 核心代码、领域实体和持久化实体必须具备有效中文注释；
4. 内部方法参数达到维护风险阈值时，使用职责内聚的参数对象稳定方法签名；
5. 区分领域聚合、持久化实体和 `record`，按数据风险登记访问策略、按 SQL 复杂度选择 MyBatis-Plus/XML/HYBRID，并把数据库中文注释作为 Schema 契约。

当前服务端基线已经通过 RuoYi-Vue-Plus 集成 MyBatis-Plus 和 Hutool，本决策不新增第二套 ORM 或工具体系，只统一未来代码的使用方式。依赖版本以服务端父 POM 和锁定的 SBOM 为准。

模型分型、数据访问策略、SQL 实现模式、数据库中文注释和存量治理边界详见 `JSH-POS-DEV-STD-002`、`ADR-027` 与 `ADR-033`；本文件继续规定日常后端编码和评审底线。

## 2. SQL 分流判定

### 2.1 使用 MyBatis-Plus

同时满足以下条件时，优先使用 `BaseMapper` 和 Lambda Wrapper：

- 单表查询或单表写入；
- 条件数量有限、语义清晰，没有复杂分支；
- 不涉及聚合、窗口函数、复杂子查询或特殊锁；
- 不依赖特定执行计划或数据库方言；
- 字段映射直接，能够保持类型安全和可读性。

优先使用 Lambda 形式引用字段，避免字符串列名。分页必须有稳定排序；批量写入必须限制批次大小。核心状态更新仍须经过应用/领域不变量校验，不能把 `updateById` 当成状态机。

`BaseMapper` 与 Mapper XML 不是互斥技术。同一个普通实体 Mapper 可以继承 `BaseMapper<T>` 处理简单 CRUD，同时声明由同 namespace XML 实现的复杂查询或专用批处理方法；此时该表 SQL 模式登记为 `HYBRID`。普通实体也可以因框架兼容或明确原因全部使用 XML，此时仍是 `CRUD_ENTITY + XML`。不得因为一张普通表存在少量复杂 SQL，就放弃其余简单 SQL 的 MyBatis-Plus 类型安全能力。

### 2.2 使用 Mapper XML

出现任一情况即使用 Mapper XML：

- 两表及以上关联；
- 聚合、分组、子查询、CTE、窗口函数或 UNION；
- 大量动态条件导致 Wrapper 难以阅读或审查；
- 需要乐观锁之外的显式锁、一致性读或数据库特性；
- 报表、导出、批处理或对执行计划敏感；
- 需要专用结果映射、字段别名或精确控制 SQL。

XML SQL 必须显式列字段、使用 `resultMap`、具备稳定排序，并说明租户条件、数据范围、索引预期和锁语义。禁止 `SELECT *`、字符串拼接输入和无条件全表更新/删除。

### 2.3 分层与租户底线

- 新增表必须分别登记数据访问策略 `CRUD_ENTITY/CONTROLLED_WRITE/APPEND_ONLY/READ_PROJECTION` 与 SQL 模式 `MP/XML/HYBRID`。简单单表 CRUD 不得因省略持久化实体而退化为注解 SQL；复杂 SQL 可以与 `BaseMapper + Lambda` 共存；核心不可变事实也不得因追求 MyBatis-Plus 使用率暴露通用更新或删除。
- `CRUD_ENTITY` 默认允许 `BaseMapper`；`CONTROLLED_WRITE` 只开放具名条件更新；严格 `APPEND_ONLY` 禁止任何覆盖更新和物理删除；`READ_PROJECTION` 对业务只读，仅允许 Projector/Rebuild 端口受控构建。Outbox/Inbox 若在同一行更新投递状态，必须登记为 `CONTROLLED_WRITE`，或拆分只追加载荷表与受控状态表。SQL 模式不能扩大访问策略授权，普通 `BaseMapper` 暴露的方法集超出后三类边界时不得继承。
- MyBatis-Plus、XML Mapper 和 Persistence Object 属于基础设施层；领域层不得依赖它们。
- Controller 只能调用应用服务，禁止直接调用 Mapper；应用服务通过领域 Repository 或应用查询端口访问持久化，禁止导入基础设施 Mapper。
- 核心模块通过 Repository/应用端口封装持久化；禁止跨模块 Mapper 修改别的领域表。
- `tenant_id` 只能取自可信服务端上下文。即使租户拦截器已生效，XML、Wrapper、原生 SQL、任务、批处理、缓存、导入导出仍须独立验证隔离。
- Mapper 变更必须覆盖跨租户攻击、空可信上下文 fail-closed、权限/数据范围和必要的执行计划测试。

### 2.4 服务端 MySQL 无物理外键

- `V202609050090` 之后的服务端 MySQL 迁移禁止新增 `FOREIGN KEY`、`REFERENCES`、
  `ON DELETE CASCADE` 或 `ON UPDATE CASCADE`；历史 V1—V89 不得为此回写。
- 必须保留主键、唯一键、`CHECK`、`NOT NULL`、不可变触发器和与查询模式匹配的普通索引。
- 引用存在性、同租户、状态和版本校验必须位于同一 Owner 应用服务或具名 Owner 端口，
  失败返回稳定领域错误；Controller、客户端和前端不得代替最终校验。
- 跨 Owner 只保存稳定事实 ID、版本/摘要或冻结快照，通过版本化事件、Inbox/Outbox 和
  一致性审计收敛；禁止跨 Owner Mapper 和数据库级联删除。
- 删除与更正继续使用停用、状态迁移、冲正或新事实，不得因无外键改为物理删除历史。
- POS SQLite 现有领域内外键不在本决策范围；其变更会影响离线原子性，必须另立 CR。

## 3. 成熟组件选用规则

### 3.1 可以复用

字符串、集合、编码、IO、格式转换等没有领域语义的通用能力，可以优先使用 JDK、Spring、Hutool 或仓库已有成熟组件。已有组件满足需求时，不新增功能重复的依赖，也不创建 `CommonUtils`、`BizUtils` 一类无限膨胀的万能工具类。

### 3.2 必须评审

新增组件或新增传递依赖前必须说明：

- 具体用途以及现有能力为什么不足；
- 固定版本、维护状态和安全响应能力；
- 许可证及商业使用风险；
- 传递依赖、制品体积和运行时影响；
- 可替代方案、退出/升级成本；
- 对 Secret、PII、资金、租户和网络边界的影响。

合入前必须通过依赖差异、SBOM、漏洞、许可证和 Secret 门禁。Hutool 只按需使用受 BOM 管理的细分模块，禁止新增 `hutool-all`。

### 3.3 禁止用法

- 不得把领域规则写成通用工具方法；
- 不得用 Bean 拷贝直接改变订单、支付、退款、库存、审计等聚合状态；
- 不得用通用数值转换处理资金精度、数量换算或优惠分摊；
- 不得用默认系统时区代替门店业务时区和业务日；
- 不得绕过项目密码学、签名、脱敏和随机数规范；
- 不得在业务代码中使用临时 HTTP 工具绕过统一超时、重试、幂等、日志脱敏和可观测性；
- 不得仅为了少写几行代码引入大型组件。

支付、密码学、序列化兼容、数据库迁移和设备 SDK 优先采用官方或经过专项评审的实现，不能仅因 Hutool 提供同名能力就直接替换。

## 4. 内部方法参数对象规则

### 4.1 触发条件

自研内部业务方法出现 5 个及以上业务参数时，默认必须改用不可变、具名且职责内聚的参数对象。这是代码评审触发阈值，不是“4 个参数以内一律合理”的许可；出现以下任一情况时，即使未达到 5 个也应提前封装或拆分职责：

- 两个及以上相邻参数类型相同，调用时容易交换顺序；
- 出现两个及以上布尔开关，调用点难以表达含义；
- 多个可选参数需要按组合满足约束；
- 一组参数在多个方法间重复传递或经常共同变化；
- 参数共同表达金额、时间窗口、身份、分页、状态迁移或幂等语义。

### 4.2 类型和命名

- 应用用例入口优先使用 `XxxCommand` 或 `XxxQuery`；
- 领域内部优先使用明确值对象、`XxxParameters` 或语义明确的 `XxxContext`；
- 仅跨 REST、消息、连接器或进程边界的传输模型使用 `DTO` 名称；
- 单一方法私有且概念不外泄时，可使用靠近使用点的私有嵌套 `record`；需要跨类复用时，放入相应应用或领域模型包，不得反向依赖接口层 DTO；
- 优先使用不可变 `record` 或等价不可变类型，字段名必须表达业务含义，构造后不得被调用方修改。

参数对象必须围绕一个用例、业务概念或稳定变化轴组织。若参数彼此无关，应拆分方法、应用用例或类职责，不能为了满足阈值机械装进一个对象。

### 4.3 校验与安全边界

- 接口边界负责格式、必填和长度等输入校验；应用/领域层仍须校验状态、金额、数量、权限、幂等和其他业务不变量；
- 金额、币种、数量、时间、状态、哈希和幂等键应保留项目规定的精确类型或值对象，不得退化为无类型字符串；
- 可信 `tenant_id`、门店数据范围、权限和操作者上下文继续从服务端可信上下文注入，可以作为独立的强类型上下文参与调用，但不得混入客户端可构造的 DTO；
- 禁止通过 Bean 拷贝让客户端字段覆盖可信上下文、聚合状态、审计字段或其他受保护字段；
- 禁止用 `Map<String, Object>`、`Object[]`、布尔标志集合、万能 `Context`/`DTO` 或无关字段拼盘规避参数数量。

### 4.4 例外与评审

框架规定的回调/重写签名、第三方接口、序列化模型、数据记录载体和依赖注入构造器不机械套用 5 参数阈值，但例外必须在代码评审中说明。依赖注入构造器参数过多通常表示类职责过宽，应优先拆分类或引入职责清晰的协作组件，禁止把服务依赖包装成 DTO。

本规则适用于新增或实质修改的方法，存量代码不做无收益的全仓机械重写。涉及资金、退款、库存、租户、幂等或审计的长参数列表优先治理；重构必须补充或复用回归测试，证明成功路径、参数校验、租户越权、幂等和状态不变量没有变化。

## 5. 中文注释规则

### 5.1 必须注释

- 聚合、实体、值对象、状态机及每个状态枚举值；
- 领域服务、应用用例、Repository/Mapper 和关键事务方法；
- 幂等键、冻结点、Outbox/Inbox、UNKNOWN、冲正和人工修复逻辑；
- 外部 API/事件契约、复杂 SQL、迁移和兼容/回退逻辑；
- 非显然的并发、锁、重试、缓存和安全处理。

### 5.2 实体注释最小内容

- 类级中文注释：实体业务职责、所属领域和数据主权；
- 金额字段：币种、最小货币单位或精度/舍入规则；
- 数量字段：计量单位、精度和换算语义；
- 时间字段：UTC、门店业务时区或业务日语义；
- ID 字段：生成方、唯一范围和是否可离线生成；
- 状态字段：状态机来源、合法值和终态含义；
- 哈希、版本、游标和幂等字段：稳定性、比较方式和不可变要求。

框架继承的通用审计字段不要求在每个实体重复解释，但本领域改变了其语义时必须说明。

持久化实体的所有映射业务字段都必须有中文说明。`record` 的类型职责使用中文 Javadoc 说明，每个组件通过 `@param` 说明业务含义、单位、可信来源或不可变要求；只给外层容器写一句总注释不能替代组件说明。数据库表和字段注释按 `JSH-POS-DEV-STD-002` 执行，不得以 Java 注释替代 Schema 注释。

### 5.3 注释质量

中文注释重点解释业务原因、不变量、边界和失败语义，不逐行翻译代码，不为 getter/setter 或显然赋值制造噪声。标识符、数据库字段和契约字段继续使用英文。代码调整后必须同步更新注释；错误或过期注释视为代码缺陷。

## 6. 代码评审核对表

- [ ] SQL 已按简单/复杂标准正确选择 MyBatis-Plus 或 XML；
- [ ] 新增表已分别登记访问策略与 `MP/XML/HYBRID` SQL 模式，选择理由、Owner、租户来源和更新/删除边界完整；
- [ ] 普通实体的简单 CRUD 已使用普通持久化实体、`BaseMapper` 和 Lambda Wrapper，复杂方法可由同一 Mapper XML 实现；核心事实未暴露危险的通用 CRUD；
- [ ] 没有复杂注解 SQL、超长 Wrapper、`SELECT *` 或不稳定分页；
- [ ] 应用/领域层未依赖基础设施 Mapper、Wrapper 或 Persistence Entity；
- [ ] 可信租户、数据范围、权限和跨租户测试完整；
- [ ] 核心更新没有绕过状态机、不变量、版本和事务；
- [ ] 5 个及以上业务参数的方法已使用内聚参数对象，或已记录允许例外；
- [ ] 未达阈值但存在同类型易错参数、多个布尔开关或共同演进参数时，已评估提前封装；
- [ ] 参数对象不可变、命名符合所在层，并且没有万能 DTO、通用 Map 或客户端可信上下文污染；
- [ ] 新组件有必要性、许可证、安全、SBOM 和替代方案证据；
- [ ] 没有新增 `hutool-all`、万能工具类或临时 HTTP 调用；
- [ ] 核心类、实体字段、状态、复杂 SQL 和失败语义有有效中文注释；
- [ ] `record` 的每个组件具有有效中文 `@param`，新增数据库表和每个字段具有有效中文 `COMMENT`；
- [ ] 注释与代码、Schema、OpenAPI、迁移和测试保持一致。

## 7. 存量代码处理

本规范自生效日起约束新增代码和实质修改的代码。存量代码不做无业务收益的大规模机械重写；当文件因需求或缺陷被修改时，在同一职责范围内逐步补齐分层、SQL、组件和注释要求。涉及租户、资金、库存、支付、同步或安全缺陷的存量问题不得以“历史代码”为由延期。
