# CR-T2G9R4-004：G9A-R4 同步故障夹具端点修复

## 1. 触发证据

- 候选提交：`ed8d97f94872f037ef851ea40a1f5786103406fb`
- GitHub Actions Run：`32885777234`
- 失败 Job：`formal-runtime`（`97926555954`）
- 稳定错误：ACK 丢失固定 seed 调用同步传输时返回 `SYNC_REMOTE_404`。

## 2. 根因与影响

正式 POS 运行时把同步端点装配在服务根地址的 `api/pos/v1/` 下；新增的 ACK 丢失故障夹具却直接把服务根地址交给 `PosSyncHttpTransport`，因而访问了不存在的 `/sync/push`。该失败发生在测试夹具构造层，未改变服务端同步契约、Inbox/Outbox 事实或业务状态。

## 3. 批准的最小修复

故障夹具复用 `SessionBoundPosRuntime` 已冻结的同步 API 根路径 `api/pos/v1/`。夹具仍只模拟“服务端已接收但客户端未持久化 ACK”，随后关闭并重新装配文件 SQLite 运行时，以原 event ID、payload hash 和幂等身份恢复。

禁止借此变更同步 API、业务状态机、资金/库存/租户语义、已发布迁移、门禁阈值或外部执行边界。

## 4. 验收与回退

- Dart 格式、静态分析和目标测试装载通过；
- 新提交从头执行完整 G9A-R4 CI，不重跑原失败 Job；
- 正式 JAR 必须观察到原事件并由生产同步协调器收敛，本地 Outbox 最终为 ACKED；
- 若新候选仍失败，保留失败证据并继续按确定性根因做独立最小修复；
- 回退仅撤销夹具端点修复，不触碰正式业务数据或迁移。
