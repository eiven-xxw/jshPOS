## 2. 需求生命周期

`DRAFT → READY → IN_PROGRESS → IMPLEMENTED → VERIFIED → ACCEPTED`

- `DRAFT`：只有想法，禁止编码。
- `READY`：ID、来源、范围、非目标、验收、不变量和依赖齐全。
- `IN_PROGRESS`：已分配执行人和目标版本。
- `IMPLEMENTED`：代码与开发者测试完成，但不能表示可上线。
- `VERIFIED`：独立测试和证据完成。
- `ACCEPTED`：产品/业务及必要角色签字。

`BLOCKED` 表示存在外部输入或规格决策缺口；`DEFERRED` 表示已明确后置。

## 3. RTM 规则

`rtm.csv` 是机器可读的需求追踪入口。每个 PR 至少关联一个需求 ID；每个需求必须关联来源、实现路径和测试证据。P0/P1、状态机合法/禁止边、资金库存不变量必须达到 100% 覆盖。

## 4. 变更控制

基线后的功能、规则、数据、接口或非功能指标变更必须：

1. 创建 CR；
2. 说明付费客户/业务价值、通用复用率、交付成本和替代方案；
3. 分析状态机、金额、库存、租户、API、数据迁移、安全和上线影响；
4. 更新来源规格、RTM、Schema、测试和发布计划；
5. 经产品、架构、QA及必要业务负责人批准；
6. 不得突破法律、租户隔离和资金安全底线。

## 5. 证据目录

自动化输出写入 `artifacts/t0/` 或相应阶段目录且不提交大体积产物；验收摘要、命令、版本、结果和报告哈希写入 `docs/evidence/`。实机照片、支付对账单和含敏感信息的材料存放在受控证据库，仓库只保存脱敏索引。
