# CR-T2G9R4-011：G9A-R4 合成恢复正式栈装配修复

## 1. 触发证据

- 候选提交：`d4626fb`
- GitHub Actions Run：`32892736089`
- 失败 Job：`formal-runtime`（`97949113347`）
- 正式运行栈 Artifact：`t2-g9a-r4-formal-runtime`，下载归档 SHA-256 `a8fabda63f942c3bc21385ee7d8edcd5ef463b2bd85a5d060692f0b685fde6b5`
- 三条 Flutter 正式旅程、订单同步和全部 Outbox ACK 已完成；后置开店检查稳定失败为 `external P0 must remain BLOCKED`。

进一步核验表明四项外部检查实际均为 `BLOCKED`，失败原因是内部必需项 `BACKUP_RECOVERY` 为 `UNAVAILABLE`：商业 JAR 没有装配 T2-BAK-001 已接受范围内的 `SYNTHETIC_RESTORE` 备份源和空环境恢复目标。因此门店状态正确保持 `CHECK_FAILED`，不是外部 P0 被错误放行。

## 2. 边界判断

冻结的 R4 三业态正式旅程明确包含“合成备份恢复”。仅把验收脚本改成接受 `CHECK_FAILED` 会掩盖正式装配缺口，不准入。

本修复复用 `T2-BAK-001`、`T2-ONB-001`、`T2-INT-001` 与 `T2-E2E-004`：只补齐内部低等级恢复证据的正式运行时装配，不新增业务能力、Requirement ID、API、表或迁移。

## 3. 批准的最小修复

- 增加只生成六类合成载荷的内部备份源；不读取 MySQL、对象存储业务对象、配置、真实证据或生产数据；
- 增加按演练 ULID 隔离的空文件恢复目标，校验租户范围摘要、恢复点、六类对象完整性和路径边界；失败保留 `ABORTED` 证据，禁止越界或覆盖；
- 对同样没有逐行 `tenant_id` 的备份集合主 Mapper 显式关闭通用租户/数据权限列注入；应用层继续用可信 `AuthorizedScope`、请求摘要、租户集合等值和范围摘要授权，XML 禁止字符串插值；
- 仅在同时设置 `SYNTHETIC_RESTORE` 和 `INTERNAL_ONLY_NOT_PRODUCTION` 双重确认时装配；配置不完整启动失败，`prod`、`production` 和 `prod-*` profile 一律拒绝；
- 正式 CI 每次运行临时生成并掩码 AES-256 密钥，备份对象和恢复目标仅位于当前 Runner 临时目录；同一 JAR 重启窗口复用同一受控密钥；
- 三业态后置旅程必须经正式 HTTP API 创建六对象加密备份并完成九项恢复检查；开店检查同时要求所有内部项通过、四项外部 P0 精确保持 `BLOCKED`；
- 固定故障 `R4-F11` 改为对已通过的合成备份注入 Schema 不兼容，必须失败关闭且原订单、原备份和游标事实保持不变。
