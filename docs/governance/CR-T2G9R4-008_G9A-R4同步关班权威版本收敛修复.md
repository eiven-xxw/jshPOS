# CR-T2G9R4-008：G9A-R4 同步关班权威版本收敛修复

## 1. 触发证据

- 候选提交：`3ae549f7fe9441b9ea30dfa4e372945b5999556e`
- GitHub Actions Run：`32889173620`
- 失败 Job：`formal-runtime`（`97937878235`）
- 稳定现象：便利店、零食折扣店和社区超市三条正式旅程均完成业务步骤，但最终只读证据显示 `shift.closed.v1` 保持 `RETRY / REJECTED_RETRYABLE / PROCESSING_SERVICEEXCEPTION`，每条旅程各残留一个未收敛 Outbox。

## 2. 根因与产品影响

POS 关班事件冻结的是本地班次前序版本；服务端班次会因已经同步的成交、现金退款等权威现金事实独立推进版本。同步转换此前把本地版本直接交给普通在线关班的严格等值乐观锁，导致服务端合法领先时必然冲突，关班事实永久重试。

普通在线关班仍应要求客户端版本与服务端完全一致；只有已经由正式 Inbox 验证身份、幂等键与载荷摘要的同步关班，才需要在行锁下验证“服务端版本不落后于本地冻结版本”，并以服务端当前权威版本和现金账本执行关闭。

## 3. 批准的最小修复

- 新增 `CloseSyncedShift` 内部命令及 `ShiftSubmissionPort.closeSynced`，不新增 REST API；
- `ShiftEventDispatcher` 将 `shift.closed.v1` 映射到同步专用端口，继续保留原 event ID、幂等键、聚合身份和本地前序版本；
- `ShiftService` 复用同一关班资金、审批、审计、Outbox 与幂等实现：普通关班版本必须严格相等，同步关班要求服务端版本大于等于本地版本；
- 实际 `UPDATE` 始终使用锁定后的服务端权威版本。服务端落后、操作者/门店不符、金额或审批不一致仍失败关闭；
- 不修改数据库、已发布迁移、HTTP/OpenAPI、资金口径或外部边界。

该修复复用 `T2-SYN-001`、`T2-POS-005`、`T2-INT-001`，不新增业务能力或 Requirement ID。

## 4. 回归与证据边界

- 新增服务端版本合法领先时同步关班成功、服务端落后时失败关闭的应用服务回归；
- 新增 Sync dispatcher 必须调用同步专用端口并保留本地前序版本的回归；
- 普通在线关班严格版本检查与原审批规则继续回归；
- 新候选必须从头执行完整 G9A-R4 CI，三业态 `shift.closed.v1` Outbox 必须全部 ACKED；
- 外部支付、真实设备/外设、伙伴现场、完整 Alpha 与生产执行继续为 0；
- `G9A-E2E-P1-001` 在完整门禁和项目发起人确认前保持 `OPEN`。
